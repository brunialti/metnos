## Root causes

1. **A relevance rejection was converted into approval.** Both localized
   `web_rerank` prompts already defined `{"top": []}` as the correct response
   when nothing was relevant. `_llm_rerank_candidates` instead classified that
   valid result as a technical failure and restored the original backend order.
   An existing unit test incorrectly required this behavior. The caller then
   crawled candidates that the relevance check had rejected.

2. **The current upstream engine had no useful recall for this query.** The
   production SearXNG configuration enables Bing web as its general-web engine.
   A bounded direct replay returned ten unrelated Italian news results in
   0.237 seconds. In an isolated adapter probe, the complete normalized query
   reached each selected provider. There is no evidence here that Metnos
   truncated the query or that changing a local rank weight could recover
   missing AMD ROCm documents. A separate cache-contamination defect was not
   established.

3. **Ordinary search implicitly expanded into a crawl.** A normal topic search
   fetched result pages and traversed one link level, with a default tier-2
   capacity of 2,000 pages. It discarded the value of ranked snippets and
   enlarged the work after the erroneous relevance fallback. The original
   `host_seed` was a crawl anchor derived from a returned seed, not an explicit
   domain restriction in the user's request.

4. **The advertised rerank budget was not applied.** The executor defined an
   eight-second rerank timeout but did not pass it to `call_llm`. The candidate
   supplies it to the shared helper, whose deadline covers its actual provider
   request. A bounded structured-payload limit now accommodates the configured
   wide candidate pool without the helper rejecting an ordinary 30-result
   payload at its smaller generic default.

5. **BM25 repeated collection work for every document.** The previous
   per-document function tokenized the entire collection and recomputed
   frequencies each time. The candidate computes all scores in one collection
   pass while preserving the formula and ordering.

6. **A resolved singleton was not normalized at invocation.** The first
   positive HTTP attempt exposed a second pipeline failure: a step reference
   selected one URL, producing a string, while `read_urls_html` correctly
   required an array. Planner-stage coercion cannot know the final type of an
   unresolved reference. Normalization now occurs at the common invocation
   boundary using the signed argument schema, before argument-dependent
   controls. It wraps a string only when the property declares exactly
   `type="array"`; it does not split values, change their contents, widen
   targets, alter unions that admit strings, or relax item validation.

## Follow-up: final presentation and current upstream availability

### Additional root cause and minimal correction

The recorded log for `660a79ac76924b2d` contains:

```text
[output_policy] mode=list action=drop_describe+final producer-kind=urls
```

The planner had included `describe_entries`; the output policy removed it.
`read_urls_html` declares a default metadata-list presentation, and that default
overrode the fact that the plan had just read page contents. This was not a
failure of the final language model: the synthesis never ran.

The correction reuses the existing text-summary branch for terminal web content
readers. It preserves an existing synthesis or inserts one, supplies the original
query, and selects the relevance preset. It does not add a topic/provider
heuristic or new intent classifier. A pure `find_urls` terminal retains its
list view. An explicit typed `list` intent, counts, mutations, terminal tabular
transforms and HTTP HEAD retain their existing presentation. Recognizing the
user's requested action correctly remains the responsibility of the existing
intent/planning boundary; this change does not infer an additional "links only"
intent from arbitrary natural-language phrases.

intermittent and has not become an operationally validated provider.

One route that leaves the other user's shared service untouched would be an
explicitly authorized **Metnos-only SearXNG endpoint**, selected through the
existing `METNOS_SEARXNG_URL` configuration contract, with a provider that first
passes a bounded live recall test. This needs no new Metnos selector or bespoke
search engine. A concrete existing integration candidate is the official
[SearXNG Brave API adapter](https://docs.searxng.org/dev/engines/online/brave.html#brave-api-engine),
which is already present in both source versions and requires an API key.
This is separate from the previously tested HTML `brave` engine; that engine's
429 response neither verifies nor disproves the API's behavior.

The API candidate has **not been called or established as useful**. Before
enabling it, an operator must approve the provider/account, credential custody,
query-data disclosure, quota and monetary budget, and the additional service's
maintenance ownership. No price, subscription, availability guarantee or API
credential is assumed here. A supplied, authorized key would permit a single
isolated retrieval acceptance check before spending model time on the original
Italian HTTP turn and its final source-grounded answer. If no provider is
authorized, the present candidate should retain its honest empty response;
deploying the Bing upgrade alone must not be represented as fixing search.
This is an optional operational alternative, not evidence that an API or a paid
service is indispensable. The following free check provides a concrete reason
to investigate query formulation before choosing that alternative.

### Consequence for the proposed fix

An API is **not demonstrated necessary**: the free engine has now retrieved
useful sources for the same subject. The immediate evidence supports testing a
general, bounded query-formulation strategy before replacing the provider. A
candidate to evaluate is ordering the most specific subject concept first while
retaining the user's remaining entities and actual constraints. An unsuccessful
relevance check could authorize at most one separately budgeted reformulation;
it must never authorize restoring unrelated results.

That strategy is a proposal, **not an implemented or generally validated fix**.
In particular, the successful two-term query drops the explicit news wording;
it does not yet show that a reformulation preserving every original requirement
will retrieve current updates. Validation must cover Italian and English,
multiple subjects and negative cases, preserve explicit domain/date/exclusion
constraints, and finish with the unchanged original user query through actual
search, reading and a source-grounded final answer. Hardcoding `ROCm AMD`,
unconditionally dropping qualifiers, or silently treating documentation as new
news would not satisfy that requirement.

The current result changes the priority of the earlier provider alternative:
validate this free path first. No paid-service decision or claim of total Bing
failure is justified by the original query's missing coverage.

cleanup block. Temporary result artifacts remain available for audit; no user
