0 · Verdetto

Il sistema funziona nella configurazione di default (Engine v2 attivo), ma l'audit ha trovato un quadro coerente e serio: la migrazione a Engine v2 è a metà strada e ha lasciato dietro di sé (a) ~9.000 LOC di codice morto/duplicato eliminabili, (b) una fascia di componenti dichiarati attivi ma di fatto inerti o no-op («latent-broken», violano §2.8), (c) diversi buchi di sicurezza sfruttabili, (d) una bomba a orologeria nello scheduler che azzera tutto il lavoro in background al prossimo restart, (e) drift doc↔codice pervasivo (ADR fantasma, default dichiarati diversi da quelli reali). Nulla di irrecuperabile a livello di impianto — l'architettura ibrida, il retrieval con vocabolario chiuso e la synthesis test-first sono confermati validi dalla letteratura. Ma una lista precisa di cose va uccisa, riparata o decisa.

1 · 🔴 URGENTE — prima di qualsiasi restart o deploy

Lo scheduler intero muore al prossimo riavvio. runtime/scheduler_v2/builtin_callbacks.py:459-464 carica 7 task builtin (apply_ager, apply_executor_ager, synt_suggest, introvertiva_propose/apply, proposals_cleanup, lifecycle_summary) via SourcelessFileLoader(".../_v1_tasks.pyc").

Verificato ✓: _v1_tasks.pyc non esiste (e .gitignore esclude *.pyc); la sorgente runtime/scheduler.py da cui sarebbe «frozen» non esiste e non è mai stata in git. Il commit 078796a (migrazione _legacy) ha rimosso l'artefatto. Il servizio gira ora solo perché il .pyc è caricato in RAM da un boot precedente. install_default_callbacks solleva FileNotFoundError a metà → nessun callback registrato; il boot wrap (metnos_http_server.py:160) lo cattura come «non-fatal» → il daemon parte senza alcun job in background, in silenzio. Secondo sito: http_routes_admin.py:1141 → HTTP 500.

Azione immediata (finestra: finché il processo vivo ha il bytecode in RAM) — estrarre la sorgente dal processo in esecuzione e materializzarla in runtime/jobs/:

import inspect, sys
m = sys.modules.get("metnos_scheduler_v1_tasks")
for name in ("task_apply_ager","task_apply_executor_ager","task_synt_suggest",
             "task_introvertiva_propose","task_introvertiva_apply",
             "task_proposals_cleanup","task_lifecycle_summary"):
    fn = getattr(m, name, None)
    if fn: open(f"/opt/metnos/runtime/jobs/_recovered_{name}.py","w").write(inspect.getsource(fn))

Poi rimuovere l'anti-pattern SourcelessFileLoader (viola §7.1 e §7.10) e wirare le 7 task da sorgenti jobs/ — è il TODO già scritto a builtin_callbacks.py:457.

2 · Causa-radice trasversale: migrazione Engine v2 incompleta

Convivono due sistemi decisionali: Engine v2 (runtime/engine/, default METNOS_ENGINE_V2=1) e la cascata Praxis legacy (runtime/_legacy/ via shim sys.modules). Engine v2 è l'unico vivo nel default: engine.dispatch.run_turn ritorna sempre un risultato (il terminator sintetizza error→answer), quindi tutto ciò che segue if _engine_v2_res is not None: return log è morto su query normali.

Da questa migrazione a metà discendono, a cascata:

  • ADR fantasma: ADR 0164 non esiste (decisions/0164* assente), né engine/ARCHITECTURE.md, ma sono citati ovunque in engine/. Verificato ✓.
  • Ramo di fallback Praxis morto E rotto (C1).
  • Doppio store di feedback disallineato (autopath vs multi_tool_paths).
  • Dashboard admin che leggono store legacy svuotati (/admin/praxis, /admin/aporiae).
  • Job legacy con wrapper rotto su store congelati.
  • Duplicazione engine/executor.py ↔ _legacy/praxis_executor.py (~80%).
  • Champion/challenger darwiniano (ADR 0162) non portato in Engine v2 → dormiente.

3 · Findings CRITICAL

Legenda: ✓ verificato di persona · A alta confidenza (agente, evidenza citata) · SEC sicurezza

C1 — Cascata Praxis eseguita e risultato scartato + blocco di consumo morto ✓

agent_runtime.py:5899-5966

Nel path default (METNOS_PRAXIS=1, non force-compound) la if a 5899 chiama _try_praxis_cascade (costo LLM + side-effect) e salva in _praxis_res; ma il blocco che lo consuma (extend steps, record_observation, return log) è nidificato sotto elif _force_legacy_compound: (5913) → mai eseguito quando la if è presa. E nel ramo elif, _praxis_res è azzerato a 5914, quindi i controlli a 5919/5926 sono sempre falsi. Il blocco 5919-5966 è dead code in entrambi i rami; nel path if la cascata gira e l'esito è buttato → si cade su return error.

Impatto reale basso (raggiunto solo se Engine v2 crasha), ma bug logico + spreco netto.

Fix: eliminare l'intero ramo 5898-5980 + _try_praxis_cascade (§7.1).

C2 — Validator _check_args: required-check è un no-op, ma default-ON e costa una 2ª LLM call ✓

engine/validator.py:83-88 · engine/__init__.py:47-50

Il loop for r in required: ha solo continue/fall-through, non appende mai un errore. Il required-check promesso non esiste; resta solo requires_one_of + type-check superficiale. Eppure is_validator_enabled() è default True (contro la docstring del validator che dice «default OFF»), e al fallimento dispatch chiama un secondo proposer.propose (LLM wise, 25-30s) prima di eseguire. Costo > valore.

Fix: required-check placeholder-aware (from_step/${...} risolti a runtime non sono «mancanti») oppure declassare il validator a sola annotazione e default OFF.

C3 — Stage 6 (verifier semantico description↔code, ADR 0114 L6) silenziosamente disattivato A

synth_request.py:517 · synt_multistage.py:502,517

_llm_wise(system,user,max_tokens=5000) chiamato con think=False → TypeError, inghiottito da un try/except il cui ramo ammette il synth. Ogni synth-on-the-fly di produzione salta la verifica semantica. Il provider sotto accetta think — è solo il wrapper a non forwardare.

Fix: def _llm_wise(system,user,max_tokens=5000,**kwargs) + passare **kwargs. Idem _llm_middle.

C4 — Tier think/num_predict scartati → fast/middle/wise identici a livello provider ✓

llm_router.py:76-82 · llm_provider.py:1059-1063

make_provider_from_spec legge solo model+endpoint; LlamaCppProvider.__init__ non accetta think/num_predict → inerti. La SoT §11/ADR 0146 («la differenza fra tier è solo think/num_predict») è contraddetta: i 3 tier locali sono identici salvo che un caller passi esplicitamente quei parametri. Analogamente il commento «default OFF in prod» del classifier è falso: il drop-in systemd setta METNOS_INTENT_CLASSIFIER=1 (verificato ✓).

Fix: propagare gli extra-key della spec al provider come default, oppure rimuovere i campi morti e dichiarare onestamente in ADR 0146.

C5 — SEC Guard di irreversibilità aggirabile da trailing-slash e set binari incompleto ✓

system/admin.py:376-417

L'unico blocco hardcoded non-derogabile (re-validato a fire-time) è sconfitto: _FORBIDDEN_PATHS confrontato con == senza normalizzazione → rm -rf /etc BLOCCATO ma rm -rf /etc/ PASSA (idem //, /usr/). E il guard scatta solo per rm/mv/cp/dd/mkfs/shred/wipefs → passano find / -delete, chmod -R 777 /etc, truncate -s0 /etc/passwd, tee /etc/sudoers.d/x, ln -sf /dev/null /etc/shadow.

Fix: os.path.normpath(value.rstrip("/")) + match per prefix-containment; classificare per target_kind della signature, non per lista binari.

C6 — SEC Signature whitelist troppo grossolane → esecuzione silenziosa di codice/file-delete A

safety/canonicalize.py:219-301 · safety_seeds/v1.toml

La signature cattura binario:subcomando:target_kind e ignora i flag che portano l'azione: find ~ -delete → find:*:fs:user (whitelist) → esecuzione silenziosa, nessuna card; env X=1 /tmp/evil.sh → env:*:* → esegue binario arbitrario; graylist copre awk 'BEGIN{system(...)}', sed … e, tee /etc/sudoers.d/x. admin è EXPOSE_TO_PLANNER=True → un LLM pilotabile può emettere argv whitelisted-ma-distruttivo.

Fix: codificare il flag pericoloso nel subcomando (find -exec/-delete → subcomando mai matchato da whitelist *); denylist di token «shell-equivalent» in _check_forbidden_argv; trattare env/xargs/find -exec come wrapper trasparenti. Fix a leva più alta dell'audit.

C7 — SEC SSRF non autenticato in photo_web_proxy ✓

http_routes_agent.py:1379-1432 (route 2460, urlopen 1416)

/agent/photos/web?u=<url> è sotto il prefisso anonimo ANON_WHITELIST_PREFIXES (/agent/photos/) e fa urllib.request.urlopen(raw_url, timeout=8) con unica validazione startswith("http"). Verificato ✓ (nessun is_private/is_loopback). Un remoto non-auth forza GET verso 127.0.0.1:8770/8765, metadata cloud 169.254.169.254, LAN interna; segue i redirect.

Fix: risolvere l'IP e rifiutare private/loopback/link-local/reserved a ogni hop; limitare a https:// + allowlist host CDN; togliere l'endpoint dal prefisso anonimo.

C8 — SEC Sandbox di esecuzione codice «planned», non attiva A + letteratura

ADR 0159 L4 · skill_audit.py

Metnos genera ed esegue codice Python a runtime (synth + skill importate) su un host con file personali, mail, credential store Fernet decifrabile e sudoer. Esecuzione in-process (Level 0) = un solo codegen sbagliato o un manifest importato malevolo ha pieno accesso al processo. La letteratura (smolagents, microVM/seccomp) considera l'exec diretto di codice non fidato inaccettabile. Sign+Jaccard verificano provenienza/somiglianza, non il comportamento a runtime.

Fix (prioritario): 3 livelli di trust → handcrafted in-process; synth locale in subprocess seccomp-BPF + netns vuoto + rootfs read-only + no credential store; importate in container/microVM no-network-by-default. Attivare prima di abilitare skill importate in produzione.

6 · Convergenza con lo stato dell'arte (2023-2026)

Punti di forza confermati:

  1. ✓ Modalità ibrida ReAct + piano-in-una-shot (LLMCompiler, LangChain plan-execute: il piano multi-step taglia costo/latenza vs ReAct puro).
  2. ✓ Retrieval ibrido lessicale+dense con RRF (RAG-MCP: 3.2× accuracy, −50% token) + vocabolario chiuso verbo_oggetto come vantaggio sui framework con API di terzi.
  3. ✓ Synthesis test-first + self-verification + admission multi-layer (Voyager, Self-Debug ICLR 2024 +12% con test).

Divergenze/rischi confermati:

  • Fastpath cosine su azioni irreversibili = anti-pattern: «check email vs send email» semanticamente vicine ma azioni opposte (Agentic Plan Caching NeurIPS 2025; CacheAttack 86% hijack, arXiv 2601.23088). In tensione con §2.8/§2.9. → match su intent canonicalizzato per i piani con action-verb + gate pre-esecuzione.
  • 14 strategie prefilter = over-engineering: l'IR conferma rendimenti decrescenti oltre 2-3 ranker; trie/bloom non sono ranker (indici/membership). Rischio ToolFlood/Attractive-Metadata. → potare a 2-3 segnali + cross-encoder re-rank + penalità di provenienza non-first-party.
  • Eval auto-confermante del classifier FT (arXiv 2406.08660): holdout non indipendente gonfia l'accuratezza. → holdout di query reali vs baseline embedding-anchor zero-shot; se Δ<5-8pp il FT non si ripaga.
  • Split compound deterministico su congiunzioni: la letteratura raccomanda LLM per il multi-intent. → regex solo ad alta precisione, LLM-fallback, guardie su entità quotate. Applicazione corretta di §7.9.
  • Replan non di prima classe: il piano-in-una-shot senza replan esplicito è datato (LATS/LangChain hanno un replan node). → rendere il replan un nodo esplicito su violazione di precondizione.
