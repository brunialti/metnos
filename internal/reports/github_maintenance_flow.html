Manutenzione issue di un repo GitHub

Un flusso componibile di executor governato da comandi schedulati — non un programma di sistema. Con fase di analisi e risoluzione frontier e approvazione dell'admin a ogni passo decisionale.

Principio architetturale. La gestione di un repo non è una funzione core cablata (es. l'attuale jobs/github_watcher.py): è una query schedulata che compone gli executor attraverso il planner. I dati di trattamento vivono in uno store (layer-dati), il flusso vive nei comandi. Sostituibile, ispezionabile, modificabile come qualunque comando — senza toccare il sistema.

Le quattro qualità

RobustoIdempotente per status: nessun doppio post. Gate di sicurezza, dedup semantico, fallback se il frontier è giù.
SempliceSolo executor + 2 comandi schedulati. Zero orchestratore di sistema, zero logica di flusso nel core.
PotenteTier frontier (Opus/GPT‑5) per analisi profonda e proposta di risoluzione; memoria semantica per il riuso.
CompletoAnello chiuso: rilevamento → analisi → approvazione → azione → memoria. Nulla resta a metà.

Il flusso a colpo d'occhio

new → prepared → approved → posted — lo status nel db rende ogni passo idempotente.

Fase 3 — Analisi e risoluzione con il frontier

Il cuore potente. Per le issue non già coperte dalla memoria (fase 2), il flusso invoca il tier frontier (Opus 4.x / GPT‑5) — non il tier locale — con il contesto necessario: testo dell'issue e commenti (read_issues_github), eventuali issue correlate e riferimenti. Il frontier produce: (a) una classificazione (bug / domanda / supporto / feature), (b) una diagnosi del problema, (c) una bozza di risposta azionabile, (d) opzionali azioni proposte (label, chiusura, link a doc/commit). Tutto resta una proposta: nessuna azione parte senza la fase 5.
Fallback robusto. Se il frontier è irraggiungibile o fuori budget, la issue resta new e viene segnalata all'admin come «da trattare a mano»: mai una risposta inventata, mai un fallimento silenzioso (§2.8).

Approvazione dell'admin — mai senza

Ogni risposta che esce verso GitHub passa dalla fase 5. L'admin riceve sul proprio canale (Telegram o mail) la terna issue + diagnosi + bozza e decide: approva (la bozza diventa accepted_reply, approved), modifica (corregge il testo, poi approva), oppure rifiuta (il record resta fermo, niente post). Solo le issue approved attraversano il Comando B. Il dedup ad alta confidenza (fase 2) può auto-rispondere solo sotto un gate di sicurezza esplicito e configurabile — e comunque notifica l'admin a posteriori.

I due comandi schedulati

Nessun codice di flusso: due voci run_user_query nello scheduler, ognuna una query in linguaggio naturale.

# Comando A — ogni 30 min: prepara
tasks.create(schedule="every 30m", query=
  "leggi le nuove issue aperte di brunialti/metnos, per ognuna cerca nel
   db le issue simili già risolte, classificala e analizzala col frontier,
   poi salva nel db la bozza di risposta come 'prepared' e avvisami")
# Comando B — su approvazione (o giornaliero): posta
tasks.create(schedule="on-approval", query=
  "leggi dal db le issue approvate non ancora postate e pubblica la
   risposta sul relativo issue, poi segnale come 'posted'")

Cosa si ritira dal core

Con questo flusso diventano obsoleti — da rimuovere —: runtime/jobs/github_watcher.py (il programma-orchestratore), github_dedup.py e github_analyze_callback.py (la loro logica diventa, rispettivamente, il gate di classificazione del Comando A e la fase 3 frontier). Resta solo github_issue_qa_store.py come layer-dati dietro write/read/find_issues.
