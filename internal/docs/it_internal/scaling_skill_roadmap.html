1. Survey letteratura e best practices

1.1 Tool routing at scale: il problema misurato

La letteratura recente (2023-2026) converge su un risultato netto: la accuracy del tool-use degrada drammaticamente quando il pool supera ~50-100 tool. I numeri pubblicati piu' rigorosi:

  • ToolLLM / ToolBench (Qin et al., arXiv:2307.16789, 2023): il primo benchmark a 16.464 API reali. Mostra che senza retrieval i modelli falliscono sopra le 100 tool. Introduce DFSDT (Depth-First Search Decision Tree) ma soprattutto API retrieval module (BGE-base trained) per selezione top-K prima della pianificazione.
  • API-Bank (Li et al., arXiv:2304.08244, 2023): 73 API + 314 dialoghi. Tier evaluation 3-livelli (call, retrieve+call, plan+retrieve+call). Mostra che il retrieval di tool e' un sotto-problema distinto e misurabile.
  • Benchmarking Tool Retrieval for LLMs (ACL 2025 Findings): documenta cali drastici: 50 tool ~85% acc → 200 tool 41-83% → 740 tool 0-20%. Position bias: tool in posizioni 40-60% del prompt 22-52% accuracy vs 31-32% a inizio/fine.
  • The Tool Selection Problem (tianpan.co, 2026-04): bench piu' recente su 70 server MCP / 527 tool: routing flat semantic search degrada >1000 tool; two-tier coarse→fine mostra +17-18% retrieval quality.
  • Trace-Free+ (curriculum learning, 2025): riduce degrado del 29.23% e migliora success rate +60.89% scaling oltre 150 tool.

Implicazione per Metnos: a ~70 tool oggi siamo nella zona sicura, ma il salto a 250 (10 skill) ci porta nella zona di crash documentata. La mitigazione e' obbligatoria, non opzionale, oltre le 5 skill.

1.2 Tool RAG / Retrieval-Augmented Action Selection

Pattern dominante 2024-2026: trasformare il pool flat in indice vettoriale, query→top-K tool semanticamente vicini, iniettare SOLO i K nel prompt.

  • ToolLLM (originale): BGE-base retriever ad-hoc, ricava 5-10 candidate da 16K. Senza retrieval il task fallisce, con retrieval ~75% success.
  • Tool-to-Agent Retrieval (arXiv:2511.01854, 2025): generalizza il pattern a multi-agent: si recuperano agenti specializzati invece di singole tool, riducendo prompt e migliorando granularita'.
  • Agent-as-a-Graph (arXiv:2511.18194, 2025): knowledge graph su (tool, agente, capability, dipendenze) per retrieval gerarchico tipato.
  • vLLM Semantic Router (2025, blog): production-grade, semantic + metadata filtering hybrid. Documenta che flat similarity degrada >1000 tool, propone two-stage retrieval.
  • GRETEL (arXiv:2510.17843): goal-driven retrieval con trial/feedback loop.

Applicabilita' a Metnos: - Pro: gia' abbiamo BGE-M3 ONNX int8 in produzione (ADR 0134, semantic affinity fallback). Riuso immediato dell'infrastruttura. Compatibile con grammar GBNF (ADR 0133): il pool inviato al grammar diventa il top-K invece del pool flat. - Contro: serve indicizzazione tools.idx rebuild su sign/load di executor (gia' abbiamo signing pipeline, manca solo hook). - Costo migrazione: M (1-2 settimane). Zero rottura vincoli: tutto deterministico §7.9 + self-hosted.

1.3 MCP (Model Context Protocol) e precedence

MCP Anthropic supporta server multipli simultaneamente. Pattern documentati:

  • Tool merging: l'agente legge il manifest combinato e routea per server-name. Nessuna precedence automatica: collision name = errore esplicito o prefix <server>/<tool> (convenzione filesystem MCP).
  • MCP connector (docs.anthropic.com): supporta allowlist/denylist per server e tool, configurazione manuale gerarchica (request > session > workspace).
  • Code execution with MCP (anthropic.com/engineering, 2025): pattern emergente "tools-on-demand" — il manifest non viene caricato upfront, ma il modello invoca list_tools(server) quando serve. Riduce token consumption ma aumenta round-trip.

Rilevante per Metnos: il _PROVIDER_SUFFIX_MARKERS (ADR 0136) e' una versione embrionale del routing MCP. Va promosso a policy esplicita di precedence (vedi §5 User-tunable preference profile).

1.4 Sicurezza supply-chain MCP — segnale forte 2025-2026

La survey sulla sicurezza ha rivelato che il problema non e' teorico:

  • OWASP MCP Top 10 (2025): MCP04 e' "Software Supply Chain Attacks & Dependency Tampering".
  • OX Security (2025): poisoning 9/11 MCP registry pubblici, RCE su 6 piattaforme paying-customers live.
  • Antiy CERT: 1.184 skill malevole confermate su ClawHub (largest AI agent supply-chain incident).
  • postmark-mcp (npm trojanizzato 2025): silently BCC ogni email outbound al dominio attaccante. Esfiltrazione memo/fatture/password reset.
  • EscapeRoute (Filesystem MCP): bypass prefix check + symlink → full RW.
  • VentureBeat (2026): "92% exploit probability" su stack MCP enterprise.

Implicazione per Metnos: il modello Metnos di skill importer da agentskills.io (ADR 0123) deve assumere a default che le skill siano untrusted. Sandbox bubblewrap esistente e' giusto in direzione, ma serve: - profilo bubblewrap per-skill (oggi unico globale) - network whitelist per-skill dichiarativa - capability allowlist firmata per-skill (oggi capability_registry e' globale) - audit log per-skill separato - supply-chain verification: sha256 manifest pinning, optional code signing GPG

1.5 Hierarchical agentic systems

Pattern consolidato 2024-2026 per scalare:

  • HuggingGPT (2023): primo dispatcher LLM verso modelli specializzati.
  • AutoGen (Microsoft, 2024): leader light-weight + group chat di sub-agenti.
  • LangGraph (LangChain, 2025): acyclic graph esplicito per routing condizionale.
  • Google ADK (2025): supervisor-style hierarchy a piu' livelli.
  • AgentOrchestra (arXiv:2506.12508, 2025): framework gerarchico general-purpose.
  • HTAA (arXiv:2604.10917): two-stage "toolset agentization" — gruppi di tool fine-grained astratti come "agent tool" coarse.
  • ToolPlanner (XiaoMi, arXiv:2409.14826): multi-granularity instructions con path planning.

Applicabilita' a Metnos: il PLANNER unico Gemma 26B sopravvive bene fino a ~150-200 tool. Oltre, va valutato two-tier: dispatcher fast (Qwen3:8B, gia' nei 3 tier) sceglie macro-area (mail/calendar/files/web/system), poi PLANNER middle lavora sul pool della macro-area. Risparmio token 60-70%, latency probabilmente neutrale (un round-trip fast in piu' ma prompt PLANNER molto piu' corto).

1.6 Plugin precedence policies (prior art software)

  • VS Code: commands registrati in package.json, conflitti gestiti via when clauses (deterministico) + Command Palette mostra tutti i match (l'utente sceglie). Nessuna precedence implicita.
  • Eclipse RCP: extension points con priority numeric esplicita, fallback first-registered-wins.
  • IntelliJ Platform: actions in <action id="..."> univoci; conflict di shortcut → user dialog.
  • Zapier: collision risolta UI-side (user sceglie account/app per ogni step). Default = last-used.
  • n8n: nodes named-unique, niente collision a livello di routing (l'utente disegna il flusso).

Lezione per Metnos: tutti i sistemi maturi non risolvono automaticamente la collision verb_obj fra provider, ma offrono default user-configurabile. La nostra _PROVIDER_SUFFIX_MARKERS e' un compromesso accettabile per query con marker espliciti; per query ambigue serve preference profile (vedi §5).

2. Analisi profonda del problema sotto tutti i punti di vista

2.1 Punto di vista del LLM PLANNER

Gemma 4 26B con tool-use nativo + grammar GBNF mostra ~22/22 PASS sulla battery attuale (ADR 0135). Cosa cambia a 250-500 tool?

  • Token budget prompt: oggi sezioni planner.j2 IT compose ~30K token. Ogni nuovo tool aggiunge ~150-250 token (manifest description + args_schema). A 250 tool → ~50K, a 500 tool → ~75K. Il modello ha context 32K/slot (ADR 0117 setup llama.cpp --parallel 2 -c 65536). Crash sicuro sopra 250 tool senza intervento.
  • Position bias (ACL 2025 Findings): documentato 22-52% accuracy su tool in middle del prompt vs 31-32% a estremi. La sezione mail/calendar/web/photos/system e' relativamente robusta perche' raggruppa, ma _OPT_IN_SECTIONS non risolve scaling.
  • Grammar GBNF crescita non-lineare: il pairTool discriminated union (ADR 0133) ha rule per ogni tool. A 500 tool il grammar passa da ~20KB a ~200KB. Il parser llama.cpp ha overhead lineare per rule lookup ma quadratico per recursive sub-rules {tool}ObjD{d}I{i}. Stimo +30-50% latency per step su 500 tool, ma serve bench reale.
  • Studi sull'accuracy: ToolBench documenta degrado anche con grammar constraints — il problema non e' il parsing ma la scelta semantica. Il vincolo formale non risolve "quale tool scegliere".

Conclusione: il PLANNER attuale e' robusto fino a ~150-200 tool. Oltre, serve action space pruning a monte (retrieval) o two-tier dispatcher.

2.2 Punto di vista latency

Numeri attuali (stimati da bench precedenti): - Prefilter+intent: ~370ms - PLANNER step 1: ~3-4s con grammar (ADR 0133 bench 70s→41s) - Vaglio LLM (opt-in): +3-5s per step

A 500 tool senza intervento: - Prefilter: ~600ms (rank lineare token-based scala bene a 500) - PLANNER step: probabile +30-50% per parser grammar = 5-6s - Total turn 3 step: ~20-25s (oggi ~15s)

Con Tool RAG + top-K=15: - BGE-M3 query embedding: ~30ms - KNN su 500 vettori 1024d: ~3ms (numpy dot product) - Prefilter ridotto: ~200ms - PLANNER step su pool ridotto 15: ~2-3s - Total: ~10-12s (40% miglioramento)

Costo locale = energia. Strix Halo a piena potenza ~120W picco. 5s in piu' per turno × 100 turni/giorno = 500s × 120W = 60Wh/giorno = 1.8 kWh/mese. Marginale ma misurabile.

2.3 Punto di vista semantic disambiguation

Quando 2+ skill espongono send_messages, cosa significa "manda una mail" dell'utente?

Ipotesi: 1. L'utente vuole sempre lo stesso provider (caso 80%): single-user, account principale. Default user-tunable risolve. 2. L'utente sceglie context-aware (caso 15%): "manda mail di lavoro" → outlook account work; "scrivi a Mario" → contact in gmail. Risolvibile via lookup contact → account. 3. L'utente vuole essere chiesto ogni volta (caso 5%): power-user multi-account. Disambiguation dialog (gia' abbiamo request_disambiguation_from_user).

Default behavior policy proposta: - Single skill installata per (verb, obj): zero disambiguation, dispatch automatico. - 2+ skill installate per (verb, obj): lookup ~/.config/metnos/skill_preferences.toml. Se key match → dispatch. Se non match → dialog choice_with_preview. - Marker semantico nella query ("via gmail", "su slack") → bypass preference, usa marker.

Il _PROVIDER_SUFFIX_MARKERS attuale e' giusto come tier 1. Manca il preference file (tier 2) e il fallback dialog (tier 3, gia' esiste).

2.4 Punto di vista security

Capability inflation: 13 capabilities canoniche oggi. Ogni skill puo' richiederne 2-5 nuove. A 20 skill → potenziali 100+ capability se non c'e' deduplica strutturale. Mitigazione: capability vocabulary chiuso come gli OBJECTS §2.2, con escalation manuale per nuovi termini.

Sandbox per-skill: oggi bubblewrap profile e' unico globale (runtime/sandbox/...). Una skill malevola che ottenga code execution puo' interagire con TUTTI i dati Metnos. Mitigazione: profile dichiarativo per-skill nel manifest [sandbox]:

[sandbox]
network_allowed = ["api.googleapis.com", "oauth2.googleapis.com"]
fs_read = ["~/.local/share/metnos/skills/google-workspace/"]
fs_write = ["~/.local/share/metnos/skills/google-workspace/cache/"]
exec_allowed = []

Verifier al load: confronta capability dichiarate vs sandbox profile (es. messaging:send_outbound richiede almeno un network_allowed).

Credenziali scaling: ADR 0131 (single store Fernet+HKDF) gia' scala. Verificare: rotation policy per scope (oggi non c'e'), revoke fingerprint via CLI (gia' c'e').

Audit log noise: oggi turn JSONL contiene tutto. Filtraggio per skill_origin nei tool importati. Necessario campo tool_provenance strutturato in observation.

Supply-chain: - sha256 pinning del manifest [provenance].source_sha256 (gia' c'e' in ADR 0123). - Verifica pre-install: matching sha contro registry trusted (TBD). - Code signing opzionale GPG (long-term).

2.5 Punto di vista manutenzione

Ogni skill importata ha: - dipendenze Python (gmail-api-python-client, ecc.) - eseguibili CLI esterni (es. gh, aws) - credenziali OAuth (refresh token TTL, scope changes upstream) - breaking changes upstream API

Strategia: - Lockfile per-skill: requirements.lock con sha256 wheel. - Health check daily per ogni skill installata (dry-run di list_messages con timeout 5s). - Skill dormancy detection (ADR 0136) gia' c'e' per credenziali mancanti — estendere a "skill failing health check". - Update upstream: snapshot pre-update, rollback su test fail. - Maintainer SLA: ogni skill ha [maintenance] con last_upstream_check, compat_tested_until.

Burden: con 20 skill, ~20 min/settimana di triage health check failures se tutto va bene. Con upstream incompatibility frequente, fino a 2h/settimana.

2.6 Punto di vista UX

  • Discoverability: a 250 tool nessun utente puo' memorizzare. Serve:
  • /help <verb>: lista oggetti supportati per verbo + provider.
  • /help <obj>: lista azioni disponibili per oggetto.
  • Gallery executor HTTP gia' c'e' (ADR 0078), va arricchita di filtri per skill_origin.
  • Auto-suggestion skill: query "manda whatsapp a Mario" + nessuna skill WhatsApp installata → suggerisci install whatsapp-skill (richiede registry curato).
  • Cognitive overhead: l'utente NON deve preoccuparsi della scelta provider per default. Single-action mental model: "manda mail" funziona, basta.
  • Onboarding: prima installazione skill → wizard "preferisci Google su Outlook per email?" → popola preference file.

2.7 Punto di vista testing

Smoke battery attuale ~25 min per ~50 tool. A 250 tool con stessa coverage ratio ~2h. Non pratico come canary pre-deploy.

Strategia: - Smoke battery prioritized: 30-50 query "must work" cross-skill (15 min target). Esegue sempre. - Per-skill regression suite: ~10 query per skill. Esegue solo sulla skill modificata (cambio manifest, sign, upstream update). - Property-based testing (vedi §5 innovazioni): generate input fuzzing dal manifest args_schema, invariants su output schema. - Pipeline cross-skill: scenari multi-skill ("filtra mail su Gmail, salva allegati su Drive, evento su Calendar"). Cap 5-10 scenari core, ogni nightly. - Sampling statistico: smoke su sample 20% random delle query del corpus reale (turns/*.jsonl).

2.8 Punto di vista data isolation

Skill A (es. gmail) puo' leggere data scritto da skill B (es. drive)? Oggi: si', stesso filesystem ~/.local/share/metnos/, stesso sqlite.

Modello proposto: - Capability boundary: skill_data_scope = "private" | "shared" | "global". Default private. - Private scope: ~/.local/share/metnos/skills/<skill_id>/data/ — accesso solo da quella skill. - Shared scope: workspace dichiarativo (vedi §5 skill subdomains). - Global scope: solo per skill trusted_publisher (registry curato).

Implementazione via bubblewrap fs_read/fs_write (vedi §2.4).

3. Visione architetturale

3.1 Breve termine — 1-2 mesi (5-10 skill)

Obiettivo: chiudere i 9 gap noti, raggiungere 5-10 skill in produzione stabile.

  • Bench scaling prefilter (Fase A) — misurazione decision-gated: decidere se serve switch a Tool RAG basato su dati Metnos a pool 250, non per estrapolazione letteratura. Mantiene il prefilter attuale se token-flat >= 85% Recall@5; switch a Tool RAG full (Fase A.1) SOLO se scende sotto soglia.
  • Capability vocabulary chiuso, validazione al load
  • Sandbox profile per-skill nel manifest [sandbox]
  • Smoke battery prioritized + per-skill suite
  • Preference profile utente per disambiguation 2+ skill stesso (verb, obj)
  • Tool provenance strutturato in observation
  • Health check daily per skill
  • Smoke routing assertion estesa a cross-skill scenarios

Vincoli rispettati: tutti. Self-hosted intatto, vocabolario chiuso intatto, prefilter attuale preservato (alterato solo se Fase A.1 attivata da evidenza).

Capacita' nuove: gmail+drive+calendar (google-workspace) + slack + outlook + immich + nextcloud, fino a 7 skill third-party stabili.

Rischi: refactor descrittivo dei manifest sandbox potrebbe creare regressioni se non rigorosamente testato. Mitigazione: opt-in METNOS_PER_SKILL_SANDBOX=1 fase 2 testing.

Costo: ~25-30 giorni-uomo.

3.2 Medio termine — 3-6 mesi (20-50 skill)

Obiettivo: refactor strutturale per scaling 20-50 skill.

  • Two-tier planning: dispatcher fast (Qwen3:8B) per macro-area + PLANNER middle su pool ridotto
  • Skill subdomains (workspace mode: lavoro/personale/casa)
  • Hierarchical capability namespace: gmail.read, drive.write invece di global capability set
  • Registry curato self-hosted (skill.metnos.com) + skill review pipeline
  • Federated skill discovery: indici remoti firmati
  • User preference learning passivo (osservare scelte, suggerire default dopo N conferme)
  • Auto-suggested skill install per query non risolte (con consent dialog)
  • Multi-user data isolation reale (multi-user gia' previsto in pairings.db)

Vincoli rispettati: 6 su 7. Il vocabolario chiuso §2.2 resta. Self-hosted resta. Italian-first resta. Vaglio+sandbox+capability resta (con per-skill enhancement). Tier middle default resta. Pattern §7.3 generale (subdomains non hardcoded per skill specifica).

Capacita' nuove: marketplace privato di skill, modalita' di lavoro, gestione team/famiglia condivisa con permessi.

Rischi: complessita' two-tier (debug, observability). Mitigazione: feature flag, fallback automatico single-tier su error.

Costo: ~45-60 giorni-uomo.

3.3 Lungo termine — 6-18 mesi (100+ skill)

Obiettivo: ecosistema plugin sostenibile, scaling teorico 100+ skill.

  • Tool RAG gerarchico: indice per domain → indice per tool nel domain
  • Skill capability sandboxing fine-grained (cgroup + per-skill bubblewrap profiles)
  • Code execution on-demand (pattern MCP list_tools lazy)
  • Skill marketplace federato (publisher signing GPG)
  • Auto-generated property tests dal manifest
  • Skill compatibility matrix (alpha/beta/stable, deprecation policy)
  • Voice + visione multimodale (ADR 0117 base, espansione)
  • Edge runtime (rust client sync-protocol gia' previsto in Phase 7)

Vincoli rispettati: 7 su 7. Possibile pivot: a 500+ skill, il PLANNER middle locale potrebbe non bastare anche con Tool RAG; fallback frontier diventa piu' frequente. Mitigazione: speculative-execution o fine-tuning locale del PLANNER su corpus utente reale.

Rischi: scope creep. Mitigare con decision gate dopo medio termine.

Costo: ~80-120 giorni-uomo.

4. Roadmap dettagliata (8 fasi)

Fase A — Bench scaling del prefilter (decision-gated, NON sostituzione cieca)

Correzione 17/5/2026: la versione precedente di questa fase prescriveva direttamente Tool RAG come Fase 0 obbligatoria. Roberto ha ricordato che bench empirico embedding-vs-token del 4/5/2026 (ADR 0075) ha confermato token-based 92.3% Recall@5 sul pool corrente (~50-70 tool). Il vocabolario chiuso §2.2 + ADR 0136 marker provider + ADR 0134 semantic fallback gia' offrono un prefilter ibrido in cui il token-rank ha piu' segnale del setup tipico ToolBench/ToolLLM. La decisione di switch a Tool RAG full va presa SULLA BASE di dati Metnos-specifici, non per estrapolazione dalla letteratura su corpus eterogenei.

  • Obiettivo: misurare quando (e SE) il token-flat degrada al crescere del pool, prima di decidere il refactor del prefilter.
  • Deliverable:
  • runtime/bench_prefilter_scaling.py (~150 LOC): genera pool sintetico di 100/150/200/250 tool fittizi (descrizione + affinity plausibili, derivati per template dai 70 reali), poi rilancia un corpus di 200 query con ground-truth top-K atteso. Misura Recall@5 e MRR su tre ranker: (a) token-flat attuale, (b) BGE-M3 puro, (c) ibrido token+semantic (rerank semantic sui top-30 token).
  • Report /tmp/bench_prefilter_scaling.md con 3 curve + soglia di degrado (es. Recall@5 < 80% → switch giustificato).
  • ADR nuovo 0140-prefilter-scaling-bench.md che documenta la metodologia e i risultati.
  • Effort: S (1-2 gg).
  • Pre-requisite: nessuno.
  • Validation criteria: la decisione di proseguire o sospendere Fase A.1 si basa SOLO sulla soglia di degrado misurata, non su priors.
  • Decisione condizionata:
  • Se token-flat resta >= 85% Recall@5 anche a pool 250 → Fase A.1 rimandata, mantenere ADR 0134 fallback semantic come unica integrazione. Risparmio: 8 gg-uomo.
  • Se token-flat scende sotto 80% a pool >= 150 → Fase A.1 attivata (Tool RAG full come descritto sotto), gate di soglia esplicito nel codice.
  • Test plan: bench su corpus query reali (4086 turn log degli ultimi 30 giorni) per cross-validazione del ground truth sintetico.
  • Roll-back: nessuno, la fase non muta il prefilter di produzione.

Fase A.1 — Tool RAG con BGE-M3 (CONDIZIONATA al risultato di Fase A)

  • Obiettivo: SOLO se Fase A dimostra degrado token-flat oltre soglia, trasformare pool flat in indice vettoriale + top-K injection nel grammar.
  • Deliverable (invariati):
  • runtime/tool_index.py (~200 LOC): build/load/query indice tool. Riusa affinity_semantic.py infrastructure (ADR 0134).
  • Hook in runtime/sign.py post-sign: rebuild incrementale ~/.cache/metnos/tool_index/.
  • Modifica runtime/prefilter.py::rank_with_intent: aggiunge semantic top-K candidates, merge con token-rank esistente.
  • Modifica runtime/tool_grammar.py::filter_pool_for_grammar: input top-K invece di pool full.
  • ADR aggiornato 0141-tool-rag-conditional.md.
  • Test: 30 unit + integration su query corpus reale (100 query).
  • Effort: M (8-10 gg) SE attivata.
  • Pre-requisite: Fase A con risultato di switch.
  • Validation criteria: smoke battery 22/22 PASS; bench latency P95 -20% su query a multi-skill misurato (NON simulato); recall@15 >= 95% su routing label.
  • Rischio regressione: prefilter altera top-K, possibile miss di tool oggi sempre in pool. Mitigazione: fallback "always-keep" per critical tool (_OBJECT_PRIMARY_TOOLS ADR 0075).
  • Test plan: A/B con METNOS_TOOL_RAG=0|1 su 200 query reali.
  • Roll-back: feature flag, default 0 in fase iniziale.

Fase B — Capability namespace gerarchico

  • Obiettivo: capability <domain>.<action> (es. gmail.read, drive.write) invece di set globale piatto.
  • Deliverable:
  • runtime/capability_registry.py refactor: tabella tipata {domain: {action: description}}.
  • Manifest schema: capabilities = ["gmail.read", "files.write_local"].
  • Migration script per i 17 executor google-workspace gia' importati.
  • Vaglio aggiornato: check capability prefix.
  • ADR nuovo 0141-capability-namespace.md.
  • Effort: M (6-8 gg).
  • Pre-requisite: Fase A non bloccante, parallelo.
  • Validation criteria: zero regressione vaglio + smoke; 100% capability esistenti mappate al nuovo namespace.
  • Rischio regressione: vaglio puo' rifiutare tool legacy con vecchio formato. Mitigazione: shim back-compat 30 giorni.
  • Test plan: matrix capability × executor (~50 combinazioni).
  • Roll-back: shim mantiene vecchio formato funzionante.

Fase C — Sandbox per-skill dichiarativo

  • Obiettivo: profile bubblewrap per-skill nel manifest, validazione al load.
  • Deliverable:
  • Manifest [sandbox] schema: network_allowed, fs_read, fs_write, exec_allowed.
  • runtime/sandbox/per_skill.py: builder bubblewrap args da manifest.
  • runtime/loader.py::verify_sandbox_consistency: check capability vs sandbox (es. messaging:send richiede network_allowed non vuoto).
  • Profile default sicuro: solo ~/.local/share/metnos/skills/<id>/ RW, no network.
  • Audit log strutturato: ogni invocazione skill scrive skill_id, sandbox_profile_sha.

5. Innovazioni proposte per Metnos

5.1 Tool RAG ibrido marker + semantic + token (gia' parzialmente prior art, ma combinazione originale)

L'innovazione e' combinare: 1. Token-rank esistente (deterministico, ~3ms) come primo filtro coarse (top-50). 2. BGE-M3 semantic (ADR 0134 infra) come fine ranking (top-15). 3. Marker provider (ADR 0136) come precedence override. 4. Always-keep primary tools (_OBJECT_PRIMARY_TOOLS) per recall guarantee.

Tutti deterministici §7.9 eccetto BGE-M3 (gia' in produzione). Compatibile con grammar GBNF (ADR 0133): il top-15 diventa l'input di filter_pool_for_grammar.

Differenza vs ToolLLM retriever: noi non addestriamo un retriever ad-hoc, usiamo BGE-M3 pre-trained + hybrid con token-rank legacy. Zero training, zero infrastruttura GPU per training.

5.2 Workspace mode con auto-detect contestuale

Estensione: oltre allo switch manuale (/workspace work), Metnos puo' inferire il workspace attivo da context: - Heuristics deterministica: ora del giorno (work 9-18 → work, altrimenti personal), location (in ufficio → work), calendario (meeting in corso → work). - Configurabile in workspaces.toml con auto_rules. - Mai bloccante: l'utente puo' sempre override esplicito.

Pattern §7.9 puro, niente ML.

5.3 User preference learning passivo

Quando l'utente dispatcha "manda mail" senza marker, e il sistema chiede "Gmail o Outlook?" e l'utente sceglie Gmail per N volte (N=3 default), Metnos propone "Vuoi che Gmail sia il default per email?" con dialog di consent.

Deterministico: counter persistente in sqlite per (verb, obj, provider_chosen). Soglia configurabile. Niente ML reale, ma effetto adattivo.

5.4 Skill capability sandboxing differenziato

(Gia' coperto in Fase C, ma innovazione vs MCP standard: dichiarazione deduttiva da capability dichiarate.)

Esempio: capability messaging:send_outbound deduce automaticamente network_allowed non-vuoto. Capability files:write_local deduce fs_write con scope. Verifier al load valida coerenza.

Vantaggio vs MCP (oggi tutto manuale per server admin): default sicuro deducibile, riduce burden manuale.

5.5 Property-based testing da manifest

Generatore Python (gia' c'e' hypothesis library, optional dep) che da manifest args_schema genera input random e verifica: - output rispetta schema dichiarato - ok=true implica almeno un results/entries non-null - truncated=true implica available_total presente - reverse_pattern dichiarato → reverse effettivamente eseguibile (per executor revertible)

Sostituisce ~50% dei test smoke statici manualmente scritti. Resta cap su test e2e di flow reale.

5.6 Two-tier planning con macro-area locale (Qwen3:8B)

(Gia' coperto in Fase F.) Innovazione vs HTAA / ToolPlanner: usa il tier fast gia' presente nei 3 tier Metnos, zero nuovo modello da scaricare. Riusa stesso process llama.cpp con seconda slot.

5.7 Skill provenance + immutable audit chain

Ogni invocazione skill scrive observation con campi: - tool_provenance = "imported:google-workspace@1.2.3" - skill_sha256 = "<digest manifest>" - sandbox_profile_sha = "<digest profile>" - capability_used = ["gmail.read"]

Audit log JSONL append-only firmato (HMAC chain). Permette post-hoc incident response se skill malevola compromessa upstream.

5.8 Federated skill discovery con publisher trust tiers

skill.metnos.com (o registry federati): publisher classificati verified | community | unverified. Default install: solo verified. Override esplicito per community con consent banner. Unverified = manual install only.

Trust tier deterministico da sha256 pinning + GPG signature opzionale + community vote (long-term).

5.bis Alternative scalabili al prefilter (oltre token vs Tool RAG)

Sezione aggiunta 17/5/2026 dopo nota di Roberto: il framing originale "token-flat vs Tool RAG semantic" ha ristretto il dominio delle soluzioni. La letteratura IR e i sistemi agentici offrono almeno 10 approcci alternativi, molti deterministici §7.9 e compatibili con vocabolario chiuso §2.2. Bench Fase A dovrebbe valutare alcuni di questi in parallelo, NON solo BGE-M3 semantic.

5.bis.1 Verb-first dispatch table (deterministico, O(1))

L'intent extractor gia' produce intent.verb (read/write/find/...). Tabella verb → list[tool] pre-calcolata al boot. Query → dispatch O(1) al sub-set di tool che hanno quel verbo. Pool ridotto da N a N/23 (numero verbi canonici).

  • Pro: zero LLM, zero embedding, deterministico. Vocabolario chiuso §2.2 perfettamente adatto. Compatibile grammar GBNF (top-K input).
  • Con: query ambigue verbo ("mostra le foto") richiedono fallback. Risolvibile con prima fase verb-dispatch + seconda fase token-rank sul sub-set.
  • Effort: S (1 gg). Reuse vocab.py::_OBJECT_PRIMARY_TOOLS esteso.
  • Letteratura analoga: Apache Lucene BooleanQuery con MUST/SHOULD clauses; Elasticsearch terms filter pre-aggregation.

5.bis.2 SQLite FTS5 inverted index (battle-tested, scalable)

Indice full-text SQLite FTS5 su (name, description, affinity) di ogni tool. Query → SQL FTS5 con BM25 ranking integrato + custom tokenizer (porter stemmer IT+EN). SQLite gia' in produzione (mnestoma, persons.sqlite, scheduler v2): nessuna nuova dipendenza.

  • Pro: scalable a 10K+ documenti senza degrado, BM25 nativo, persistente. Stesso pattern usato da Notion search, GitHub issues search, VS Code symbol search.
  • Con: serve build/refresh ad ogni sign executor (analogo a ADR 0093 async index build). Re-encoding affinity per stemmer.
  • Effort: M (3-5 gg). 1 nuovo modulo + hook in sign.py.
  • Letteratura: SQLite FTS5 docs (sqlite.org/fts5.html); paper "Anserini: Reproducible Ranking Baselines" (2017).

5.bis.3 Bloom filter pre-screen (cheap negative filter)

Per ogni tool, costruisci Bloom filter dei suoi token caratteristici (name + verbi + oggetti + affinity tokens). Query → check Bloom in O(1) per tool. Tool con Bloom miss → escluso senza token-rank. Pool ridotto 80-95% in O(N) con basso costante (un AND bitwise per tool).

  • Pro: cost-effective screening prima del rank piu' costoso. No false negatives su token esatti (Bloom garantisce). Falsi positivi rari (1-5%) si filtrano comunque a valle.
  • Con: serve update Bloom su sign. Memory footprint ~100 byte/tool.
  • Effort: S (2 gg). runtime/tool_bloom.py standalone.
  • Letteratura: "Bloom filters in Probabilistic Verification" (1970); uso pratico: Bitcoin SPV, Cassandra, Redis filter.

5.bis.4 Trie / Radix tree sui prefissi verb_object

Pre-costruisci trie dei nomi tool: read_messages_google_workspace → path read → messages → google → workspace. Query token → traversal O(L) (L = lunghezza). Stessa idea di un router HTTP (Express.js, Gin).

  • Pro: O(L) lookup costante in N. Vocabolario chiuso §2.2 amplifica: 3-4 levels max. Memory efficient.
  • Con: solo trovare PER PREFISSO esatto. Necessita normalizzazione query (lemmatizzazione IT→canonical verb).
  • Effort: S (1-2 gg) + integration con intent_extractor.
  • Letteratura: trie classico Knuth Vol. 3; Aho-Corasick per multi-pattern matching.

5.bis.5 Learned ranker (decision tree / gradient boosting)

Addestra un classifier (XGBoost o random forest) su corpus turn log Metnos (4086 turn negli ultimi 30 giorni) per predire top-K tool data la query. Features: token features query + intent verb + intent object + marker provider + history. Inference ~ms, no LLM.

  • Pro: usa dati REALI Metnos (no estrapolazione letteratura). Cresce con corpus utente. Deterministico a inference time.
  • Con: serve labeled training set (turn log con first_tool come label sintetica). Re-train periodico. Black-box (no spiegazione del match). Overfit possibile a 4K esempi.
  • Effort: M (4-6 gg) + scikit-learn dep.
  • Letteratura: "Learning to Rank" (Liu 2009); industry: Amazon product search ranker, LinkedIn talent search.

5.bis.6 Hierarchical skill routing (dispatcher → skill scope)

Two-stage: stage 1 e' un mini-classifier (anche LLM tier fast Qwen3:8B) che assegna la query a UN dominio/skill (gmail, calendar, photos, files, web). Stage 2: il PLANNER lavora solo sul pool della skill scelta (~5-20 tool). Equivalente a "two-tier planning" gia' presente in Fase F della roadmap.

  • Pro: scalable a 100+ skill (ogni skill resta self-contained). Native a MCP architecture (Anthropic server-per-domain).
  • Con: errore al stage 1 propaga (query cross-skill misrouting). Latency extra ~200ms per dispatcher.
  • Effort: L (10-15 gg). Gia' descritto in Fase F.
  • Letteratura: HuggingGPT (2023); MCP servers Anthropic; CAMEL multi-agent dispatch.

5.bis.7 Constraint-based filtering (SMT-style)

L'intent extractor produce constraint strutturati: {verb in {send, write}, object in {messages}, provider != metnos}. Filtro tool come risoluzione di constraint (intersection di set). Deterministico, spiegabile, niente LLM in fase di filter.

  • Pro: 100% deterministico §7.9. Debugging facile (constraint trace). Audit log perfetto: "tool X escluso perche' violato constraint Y".
  • Con: dipende dalla qualita' di estrazione constraint dall'intent (intent_extractor LLM ha errore ~5%).
  • Effort: M (5-7 gg) + extension intent_extractor schema.
  • Letteratura: SAT/SMT solvers (Z3, CVC4); rule engines (Drools); pratica IT: AWS IAM policy evaluation.

5.bis.8 Selective semantic expansion (cost-aware hybrid)

Token-rank sempre primary. SOLO per query con top_score < threshold (es. 0.4) o entropy(top-3) > soglia (incertezza alta), attiva fallback semantic BGE-M3. Pattern gia' parzialmente in ADR 0134 per affinity; estendere allo stesso prefilter principale.

  • Pro: zero costo aggiuntivo sulle query "facili" (90%+); semantic attivo solo dove serve. Backward compat completo.
  • Con: serve calibration soglia. Misurabile via Fase A bench.
  • Effort: S (1-2 gg). Modifica prefilter.py::rank_with_intent.
  • Letteratura: "Cost-Aware Retrieval" (Carbonell+Goldstein 1998); industry: Google "deep retrieval" + sparse fallback.

5.bis.9 Cluster-based pruning (K-means su embedding affinity)

Offline: clusterizza i tool in K cluster (K=10-20) via K-means sull'embedding affinity BGE-M3. Online: per ogni query, embedding + cluster assignment (1 dot product per K centroidi), poi rank solo dentro il cluster scelto. Pool ridotto da N a N/K.

  • Pro: scalabile a N grandi. Cluster centroidi cacheable.
  • Con: cluster boundary issues (query borderline → cluster sbagliato). Approximate KNN sotto-ottimo.
  • Effort: M (3-4 gg). Reuse ADR 0134 BGE-M3.
  • Letteratura: FAISS IVF index; pgvector ivfflat; Annoy.

5.bis.10 Hybrid sparse-dense retrieval con BGE-M3 (state-of-the-art IR)

BGE-M3 e' un modello multi-functional: produce SIA dense embeddings SIA sparse vectors (lexical weights). Tipico setup IR moderno: combina i due con weighted fusion (lambda * dense + (1-lambda) * sparse). Equivalente a "ColBERT v2" senza late interaction overhead.

  • Pro: state-of-the-art IR retrieval; recupera meglio query con termini rari (sparse compensa). BGE-M3 lo supporta nativamente.
  • Con: serve embedding sparse calcolato al sign (oggi solo dense usato in ADR 0134). +5-10ms inference per sparse.
  • Effort: M (3-5 gg). Estende infrastruttura ADR 0134.
  • Letteratura: "BGE-M3 Multi-functional Embeddings" (BAAI 2024); "ColBERT v2" (Khattab+Zaharia 2022).

6. Sintesi esecutiva

6.1 Cinque raccomandazioni in ordine di priorita'

  1. Fase A — Bench prefilter scaling (1-2 gg). Misura quando token-flat degrada al crescere del pool, prima di committare al refactor. Switch a Tool RAG (Fase A.1) o ad altre soluzioni (vedi §5.bis) SOLO se evidenza empirica Metnos-specifica. Non estrapolare dalla letteratura ToolBench su corpus eterogenei.
  2. Fase E — Smoke tiers (10 gg, parallelo a A). Senza canary sub-20-min, deploy con 10+ skill diventa rischioso. Prerequisito per tutto il resto.
  3. Fase C — Sandbox per-skill (15 gg). Security debt che si accumula a ogni skill aggiunta. Procrastinare = breach probabilita' crescente (OWASP MCP04 documenta scenari reali).
  4. Fase D — Preference profile (5 gg). UX critica: senza, 2 skill messaging = chiede ogni volta. Effort minimo, payoff alto.
  5. Fase F — Two-tier planning (20 gg). Sblocca scaling 30→100+. Solo dopo che A, C, E sono stabili.

Fasi B, G, H sono accessorie di medio/lungo termine; non bloccano i primi 6 mesi.

6.2 Investment richiesto

  • Breve termine (Fasi A+B+C+D+E): ~45 gg-uomo, 2.5-3 mesi calendar con un developer FTE.
  • Medio termine (+F+G): ~30 gg, 1.5-2 mesi addizionali.
  • Lungo termine (+H): ~30 gg, 1.5-2 mesi addizionali.
  • Totale 18 mesi: ~105 gg-uomo (~5-6 mesi calendar FTE).

6.3 Primi risultati misurabili

  • Settimana 4: Tool RAG funzionante, smoke 22/22 PASS con 30 tool simulati.
  • Settimana 6: smoke tiers in produzione, deploy con canary <12 min.
  • Settimana 10: per-skill sandbox in produzione, penetration test passato.
  • Settimana 14: 5 skill third-party stabili in produzione (oltre google-workspace).

6.4 Porto sicuro quantitativo

Target "porto sicuro" misurabile alla fine di Fase F (medio termine):

  • Skill supportate: 30 stabili, fino a 50 con degrado <10% latency.
  • Latency P95 per query: <12s (oggi ~15s, target -20%).
  • Accuracy routing: >= 95% (baseline current).
  • Smoke battery time: critical tier <12 min, full nightly <90 min.
  • Security: zero shared filesystem cross-skill; sandbox profile dichiarato per il 100% delle skill; audit log firmato.
  • UX: zero disambiguation dialog per single-provider; <=1 dialog per query multi-provider con preference set.
  • Manutenzione: <=30 min/settimana di triage skill health failures.

7. Note per Roberto

Tre punti da discutere prima di iniziare:

1. Decisione architetturale fondante — bench prima di scegliere il prefilter. La letteratura 2023-2026 mostra degrado dei pool flat oltre ~100 tool su corpus eterogenei (ToolBench, RestGPT). Ma il prefilter Metnos NON e' un retriever flat letterario: ha vocabolario chiuso §2.2 + ADR 0136 marker provider + ADR 0134 semantic fallback gia' integrato. Il bench embedding-vs-token del 4/5/2026 (ADR 0075) ha confermato token-based 92.3% Recall@5 sul pool corrente (~70 tool). Roberto giustamente segnala che l'estrapolazione "letteratura RAG -> Metnos" e' rischiosa. Approccio corretto: Fase A misura prima (1-2 gg), poi attiva Tool RAG (Fase A.1) o uno fra le 8 alternative deterministiche scalabili (vedi §5.bis) SOLO se serve. Niente refactor cieco.

2. Sicurezza supply-chain: fino a che livello? OWASP MCP Top 10 e gli incidenti 2025 (postmark-mcp trojan, OX poisoning 9/11 registry, 1184 skill malevole ClawHub) sono dati duri. La nostra ADR 0123 ha gia' sha256 pinning, ma sandbox bubblewrap e' globale. Tre opzioni: (a) profile dichiarativo per-skill (Fase C, 15 gg, raccomandato); (b) status quo + monitoring (rischio reale); (c) tutto fino a code signing GPG mandatory (eccesso, sproporzionato). Decisione: livello (a) e' il giusto compromesso, ma serve commitment a 15 gg di refactor.

3. Two-tier planning: quando attivarlo. Fase F (15-20 gg) e' tecnicamente attraente ma rischia over-engineering. La regola d'oro: attivarlo SOLO quando il bench dimostra che il PLANNER middle Gemma 26B degrada misurabilmente. Probabile soglia: 30-50 skill installate. Fino a li', single-tier + Tool RAG (Fase A) basta. Mio suggerimento: includere F nella roadmap come gate condizionale dopo Fase A+E, decidere con bench A/B su 200 query reali. Se accuracy single-tier resta >95% a 30 skill con Tool RAG, posticipare F a long-term.
