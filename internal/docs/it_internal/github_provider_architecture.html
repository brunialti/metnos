0. Scope

In scope — Fase 1

  • Provider github come skill first-party Metnos (non import esterno), suffix _github allineato a _google_workspace
  • Issues + PR read/write ops (find/read/create/set/delete + send_messages per commenti)
  • Workflow issue watcher con dedup semantica (BGE-M3) + auto-reply su precedenti
  • Primitiva builtin consult_frontier con modo agentic tool use (frontier esplora repo autonomamente)
  • Uniformazione approval flow Telegram + HTTP chat UI via get_inputs(fmt="auto") esistente

Out of scope — Fase 1

  • Git push/branch ops (richiede git auth separato)
  • Repo settings / admin / billing
  • GitHub Apps multi-user OAuth (non rilevante per .33 single-host)
  • Cross-org search avanzata

1.3 Meta-verb riservato — consult approvato

Nuova categoria §2.2 system verbs:

System verbs sono verbi-meta riservati a builtin runtime. Fuori dai 23 verbi canonici §2.2. NON usabili da synt o user-domain executor.
  • admin — shell privilegiata (ADR 0088)
  • undo — reverse turn
  • synthesize — synt multistage
  • consult — consultazione frontier LLM con role/spec/context strutturati (nuovo)

2.1 Naming uniforme wrapper

Convenzione §2.2 componibile a 2 livelli:

Per google-workspace: tutto già coperto da generic wrapper (subprocess script Python). Niente skill_wrapper_google_workspace.py necessario.

Per github: probabilmente serve skill_wrapper_github.py per X-RateLimit handler, Link header pagination, conditional ETag.

2.2 tasks con provider _github NON è specializzazione ad-hoc

È istanza del pattern multi-backend già canonico in Metnos (ADR 0130 + 0136):

  • create_tasks (default) → backend local = scheduler v2 in-process
  • create_tasks_github → backend github = workflow_dispatch trigger
  • create_tasks_jenkins (futuro, se serve) → backend Jenkins

Identica logica già applicata in messages (smtp/gmail/telegram), files (local/drive), events (ics/gcal). Zero codice ad-hoc per github: rispetta primitive Metnos §7.3.

5. Primitiva consult_frontier agentic

Insight chiave (Roberto): se Metnos sapesse quale parte di codebase è rilevante per analizzare issue X, già conoscerebbe la risposta. Quindi remote_context non è qualcosa che Metnos pre-fetcha — è un set di tool che il frontier può chiamare iterativamente per esplorare autonomamente.

5.1 Due modi di operare

ModoQuandoTier minimoTool exposure
A — single-calltutto il context in mano (summarize email, draft testo)Gemma 26B locale OKnessuno
B — agentic tool usefrontier deve esplorare repo/URL≥ Sonnet (Anthropic/OpenAI con tool API)tool set passato da Metnos (read-only)

Selezione automatica via signature: remote_context=None → A, remote_context=[...] → B (+ auto-bump tier se necessario).

5.2 Flusso Modo B (esempio issue analysis)

Metnos invoca frontier con:
  prompt: «sei reviewer issue/PR Python self-hosted, leggi #42 e
           i file rilevanti per capire root cause»
  tools: [github_read_file, github_list_dir, github_read_issue,
          github_read_pr_diff, github_search_code, fs_read_local_file]
  tool endpoints implementati da Metnos

Frontier (autonomamente, loop tool use):
  step1: github_read_issue(metnos/myclaw#42)
         → Metnos esegue, return body + commenti
  step2: github_list_dir("runtime/scheduler_v2/")
         → Metnos esegue, return file list
  step3: github_read_file("runtime/scheduler_v2/store.py")
         → Metnos esegue, return contenuto
  step4: github_read_file("executors/find_events_empty/...")
  ...
  stepN: final message:
         «root cause: race condition perché lock manca a
          store.py:142. Fix proposto: aggiungere RLock attorno
          a write_slot. ~5 LOC.»

Metnos: return frontier final_message all'utente nello scratchpad
         del watcher

5.5 Tool set canonico github (read-only)

Constraint duro: i tool exposed al frontier sono SOLO read-only. Write ops (create_issues, send_messages, change_pulls) restano fuori scope frontier — passano sempre dal Telegram/chat consent dell'utente. Evita scenari "frontier crea issue auto" o "frontier mergia PR". 
GITHUB_FRONTIER_TOOLS = [
    {"name": "github_read_file",
     "input_schema": {"repo": "str", "path": "str", "ref": "str?"}},
    {"name": "github_list_dir",
     "input_schema": {"repo": "str", "path": "str", "ref": "str?"}},
    {"name": "github_read_issue",
     "input_schema": {"repo": "str", "number": "int"}},
    {"name": "github_read_pr_diff",
     "input_schema": {"repo": "str", "number": "int"}},
    {"name": "github_search_code",
     "input_schema": {"repo": "str", "query": "str"}},

5.6 Tier requirement

  • Modo A: qualsiasi tier (anche fast Haiku o locale)
  • Modo B: ≥ middle (Anthropic Sonnet con tool use loop). Gemma 26B locale NON supportata in modo B (tool use limitato 1 step/turno via llamacpp Metnos, non agentic-loop)

5.7 Cost stimato

  • Modo A: $0.05-0.20/call (Sonnet single-call)
  • Modo B: $0.20-0.80/call (Sonnet con 10-30 tool iter, repo grosso)
  • Repo myclaw ~5MB codice rilevante. Cap 500KB letti via tool tutela budget

6.2 Storage github_issue_qa.sqlite

CREATE TABLE issue_qa (
    id INTEGER PRIMARY KEY,
    repo TEXT NOT NULL,
    issue_number INTEGER NOT NULL,
    classification TEXT,          -- support|bug|question|enhancement|other
    question_text TEXT,           -- title + body normalizzati
    question_embedding BLOB,      -- BGE-M3 vec 1024d float32
    accepted_reply TEXT,          -- reply finale postata
    posted_at INTEGER,
    auto_replied BOOLEAN DEFAULT 0,
    related_refs TEXT,            -- json: [{ref, similarity}]
    user_satisfied INTEGER,       -- null|1|0 (1 se issue closed, 0 se lamento follow-up)
    cost_usd REAL,                -- $$ frontier per audit
    UNIQUE(repo, issue_number)
);
CREATE INDEX idx_qa_repo ON issue_qa(repo);
-- Cosine search via numpy in memoria (cap ~10k issue/repo, fattibile)
-- OR sqlite-vec extension se cresce

6.3 Safety: 4 condizioni AND per auto-reply dedup

TUTTE devono essere vere, anche una falsa → flow normale gate:

  1. top.similarity ≥ 0.85
  2. classification_hint ∈ {support, question} (mai bug/enhancement)
  3. top.user_satisfied == 1 (la reply precedente non ha generato lamenti)
  4. top.accepted_reply.length > 100 (no auto su risposte stub)

6.4 Threshold di similarity (calibrato su BGE-M3 multilingue)

Range cosineCosa significaComportamento
≥ 0.92Stesso topic, fraseggio simileAuto-reply con 1 riferimento principale
0.85 — 0.92Stesso topic, fraseggio diversoAuto-reply con 2-3 riferimenti
0.75 — 0.85Topic correlato ma non identicoNO auto-reply. Frontier riceve precedenti come hint context
< 0.75No match significativoFrontier senza hint

Default auto_reply_threshold = 0.85. Configurabile in ~/.config/metnos/github_dedup.json.

6.5 Classification hint pre-frontier

Per applicare safety AND condition #2 PRIMA di chiamare il frontier (deterministico §7.9):

9. Decisioni residue

Risolte approvate

  • OBJECTS nuovi: issues + pulls separati (Fase 1 implementati entrambi, pulls future-ready)
  • Sub-form: reviews e comments via send_messages_github, workflows via tasks_github
  • System verb consult: meta-verb riservato
  • Skill origin: first-party Metnos (no import esterno)
  • Naming wrapper: base generic + provider extension solo quando serve
  • remote_context semantica: tool exposure agentic (modo B), NON prefetch
  • Tool exposure read-only: write ops sempre human-gated
  • Auto-reply dedup: 4-AND safety + threshold 0.85 + classifier deterministico hint
  • Approval flow: get_inputs(fmt="auto") uniformato Telegram + chat UI
  • Storage: sqlite dedicata github_issue_qa.sqlite, embedding entry su ogni reply postata

Da decidere all'implementazione

D1 — Tier default consult_frontier
tier="wise" (Opus) per max qualità, o tier="middle" (Sonnet) per cost? Auto-bump a wise sempre se remote_context presente?
Sonnet tipicamente basta per issue analysis. Wise solo per casi complessi.
D2 — Token PAT scope
Fine-grained per-repo (raccomandato) o classic? Setup user-driven, può anche essere uno per inizio + altri dopo se serve cross-repo.

Note finali

  • Conoscenza repo: il frontier vede repo HEAD remoto via tool calls, NON l'ultimo stato non-pushato del .33. Acceptable per la maggior parte delle issue (sono già pushate)
  • Tono reply: il draft non sarà mai indistinguibile da Roberto. Tu modifichi sempre prima di Invia (Stage 2 gate)
  • Riusabilità consult_frontier: oltre github, primitiva generale per email triage, monthly report, code review delegate, doc draft
  • Sicurezza: tool exposed al frontier sempre read-only; whitelist + cap iterazioni + cap bytes; write ops sempre user-gated via approval card uniformata cross-canale
  • Apprendimento incrementale: ogni reply postata (auto-dedup o gate-approved) entra nello store come knowledge per futuri match. Dedup rate cresce nel tempo
