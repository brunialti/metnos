1. What Metnos is, in thirty seconds

Metnos lives on a Linux server in your house.
You talk to it from Telegram or a terminal.
It reads your mail, files and calendar, takes actions on your behalf,
and stops to ask before anything it cannot undo.

Two minutes of detail. Metnos is not a chatbot: it acts. You say «archive last month's invoices into ~/Documents/invoices/2026-03/ and add the totals to my spreadsheet», and it actually does it — runs a script in a sandbox, shows you what it touched, leaves an audit line. It is also not a hosted service: there is no Metnos cloud, no «sign up». You install it on a small Linux box, you keep the keys. The data and the logic stay home.

The four properties that distinguish it from a generic agent framework:

  • It asks before acting. Two-phase guard (a binary constitutional filter, then a graded judge against your stated ends) decides whether an action goes through silently, asks for confirmation, or is refused outright. The card you see on Telegram is three lines and two buttons. See vaglio and approval_ux.
  • It builds new tools when it needs them. The first time you ask it to pretty-print a JSON blob and it has no executor for that, a component called the synthesiser writes one in two or three minutes through a five-stage pipeline (naming, signature, tests, description, code), runs four tests on it, signs it, and puts it in the toolbox — with your approval. The next time, it just calls it. See synt.
  • It remembers what it tried, including what it failed. Every successful chain leaves a trace; every gap (a request it could not quite resolve) is recorded as an «aspiration». After a pattern recurs, the system proposes a new tool that would close that gap. Memory of the world and memory of itself, kept apart. See mnestome.
  • It is provider-agnostic. Local LLM (Qwen 3 8B, Gemma 4 26B), cloud LLM (Claude Sonnet, GPT-5), or a mix — the runtime exposes three tiers (fast / middle / wise) and each component picks one. Swapping a provider is a config line, not a code change.
testedWhere the project stands as of 27 April 2026. 14 canonical microdesign documents (all bilingual IT+EN), all backed by tested code. Phases 1–5 closed: signed executors with bubblewrap sandbox, ReAct runtime with native tool-use, real Vaglio (binary guard + rule-based judge), synt-on-the-fly (compose + generate), Telegram channel with Ed25519 pairing, extended Capability Registry, interactive approval card via Telegram callbacks, static observability dashboard, introvertive synt (merge + generalize). 2. Why Metnos and not OpenClaw?

A fair question: today you can stand up a local assistant with OpenClaw too — a terminal agent that runs on your own machine and reads your own files. The two look similar around the edges — a chat agent, a toolbox, a tight bond with the machine — but the engine is different. Honest summary.

Three things Metnos does that OpenClaw, today, does not

It writes its own missing tools, and keeps them clean
When a tool is missing, OpenClaw suggests a shell command or a small throwaway script that lives only in the current turn. Metnos instead materialises a new executor: TOML manifest, signed Python file, sandbox profile, a handful of tests generated alongside the code. The tool enters the catalog and on the next turn the planner can pick it like any other. The flip side — risk of cluttering up with defective tools — is guarded by five cumulative checks (closed vocabulary, affinity overlap, success rate monitored, routing smoke battery, semantic verifier description-vs-code) plus an auto-evaluator of proposals.
It notices when a tool is too specific or too generic, and proposes a change
The introvertive loop watches the mnestome and suggests specialisation (an expensive executor often called with near-fixed arguments splits into a specialised and a general one), generalisation (three executors doing the same thing with small differences merge into one), and dedup. OpenClaw lives in the turn and the context, not in the shape of its own catalog: the practical consequence is that Metnos becomes more suited to the user over time, not just more used to them.
It is multilingual by construction, not by translation
All runtime messages visible to the user, tool descriptions, LLM prompts and i18n live in three parallel layers with the same shape for each language. Adding a new language is one command that creates the structure and seeds placeholders; translation can be delegated to a frontier LLM, but it remains a choice. OpenClaw speaks the user's prompt language, but tool descriptions, runtime errors and confirmation requests are texts hard-coded in source. It matters only if your house speaks several languages, or has multilingual guests.

Importing tools already written by others (skills)

There is a small public standard, agentskills.io, where third-party developers describe how to use a service (Google calendar, mail, storage drive, …) in a structured text file called a skill. The format is simple: title, author, description, and a series of call examples.

Adopting it as-is would be unsafe for Metnos. The standard has no trust model: anyone can publish a skill, helper scripts can do anything, no digital signature, no sandbox, no closed vocabulary. Importing a third-party skill blindly would open the door to unpredictable behaviour inside the system. Not done.

We can however import a skill: there is a deterministic translator that reads it, produces one or more Metnos executor folders (with all the checks of the case: vocabulary, sandbox, signature, manifest), and installs them in a separate watched zone (_imports). The skill becomes a first-class tool of the system, indistinguishable from a handwritten one once the five admission checks pass. Required credentials (API key, OAuth token) are asked on first invocation through a dialog window, encrypted into a local vault, and never put in code. See skill importer for details.

Forward direction: the agentskills.io ecosystem already covers many everyday services. Metnos aims to import them all, one at a time, with the same care given to a handwritten executor. The user advantage: nothing to configure by hand, no tokens in text files, every new service arrives with a readable, traceable manifest.

On language models: three tiers (plus one optional)

OpenClaw leaves the choice of which LLMs to call (local, frontier, or a mix) entirely up to the user. I do not know whether it has a structured tier system.

Metnos has one, and it exists for a specific reason: to enable modular use of resources. Different tasks have different costs. Telling the time is not worth the same model used to write a four thousand word narrative synthesis. Putting everything on the most powerful LLM you have available means burning resources for nothing, and paying beyond what is needed when using paid services.

The three «at home» tiers:
  • fast — small model (e.g. Qwen3 8B) for rapid decisions: intent extraction, lookups, simple schemas. Answer in a few seconds, low consumption.
  • middle — medium model (Gemma 4 26B locally) for most work: planning, vetting, entry description, short summaries.
  • wise — high-quality local model (Gemma 4 26B in full mode, with extended reasoning budget) for tasks that warrant it: new code generation, long narrative synthesis, dependency chain reasoning.
Plus one optional: the frontier model (Claude, GPT, …) as declared fallback, when local is not enough. Never the primary choice; an option to activate when really needed.

Each Metnos component picks the tier that fits. The goal is not to save at all costs: it is to not waste when the task does not deserve it.

What OpenClaw does better

Maturity as a tool for code writers
OpenClaw was born to sit next to the developer, from the terminal, in real time. That trade it does excellently. Metnos does not replace that role: my daily use remains OpenClaw for code, and Metnos for home assistance.
Ecosystem of extensions and integrations
A third-party ecosystem, slash commands, MCP servers, documented and maintained hooks. Metnos is a personal research project: the ecosystem is one node, one person, one machine.

Rule of thumb

OpenClaw is a tool of the trade: a companion for those who develop. Metnos is an assistant that lives at home: mail, photos, calendar, notes, heating, reminders. The two do not exclude each other. If you already use OpenClaw and you are happy, you do not need Metnos unless one of these three traits attracts you: a tool catalog that extends itself and stays clean; multilingual by construction; the ability to import in a controlled way the skills written for other systems.

3. Eleven scenes from real life

The fastest way to grasp what it does is to watch a few examples. Scene 1 is a simple reactive read; scene 2 shows what an approval card actually looks like for an irreversible action; scene 3 is reactive but composed (Metnos chains four executors on its own to sort a photo archive); scene 4 closes the loop on scene 3, showing every critical action can be undone with one sentence; scene 5 is the full case from 4 May 2026: daily monitoring of an online school register with programmatic login, encrypted credentials, multi-user (the daughter receives the digest, not the host), recurring task; scene 6 shows it fetching a single web page and summarising it by composing two library verbs; scene 7 shows it building itself a new tool right in the middle of a turn; scene 8 shows size-bucket aggregations; scene 9 previews visual semantics on photos; scene 10 shows how the same bot serves multiple family members while keeping their memories separate.

Scene 1

«Summarise today's mail»

The user opens Telegram from the train and writes to the Metnos bot:

«Give me the summary of today's important mail.»

Metnos reads the inbox, drops the spam, groups by sender, replies in four lines: «3 mails today: counsel asks for the document by Friday; bank confirms yesterday's transfer; sister about Sunday lunch. Want me to draft a reply to any of them?»

capability: mail:read (read-only) autonomy: Supervised → allow_silent executors: mail_search → mail_summarise latency: ~3 s

No approval needed: a read-only capability with no side effects passes the policy without disturbing the user. The mnestome records the chain (mail_search→mail_summarise); next time the same request will run with one less probing step.

Scene 2

«Reply to counsel for me»

Still on the train:

«OK, reply to counsel, tell them I'll send the document by Thursday.»

Now the policy raises a flag. mail:send with an external recipient is approval_required at any autonomy level. Metnos drafts the message, calls render_approval_card, and pushes the following bubble on Telegram with two inline buttons:

May I send a mail?
to counsel@studio.example · subject: «document delivery» · ~140 chars
reversible: no · class: mail:send

The user taps Approve. The Telegram callback travels back to the ChannelDaemon, which extracts approve:<token>, verifies that the token is still pending (not expired, not double-spent) and that the decider is the same paired sender who raised the request, then flips the registry row from pending to approved and unblocks the planner. Two seconds later: «Sent at 11:34. Audit line #1247.»

capability: mail:send (irreversible) card form: full (first occurrence) token TTL: 600 s identity check: decider == requester
The card has three lines — question, object, meta — not because the designer found three pretty. They are the three things you need to recognise an action at a glance: what Metnos wants to do, on what, and how undoable it is. After the third or fourth time the same class of request comes through, the renderer collapses to a two-line, then a one-line form: when you already know what you are approving, brevity is care. See approval_ux ch. 4.
Scene 3

«Sort these photos by year and place»

The user has a few hundred photos sitting in ~/images, imported from various cameras over the years. From Telegram:

«Sort all image files in /home/roberto/images, creating subdirectories per year, and prepending date and place of capture to the filename. If place is unavailable, use 'unknown'.»

The request is composed: filter only images, read EXIF date and GPS coordinates of each file, resolve coordinates into a place name, finally move each file under a per-year subfolder with a name that begins with date and place. None of this is a single tool: Metnos builds it inside the planner by chaining four executors from the standard library. The diagram below shows how the composer — the LLM planner — picks and connects the steps.

What the composer did: none of the four executors knows about the others. The composer scans the library, picks tools that have the right semantics (LLM-readable manifest, explicit descriptions), and chains the output of one step into the next via the {{stepN.field}} reference syntax (raw data does not flow through the model: it lives in the scratchpad, the model only sees references). The sensible date is a field enriched by get_files_metadata: it falls back to mtime if EXIF is missing; same for place, which falls back to "unknown". No error if missing: the user spelled it out.

Once finished, Metnos replies on Telegram in three concise paragraphs (actual run on 28 April 2026, translated from Italian):

I've organized your images in /home/roberto/images.

I analyzed the EXIF metadata of all 98 files found and moved them into year-named subfolders. The new filename format is yymmdd_place_originalname.jpg (e.g., 140221_unknown_046.JPG).

Operation details:
• Files moved: 98
• Structure created: /home/roberto/images/{year}/{date}_{place}_{name}
• Place: set to unknown where GPS data was missing.
capability: fs:read, fs:write, net:read autonomy: Supervised → approval card on fs:write executors (4): find_files → filter_entries → get_files_metadata → move_files latency: ~13 s (governed by reverse-geocode rate limit) reversible: yes via undo_last_turn
This is the interesting case for understanding how Metnos thinks: the request is trivial for a human («sort these photos») but demands four conceptually distinct abilities (find, filter, read metadata, move). The composer does not have a special action for «sort photos»: it composes the library's atoms. The same approach applies to «archive March's invoices» or «find songs you haven't listened to in a year»: the filter changes, the destination template changes, but the machine is the same.
Scene 4

«Undo the last operation»

Right after seeing the photos sorted by year and place, the user changes their mind: not the structure they wanted. From Telegram, one sentence:

«Undo last operation.»

Metnos checks the undo log — an append-only on-disk file that, before and after every reversible critical action, records what was about to happen and what actually happened. It finds the previous turn: one operation, move_files, with 98 source→destination pairs and a handful of sub-folders created. It calls reverse(plan, results) exposed by the executor itself. The reverse is multistage: it first moves the 98 files back to their original paths, then removes the sub-folders the move had created — but only those that are still empty (safety: never a silent rmtree). The runtime does not know what reversing a move means; the executor's code does.

The reply on Telegram is short:

I undid the last operation: 98 files were restored to their original paths.
capability: fs:write autonomy: Supervised → approval card on critical ops executor: undo_last_turn → reverse(move_files) latency: ~3 s on 98 files idempotent: a second call does nothing
The undo of a composed action is by nature multistage: anything that has touched multiple parts of the filesystem must be reversed in inverse order. The pattern is a contract between runtime and executor: the runtime records, the executor knows how to undo its own job. Not every action is reversible (a sent mail, a pressed TV button cannot be recalled): in those cases undo reports «X cannot be undone» and reverses the rest.
Scene 5

«Daily school portal digest» — multi-user + login

The user wants to monitor news from his daughter's online school register. The site requires username + password login. The daughter (Lucia) is the recipient of the digest on Telegram, not Roberto. Four fresh pieces from 4 May 2026 come together: logical users (host + guest), simplified pairing via /start, encrypted credentials, the tier-policy web crawler.

Step 1 — create user Lucia. Roberto opens http://localhost:8770/admin/users in the browser and creates a new guest with name=lucia, autonomy restricted, owner Roberto. The «Pair Telegram» button issues a short-lived token (TTL 1 hour) like a1b2c3.... Roberto sends the token to Lucia by Telegram DM. Lucia writes to the Metnos bot: /start a1b2c3.... The daemon replies: «You are now paired as lucia (guest). Welcome to Metnos.». From then on to_user="lucia" resolves.

Step 2 — credentials setup (host chat). From Telegram Roberto types:

«Save credentials for web.spaggiari.eu: user roberto.brunialti, pwd MyPwd2026!.»

Metnos detects a token that looks like a password and opens a «credentials detected» approval card: it offers to encrypt the payload at ~/.config/metnos/credentials/web.spaggiari.eu.json.age, replaces the clear value with <REDACTED:cred> in the turn log, and offers a test login. Roberto taps «Yes». Smoke OK, cookie cached for ~14 days.

May I store encrypted credentials?
domain: web.spaggiari.eu · storage: Fernet encrypted with admin.key · turn log scrubbed
reversible: yes (rm of the .age file) · class: auth.password_storage

Step 3 — recurring task. Still on Telegram:

«Every morning at 7 search news on https://web.spaggiari.eu/cvv/app/default/menu_genitori.php in auth mode, keywords 'homework, marks, meetings, circular', read PDF attachments too, and send a Telegram digest of the 5 most relevant items with links to Lucia.»

Three-line vaglio card: «authenticated recurring search, every 7:00, recipient=Lucia — proceed?». Confirm. The task is registered via schedule_recurring.

Step 4 — daily 07:00 run. The canonical pipeline, rebuilt by the planner with no hardcoded logic:

truncated_intentional: true 4 read_urls_html(from_step=3, content_type="html", auth_cookies_file=...) + read_urls_pdf(from_step=3, content_type="pdf", auth_cookies_file=...) readability-lite (article > main > body), pypdf with 200KB body_text cap per PDF 5 group_entries(from_step=4, by="url") → describe_entries(style="news_summary") single LLM hop in the whole pipeline: produces a structured summary of the 5 most relevant items 6 send_messages(messages=[{"to_user":"lucia","via_channel":"telegram","body":...}]) resolve_recipients maps lucia → chat_id; cross-user vaglio: actor=host, allowed

Lucia receives a concise Telegram message, sample real run:

School — report 04/05/2026
1. Teachers' strike on 07/05 (circular 198) — morning classes suspended
2. Maths test moved from Thursday to 10/05
3. Weekend philosophy homework: chapters 4-6 + short essay
4. Coordinators meeting Friday 9 May, 15:30
5. Latin test mark posted (8/10)

Step 5 — cookie expiration. After ~14 days the first morning run fails with HTTP 401. Metnos retries with login_session(force=true), reuses the encrypted credentials and refreshes the cookie. If the login fails too (e.g. password changed on the portal), the task is paused and the host receives a Telegram: «Cookie expired on web.spaggiari.eu and re-login failed. Want to update the credentials?».

capability: auth.password_storage, network.read, crawl.recursive (standing) autonomy: Full (host) + Supervised (Lucia, recipient) executors (6): login_session → find_urls → filter_entries → read_urls_html+pdf → group_entries+describe_entries → send_messages latency: ~25–40 s/run (1 LLM call, no LLM-driven HTML parsing) turn-log scrub: <REDACTED:cred> + n_redacted_fields=2
The scene weaves together six pieces all new on 4 May 2026: (a) multi-user with guests paired via /start (ADR 0083); (b) Fernet-encrypted credentials with admin.key as master (ADR 0082); (c) regex scrub in the turn log (ADR 0082); (d) tier-policy web crawler with cookie session (ADR 0081); (e) HTML+PDF pipeline with deterministic readability-lite (no LLM for HTML parsing); (f) nightly recurring task with a recipient distinct from the host. This scene replaces the «mum's birthday» version of 1/5/2026: the school case is richer and showcases capabilities just gone into production.
Scene 6

«Fetch this page and tell me what it contains»

The user is weighing whether a long documentation page is worth reading. From Telegram, paste the URL and ask for a summary:

«Fetch the page https://metnos.com/en/Metnos_QuickTour_v1.html and summarise what it contains.»

Nothing magical in the toolbox: two steps of the standard pipeline, one to grab the content from the network, one to produce a structured summary on top of it. The composer puts them in line and that is all.

net:read: HTTP read, no side-effects, no confirmation 2 describe_entries(from_step=1, style="by_importance", data_kind="web_result") → structured bullet summary from_step=1 refers to the previous step's entries by handle, no payload copy-paste style by_importance nudges the LLM to order points by salience, not by position in text final answer: step 2's summary lands in the Telegram message, sanitised

What the composer did: it found two sufficient verbs in the toolbox, get_urls to download the identified page and describe_entries to summarise. The first is a vector executor: it accepts a list of URLs of any length, including one (degenerate case). The second works on the previous step's entries by reference (from_step=1), with no need for the planner to invent the payload. For direct on-site discovery (finding fresh URLs starting from a root), the pool also has find_urls: sitemap/RSS/BFS discovery, deterministic tier-policy, BM25 ranking. See scene 5 for the full authenticated pipeline.

Scene 7

«Pretty-print this JSON I am pasting» — synt-on-the-fly

The user, exploring an API response on the terminal, pastes a 4 KB JSON string into the Metnos chat:

«Format this with readable indentation, please.»

The planner inspects the toolbox. There is no format_json executor. Composing the existing seeds (fs_read, fs_write, shell_exec) into a chain that solves the gap leads nowhere. The synt cascade falls through to generate. The terminal prints a status line:

… building a new component to extend my capabilities. First time takes two or three minutes, every reuse is instant.

Behind the scenes, a five-stage pipeline: small focused prompts instead of one mammoth prompt. Each stage sees only the slice of the skeleton it needs, from the most procedural (closed-vocabulary lookup) to the most creative (code). A closed vocabulary of 20 actions and 11 objects ensures conformant names without bespoke prompt engineering.

  1. Naming + classification (~10-15 s): name selected as {action}_{object}[_qualifier] from the closed vocabulary, plus revertible/critical/target_kind classifications. Middle tier (Gemma 4 26B think=true).
  2. Signature (~20-25 s): args_schema, capabilities, reverse_pattern from the catalogue. Middle tier.
  3. Birth tests (~25-30 s): 4-6 tests in fixed format with setup/input/expect/teardown. Middle tier.
  4. Description + affinity (~20-25 s): LLM-readable prose plus keyword affinity. Middle tier.
  5. Code (~40-45 s): Python file with def invoke(), safety net, runtime conventions. Wise tier (Gemma 4 26B think=true). Zero cost, local.

Right after, sandbox profile is derived from the imports, birth tests run, human approval lands, Ed25519 signature is applied. The executor arrives in workspace/executors/format_json/; the planner calls it on the original JSON and returns the formatted output.

cascade stage: compose → generate (multistage 5) wise tier: Gemma 4 26B (local) cost: €0 (local) tests written: 4-6 green second call: <100 ms

The next time anyone in the household asks for JSON formatting, no LLM is harmed. The executor is in the toolbox, the call is a regular function invocation. This is how Metnos's seed pool of 27 executors becomes 28, 29, 30 — one capability at a time, motivated by a real request, never in advance. See synt for the full five-strategy cascade.

Scene 8

«How many .py do I have, group them by size»

A concrete admin request: count and classify the Python sources of a module, split into three size bands chosen by the user. From Telegram:

«Find in my files in /opt/myclaw/runtime how many .py there are, group them by size (small <5KB, medium 5–30KB, large >30KB) and tell me which group is most populated.»

The request is not «read a file»: it is a quantitative aggregate. The composer discovers there is no executor for «group by size band» and builds it by composing five steps from the standard library.

What the composer did: there is no «group by size band» in the library. The composer discovers find_files (which now includes size in the entries) and filter_entries (which can filter by size_min/size_max) and combines them into three orthogonal filters. The final answer is pure synthesis on top of the three subset counters: no fabrication of numbers, no content read.

The shape of the problem is common: aggregate these objects across a dimension that falls into numeric bands. It applies to files by size, emails by day, photos by year, transactions by amount. Scene 9

«These photos… I've seen them before»

Weeks after a one-shot photo-tidying script, the user begins to ask questions of the sorted folder — no longer «put them in subfolders», but things like:

«Give me the photos from the Corfu holidays.»
«Find the photos with mum.»
«Which ones are from the wedding?»

Metnos does what it can: searches EXIF metadata (geotags, dates), writes little scripts on the fly, occasionally lands. But requests about visual content — who is in the photo, where it was taken without a geotag, what kind of event it was — escape its metadata-only toolbox. It does not fail loudly: it admits the limit, tries an alternative route, and often answers «I don't know». Each one of those moments leaves a proto-mnest in the mnestome: a record of an attempt that did not close, with enough context to recognise the same shape next time.

Five weeks pass. One Saturday evening, spontaneously, the user receives:

A proposal, if you like.
In the last five weeks I have met twelve photo-related requests I cannot resolve from metadata: recognising a place from visual cues, people present, type of event. I did what I could, but I also kept track of the gap.

The pattern is clear enough now. May I propose two new tools?
  • one to recognise recurring faces (after you tell me, once, who is who in the first thirty photos);
  • one to classify a place from visual cues (sea, mountain, indoor, street).

I'll bring the drafts on Thursday and you decide. If they aren't useful, I drop them.

What happened here. Every time the system met an unresolvable request, it recorded the void as a half-finished attempt — not as a failure to forget, but as an aspiration to remember. Twelve attempts of the same shape in coherent contexts triggered the introvertive synt: an asynchronous sweep that proposes generalisation across recurring proto-mnests. The proposal does not come from the designer; it does not come from the user explicitly asking. It comes from the history of use. Two Metnos installations in two different households, after six months, will have different toolboxes — each one shaped by what it was actually pulled toward.

And it never grows alone: the drafts come to your judgement before becoming tools. The third principle of the six — one-channel generation — says exactly this.

Scene 10

A quiet corner: a guest writes from the same Telegram bot

Pairing in Metnos identifies a (channel, sender) pair, not a person. So the same bot can serve the host (paired Full) and a guest (paired ReadOnly with a one-shot signed code) at the same time, without mixing them up. A family member with whom the user has shared a 10-minute ReadOnly code writes:

«Search the family calendar for Sunday's lunch time, please.»

The ChannelDaemon looks up the pairing, finds autonomy_level = ReadOnly, runs the turn, and replies as usual. The same guest then tries:

«Move yesterday's photos into the shared folder.»

The reply is polite and short: «ReadOnly: I can't perform write actions for this channel. Ask the host.» The pairing registry, the policy table, and the autonomy level conspire to keep the guest's reach consistent with what the host granted. Each pairing has its own door, its own key, its own audit line. See pairing.

Scene 11

Adding French to Metnos in one command

Metnos has spoken Italian and English from day one. At some point a French-speaking family member moves in and the bot needs to answer in French on their channel. The host opens a terminal on the server and types one line:

$ metnos-prompts add-language fr

This idempotent bootstrap does three things at once: it creates an empty runtime/prompts/fr/ (the 26 core LLM prompts will be generated as candidates in _pending/ by the nightly daemon), populates ~/.local/share/metnos/i18n.sqlite with a placeholder for each of the 118 user-facing keys (errors, confirmations, notifications), and lays the ground for the next daemon cycle to scan executor TOML manifests and propose translations of their descriptions.

The next day the host runs:

$ metnos-prompts review planner --lang=fr

to inspect the structural diff of the candidate (MiniJinja placeholders matching, length within the expected range). If the translation holds, metnos-prompts mark-synced planner --lang=fr promotes it from _pending/ to the runtime directory. For the more delicate nuances (Vaglio judge, planner) there is the opt-in frontier tier:

$ metnos-prompts translate vaglio_judge --to=fr --quality=frontier

which uses a higher-quality external LLM (~$0.015 per call, explicitly declared). When the whole translation is in line, the host sets METNOS_LANG=fr in the systemd unit of the channel dedicated to the guest, restarts, and Metnos speaks French without a single line of code touched. The underlying discipline is latest-wins: no language is canonical, the latest editor wins. See multilang.

4. Where it lives and how you talk to it

Metnos runs on a Linux server in your house — in this project's case, an Ubuntu 24.04 box with a Strix Halo SoC and 128 GB of unified RAM, quiet, sitting in the next room. The size of the box is a function of the LLM you want to host locally: a 7–8 B fast model fits on any modern mini-PC, a 26 B wise model wants more. Either way, the box is yours, in your home, on your network. There is no Metnos cloud.

Your laptops, phones and tablets are not where Metnos lives: they are clients. They reach the server through the home LAN when you are at home, and through a self-hosted WireGuard overlay (Headscale) when you are away. The mind, the memory, the audit log, all live on one machine. This is the self-hosted property the architecture foregrounds: the data and the logic do not pass through third-party clouds. An external service may be borrowed for individual tasks (an LLM call now and then, the Telegram channel itself), but it is never the place of residence.

Two surfaces, one mind.

The phone face: Telegram

Pairing: how the bot knows it's you

Telegram is a multi-user surface: anyone who knows the bot's handle can write to it. Metnos solves this with pairing: a one-shot signed code (Ed25519, 5-minute TTL by default) that the host generates on the server and shares out-of-band with whoever they want to admit. The first time a guest writes to the bot, they send /pair PAIR.<code>; the daemon consumes the code, ties their (channel, sender_id) to an autonomy level (ReadOnly, Supervised, or Full), and from that point on every message from that sender travels at that level. There is no central account, no login, no identity in any registry sense — just a per-channel, per-sender ledger that only the host can write to. See pairing.

The home face: terminal

Anyone who likes a terminal can talk to Metnos there, and watch what it is doing in real time. For those who prefer the phone, this is never necessary.

A sample dialogue from the terminal

Scenario: a model download was started yesterday evening; was it ever finished?

user
is the model download finished?
Metnos
Checking ~/downloads/ and the wget log. One sec.
(internal)

Metnos
Yes. 8.2 GB of 8.2 GB, checksum verified. The file is gemma-4-26b-q4_k_m.gguf, finished at 03:14 last night. Move it to /opt/models/?
user

(internal)
capability fs:write:/opt/models/** outside workspace → approval_required. Vaglio: guard silent, judge score 0.78 > 0.30 → approval card raised, «yes» resolves token a0f3b21c.

The italic grey lines show what Metnos is doing «behind the scenes»: useful when you want to understand what the policy and the Vaglio decided, ignorable otherwise. Notice how Metnos explains what it is about to do before doing it; how it does not ask confirmation for read-only operations; how it does ask for a move outside the workspace; how every action lands in an append-only audit log with a timestamp and a sequence number, so a question like «what did Metnos do last Tuesday between 9 and 10?» always has a precise answer.

5. What happens when it says «may I?»

This is the single most important piece of UX design in the project. Every time Metnos is about to do something that changes the state of the world — send a mail, write a file outside an already-granted folder, run a shell command, post to a channel — it stops and asks. That moment is not a usability tax: it is the system's primary safety mechanism, and the place where the human stays a human, not a rubber stamp.

The path from your message to a confirmation card and back goes through four real components, in this order.

1
Plan a step. The ReAct planner picks an executor and arguments for the next step (e.g. mail_send with a draft). The action is prepared in memory but not yet performed.
2
Vaglio: guard then judge. The vaglio runs two checks. First a binary guard: forbidden paths (~/.ssh, /etc/passwd, …) and quasi-irrecoverable shell patterns (rm -rf /, mkfs, fork bombs) are denied outright, no matter the autonomy level. Then a graded judge: a rule-based score in [0, 1] measuring alignment with the user's telos. Below threshold → silent denial; above → the policy is consulted.
3
Policy: capability, autonomy, grants. The policy looks up the action's capability class (one of 13 canonical classes: fs:read, fs:write, shell, net:fetch, mail:send, …) against an autonomy×capability table and any persistent per-target grant. The combined outcome is one of allow_silent, approval_required, or deny. For approval_required, the planner pauses and an approval card is pushed on the channel that initiated the turn.
4
Approval card & callback. The approval_ux module renders a 3-line card (question + object + meta) with two inline buttons, issues an opaque token, and writes a row in a SQLite registry with a 600 s default TTL. When you tap, Telegram returns approve:<token> or reject:<token>; the daemon verifies the token is still pending, has not expired, and that the decider is the same paired sender as the requester (no cross-user approvals). Only after a clean approved resolution does the planner step proceed; the executor runs inside a bubblewrap sandbox with the profile the manifest declared.
Many cards, less friction over time. The card has three forms by recurrence count: full (3 lines, first two times), medium (2 lines), short (one compact line, after eight identical occurrences). The first time you approve a class of action, you also see a territory marker if the request asks for a session-wide or permanent grant: [territory: session] or [territory: permanent]. Approving the marker writes a per-target grant in the policy and silences future requests of that exact shape, until you revoke it from the CLI. Card design and rationale: see approval_ux.

6. Its memory: what it remembers and what it doesn't

Metnos's memory is not a single black box. It is four distinct stores with different roles, lifetimes and write rules — three for conversations and facts about the world, one for facts about itself (what it tried, what worked, where the gaps are). Each one is a real SQLite table or markdown file; nothing is implicit, nothing is hidden in a vector store you cannot inspect.

Concretely:

  • Short is the planner's scratchpad for the current turn (scratchpad): observations of intermediate steps, large blobs not worth pasting back into the LLM context. Cleared at the end of the turn.
  • Medium is the JSONL turn log: one line per turn, with the user query, the chosen executors and the answer. It supports questions like «what did I ask Tuesday afternoon?» and feeds the observability dashboard.
  • Long is workspace/MEMORY.md: explicit facts about the world («the router password is in Bitwarden», «mum's birthday is 23/4») injected into the system prompt on every LLM call. Editable by hand, never silently rewritten by Metnos.

The detail that matters. Metnos never promotes a fact to MEMORY.md on its own. Once a day, in the evening, it can propose: «I noticed you kept mentioning the new dentist today; save them as a regular contact?». You say yes or no. Long memory is built this way, never surreptitiously.

And then there is the fourth memory: the mnestome. Beyond facts about the world, Metnos keeps track of how it works: which executors have collaborated, with what success, in what context (a mnest); and, more interestingly, which attempts stayed half-finished because no executor was suitable (a proto-mnest). The set of all mnests is the mnestome: a SQLite graph of co-activations that grows with use, ages with disuse, and is the substrate the synthesiser reads when it decides whether to propose a new tool. It is not memory of you; it is memory of itself. The Dialogue on executors and distributed memory tells the full story.

7. How it grows: new tools, on the fly

Metnos is not born omniscient. It is born with a small seed pool of hand-written tools and a component — the synthesiser, or synt — that can grow that pool when the system realises a tool is missing. Always under human approval, never in secret.

Tools have a proper name: executors. An executor is a small Python file that does one thing (read a file, fetch a URL, format a JSON, extract email addresses from text), with a TOML manifest declaring its inputs, its outputs, and the sandbox profile it needs. Once signed with an Ed25519 key, an executor is a stable artefact: it does not learn, does not change inside, has no internal state. Intelligence does not live there.

The growth lives in the synt. The synt does not write from scratch every time — that would be both heavy and noisy. It runs a cascade of five strategies, ordered from the lightest move to the most committing one:

#StrategyWhenWhat it does
1ComposereactiveFind a chain of existing executors that closes the gap. Pure orchestration, no new code.
2GeneratereactiveFive-stage multistage LLM pipeline (naming, signature, tests, description, code) followed by profile, test execution, approval, signing and install.
3MergeintrospectiveAt night: two executors with overlapping traces and compatible profiles fuse into one.
4GeneraliseintrospectiveThree or more specialised executors with the same shape collapse into one parametric.
5SpecialiseintrospectiveA general executor begets a focused version for a hot, recurring case (deferred to v1.2).

Reactive strategies (1, 2) run inside a user turn, when the planner hits a gap. Introspective strategies (3, 4, 5) run at night when the load is low: the ager sweeps the mnestome and the pool, looking for patterns the system did not see in the moment. The principle is the same in both cases: compose first, generate later, merge / generalise when the picture is clear enough. Reaching for the lightest move that still works is a real economy of effort, not aesthetic minimalism.

Why this is interesting. Metnos's growth is not driven by the designer; it is not driven by the user explicitly asking for new tools. It is driven by the actual use the system has had so far, mediated by the human gate. Two installations in two different homes, after six months, will have different toolboxes — each shaped by what was actually pulled out of it. The synt proposes; you dispose.
What is live as of 27 April 2026. Reactive cascade (compose + generate) and introvertive cascade (merge + generalise, rule-based) are running in code. The first end-to-end synthesised executor is format_json: born in ~65 s wall-clock from the proto-mnest, checked by four declarative tests the system itself wrote and ran in the sandbox, Ed25519-signed after a human approval card. Seed pool today: 27 hand-written executors covering filesystem, shell, network, LLM, mail, channel, parse, time and packaging primitives. The runtime exposes a three-tier LLM router (fast: qwen3:8b local; middle: gemma-4-26b local; wise: gemma-4-26b local or Claude Sonnet 4.6 / GPT-5 online); a hard quality floor on the wise tier prevents silent downgrades to fast for code generation. A provider-specific prompt repertoire smooths over the idiosyncrasies each model family shows in the first generations.

For the full mechanism — the five stages of multistage generate, the R score that weights candidates, how a proposal becomes a signed executor, how aged-out tools are archived — see synt, executor, and the Dialogue on executors and distributed memory.

8. Hosts, guests, and the road to remote executors

Metnos lives on one server. The interesting question is: who can talk to it, with what authority, and where can the actions land. The answer has two layers — who is on the other end of the channel, and where the executor's code is running. The first is solid; the second is the project's most exciting open direction.

Host and guest: a light multi-user model

Metnos is not multi-tenant in the SaaS sense; it is single-instance, single-household. Within that household, there is a host — the owner of the server, holder of the signing key — and zero or more guests: family members, occasional users, admins on a temporary boost. Pairing identifies a (channel, sender) pair, not a person, and binds it to one of three autonomy levels:

LevelTypical pairingWhat the daemon does
ReadOnlyA guest, a sensitive channelThe turn runs but only read-only executors can fire; any write or shell action is politely refused without ever reaching the planner's action phase.
SupervisedDaily use by a known senderThe full turn runs; sensitive actions raise approval cards on the same channel.
FullThe host on the host's own phoneAs Supervised, plus the broadest set of capabilities that the policy table allows. Forbidden paths remain forbidden, even at Full.

The mechanics are already in place: the daemon keeps each pairing's audit lines separate, and the capability registry is rich enough to express per-target grants. What lies ahead is the everyday gesture — how a host says, without ceremony, «a guest can read the kitchen calendar but not send mail from the family address». The plumbing is there; the rituals will follow, when real households start using them.

Remote executors: where the code is

One server, one mind, one mnestome — but not one filesystem. Many of the things you would want Metnos to act on (laptop files, photos, applications) live on machines other than the server. The architecture's answer is to keep the gateway, the policy and the memory on the server, and let the executors sometimes run elsewhere: on the user's laptop, on a Windows PC, behind a Headscale overlay. This is the remote executor direction outlined in Architecture ch. 4.

The first pieces are already in place. A thin Rust client carries its own Ed25519 identity and joins the server through a one-shot signed admission; the daemon answers on a small HTTP service that the single-instance lockfile keeps honest; the register ritual is proven end-to-end. Light enough to install on a laptop without ceremony, and small enough that a new device is born from a single tarball. mTLS over the household overlay and a reversibility manifest for state-changing calls are the next short steps.

Today, most of daily life already flows through Telegram, terminal, or a shared folder. The remote-executor horizon makes room for what folders cannot reach: tidying a photo archive in place, driving an application on a laptop, taking a screenshot of something that exists only there. A horizon worth walking toward — slowly, with the care the warn below suggests.

The security abyss is acknowledged. Remote executors opens a real surface: a confined process on a Windows laptop is weaker than a bubblewrap-jailed one on Linux; an intermittent network needs idempotent invocations and replay protection; a stolen device must be revoked from the server in a single move. The architecture chapter enumerates five non-trivial security questions; none of them is solved «in the small». The rule is: introduce remote executors one at a time, motivated by a use case the shared folder cannot cover, with all the guarantees up front. See Architecture ch. 4 and executor ch. 12.

9. What it can do, what it will never do

✓ What it does today, or in active build

  • Multi-step turns from terminal and Telegram (ReAct planner with native tool-use, ~800 ms/step on local Qwen 3 8B)
  • Read and summarise mail, draft replies; outbound mail behind an approval card
  • Search files in the workspace, fetch web pages, extract data from text
  • Run shell_exec inside a bubblewrap sandbox with a per-executor profile
  • Manage the calendar (read primitives in seed pool; write deferred to a backend choice)
  • Remember named facts about the world (MEMORY.md) injected on every turn
  • Schedule recurring tasks (scheduler builtin, cron-like or natural language)
  • Recognise hosts and guests on the same channel with separate autonomy levels (Ed25519 pairing)
  • Raise interactive approval cards on Telegram (3-line card, two buttons, recurrence-modulated, identity-checked)
  • Synthesise new executors on the fly when the toolbox is missing one (compose + generate)
  • Maintain the toolbox at night (merge + generalise; specialise in v1.2)
  • Run a static observability dashboard aggregating six data sources (mnestome, pairings, turns, vaglio, scheduler, tests)
  • Append a per-action audit line that survives forever and feeds the dashboard

× What it does not, by design or for now

  • Act on the internet without your explicit consent — outbound capabilities are gated
  • Run beyond the configured daily ceiling on external LLM use (hard-coded)
  • Send messages to senders not explicitly paired with at least Supervised level
  • Delete files without showing them first
  • Touch /etc, ~/.ssh, ~/.gnupg, /root, ~/.aws/credentials — the binary guard's hard list, not configurable from YAML
  • Run rm -rf /, mkfs, fork bombs — refused outright by the guard regardless of autonomy
  • Modify its own Laws or its constitutional guard (a code change + new release is required)
  • Self-modify the synt or the runtime (one-channel generation: only executors are synthesisable, never the meta-system)
  • Install a new executor without an explicit approval card (no autonomy level bypasses this)
  • Listen through a microphone yet (voice channel is roadmap phase 6, currently in standby)
  • Drive a browser, control smart-home devices directly, or leave the house in any sense (delegation to sibling agents is the design)
  • Run an executor on a remote device (the Rust client is W1–2 MVP; not yet distributable)
The 4 Laws. Metnos operates under 4 rules that it cannot rewrite on its own: (0) stay within the declared perimeter, (1) do no harm, (2) obey only informed instructions, (3) always leave a trace. They live in workspace/SOUL.md and they are enforced two ways: the binary guard of the vaglio turns Law 1 into a list of forbidden paths and quasi-irrecoverable shell patterns; the LLM judge (opt-in, v1.1) and the future probabilistic judge (v1.2) ground the other three Laws in the prompt of the proposer's independent reviewer. If SOUL.md is altered without going through the modification rite, Metnos refuses to start.

Where the «essential commands» come from

If you eventually run a copy of Metnos, the operational surface you will touch is small.

CommandWhat it does
python3 -m runtime turn "<query>"One-shot turn from the terminal, default Supervised autonomy.
python3 -m channels.daemonStart the Telegram daemon (long-poll + callback dispatcher). Run as a systemd user unit in production.
python3 -m pairing generate <Level> [ttl]Mint a one-shot signed pairing code (default 5 m TTL). Out-of-band delivery to the guest.
python3 -m pairing list [--include-revoked]Inspect the pairing registry.

The single configuration file the host edits by hand is ~/.config/metnos/credentials.env (Telegram token, LLM keys, overrides). Behaviour is shaped instead by the six markdown files of the workspace — IDENTITY.md, USER.md, MEMORY.md, AGENTS.md, SOUL.md, TELOS.md — injected into the system prompt on every LLM call, editable at any time without restart.

The forty-eight cents description

If you take one thing away from this document, take this. Metnos is not a chatbot, not a SaaS, not a generic agent framework. It is a personal AI assistant with three peculiar commitments: ask before acting (a two-phase guard you can audit, not a vibe); build new tools when needed (a synthesiser that adds capacity without retraining the brain); keep the keys at home (one Linux server, one mnestome, one audit log, no cloud of residence). It is documented before it is shipped, on purpose. If that combination interests you, you are the audience.

11. Mini glossary & further reading

The complete glossary of the project — technical terms, components, inspiration projects, foundational concepts — lives in a dedicated document:

→ Open the Glossary about 35 entries, alphabetical, with links to canonical sources.

A handful of entries that recur in this document:

Executor
A tool in Metnos's toolbox: a small Python file with a TOML manifest, an Ed25519 signature, a sandbox profile and a frozen profile lock. Three categories: seed (hand-written), synthesised (born from the synt), builtin (part of the runtime, e.g. the scheduler). All share the same external contract.
Synt (synthesiser)
The cascade of strategies that grows and curates the executor pool: compose, generate (reactive); merge, generalise, specialise (introvertive). Always behind a human approval card.
Mnest
The trace of a successful (or attempted) co-activation between two executors, persisted as a row in the mnestome. A failed attempt with no suitable executor is a proto-mnest: an aspiration to remember.
Mnestome
The emergent SQLite graph of all mnests. Memory of how the system itself works, distinct from MEMORY.md (memory of the world). Read by the synt to decide when and what to propose.
Vaglio
The two-phase evaluator that stands between a proposed action and its execution: a binary guard (forbidden paths, irrecoverable shell patterns — non-negotiable) and a graded judge (alignment with telos, configurable threshold).
Telos
The user's ultimate ends, written in TELOS.md as three to seven soft tendencies. The judge measures action proposals against them. Distinct from the 4 Laws (which are non-negotiable, perimeter-only).
Pairing
The Ed25519-signed admission of a (channel, sender) pair to one of three autonomy levels. Replaces the notion of «login»: each channel has its own door, its own key, its own audit line.
Approval card
The 3-line, 2-button bubble that appears on Telegram when an action needs explicit consent. Modulated by recurrence (full / medium / short) and by territory concession (none / session / permanent).
Channel
A way to talk to Metnos. Terminal and Telegram are live; voice (through Piper TTS plus a wake-word satellite) is roadmap phase 6.
Workspace
The agent's home directory: ${METNOS_HOME}/workspace/. The six markdown files (IDENTITY.md, USER.md, MEMORY.md, AGENTS.md, SOUL.md, TELOS.md), the audit log, and the synthesised executors.
Sandbox
The bubblewrap-derived jail in which an executor runs: filesystem namespacing, network isolation when not declared, CPU/RAM quotas, timeout. The sandbox profile is part of the signed manifest.
LLM router
The runtime layer through which Metnos accesses language models, exposing three tiers (fast, middle, wise). Each component picks a tier; alias automatically downgrades only when quality is not at stake. The wise tier has a quality floor (Gemma 4 26B or above): for code generation, a smaller model triggers an explicit boot error.
