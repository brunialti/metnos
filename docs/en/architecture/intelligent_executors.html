Executors that use a model

An intelligent executor uses a model to resolve one or more uncertain steps while keeping the ordinary executor contract. The planner gives it a precise task and receives the expected result without having to know its internal route.

Core idea. The model may propose how to proceed within a bounded set of possibilities. This does not grant it new permissions or let it decide by itself what counts as success.
Stable contractArguments, authority, and result shape do not change when the model is involved.
Bounded choiceThe model proposes only values or actions that the adapter knows how to validate.
Verified outcomeThe executor's postcondition, not a model's claim, determines whether an attempt succeeded.

The architectural boundary

The executor's manifest and code define its purpose, arguments, capabilities, consent, limits, and result shape. When part of the route needs a model, the adapter prepares a bounded observation, validates the proposal, and decides which concrete operation to run. The model does not invoke executors directly or alter its own contract.

In a manifest, intelligence = "agentic" declares this mode so that the registry and interface can represent it correctly. The declaration is validated, but it does not prove that an implementation is safe: proposal limits, validators, and postconditions must still be checked in code and tests.

What the shared runtime provides today

Metnos provides both synchronous and asynchronous loops. On each attempt, the loop may refresh the observation, request a proposal, validate it, execute it, and check its postcondition. The internal outcome is completed, inconclusive, or exhausted. A deterministic-first variant is also available: when the model fallback fails to produce a valid improvement, the initial deterministic result is retained.

Where it is used

Controlled selection

During web navigation, the model may choose a control identifier from candidates prepared by the broker. It cannot produce CSS or XPath selectors.

During image search, it may reorder known identifiers when metadata provides no useful lexical signal.

Controlled fallback

OCR tries Tesseract first. Only when the text is insufficient may it ask the vision model for a transcription; a weak result does not replace the original.

Structured extraction and some consultation paths apply the same principle under their own contracts.

A model is useful when the purpose is narrow, the route may vary, and the end state is verifiable. It is not a good way to hide open-ended research, cross-domain strategy, or a task without a crisp completion criterion inside an executor. Those decisions belong to the planner.

Placeholders are allowed only in generative examples. Website observations and results retain the data actually observed or state its absence; a placeholder does not establish that an item was found.

Signing in to a website

Metnos first looks for a sign-in form. If it cannot find one, it follows relevant account links and menus. It uses signals from the page; when these are insufficient, the local model chooses among controls actually observed. It does not invent links or use routes written for individual websites.

A preference between signals counts only when it singles out a control. Some pages use the sign-in word as a generic verb, such as “Access” followed by many different sections: that word does not identify the entry and does not hide the one control the whole evidence designates unambiguously, such as “Customer area”.

The search explores up to four steps per route, with a shared limit of 32 actions. At a dead end, it returns to a verified branch and tries an alternative. If the page has changed during that return, it discards the branch and returns to the original entry for a fresh observation, keeping attempted controls and limits. This restart is available only before credential use and does not repeat the discarded branch. An ambiguous control still stops the search. A temporary panel covering the page, even one drawn inside an iframe, is closed only through a safe exit that neither navigates nor submits data. Pausing for consent does not reset attempts.

After a click, it also waits for a delayed form or new tab within the search time budget. An entry already tried is not treated as a new alternative. New tabs pass through the same authorized website checks.

Once a form is found, the browser component enters credentials without giving them to the model. It checks the authorized website and field values before submission. An ambiguous form or an unexpected value prevents submission. In two-step forms, it distinguishes the email address from the password; a sign-in link elsewhere on the page does not turn a newsletter form into a login form.

After submission it observes the page for a bounded interval. Sign-in evidence that appears within that interval completes its own stability check, for at most the observations the check requires; later, interrupted or unobservable evidence remains unverified. When the form submits by script and its own request has not answered yet, observation extends once by one more interval. A page already loading the next document, as in single sign-on redirects, is not an outcome yet: observation and collection wait for that document.

Saving, listing, using, and deleting credentials share one encrypted store. Listings show metadata only. Values do not appear in results or logs, and changing the instance data directory does not select a different store.

Collecting data across pages

A request such as “collect all invoices from 2026” requires Metnos to distinguish the objects sought, the filters, and the fields to extract. Finding the first list does not finish the job: Metnos also looks for next pages, archives, other periods, and details needed for the requested fields. Visible controls are examined in groups, so a long page does not hide later ones.

The search explores up to eight levels. Expansions of the same list, such as the next page, remain at the same level, as do buttons that change the page in place (a menu, the full list); that state explores only what the change revealed. A detail view enriches an item already found. Forward navigation, scrolling, and returns share 256 actions and ten minutes of active work. Waiting for the user does not consume that time or reset the attempts. Each local model decision has 20 seconds, included in the overall time limit.

On returning to a page, Metnos finds previously verified controls without repeating unnecessary clicks. Identical buttons are distinguished by the visible text of their own row. Indistinguishable rows remain ambiguous; hidden text and editable values do not distinguish them. A control that cannot be identified reliably is not chosen by its position.

After clicking a link to another page, Metnos waits for the navigation to complete. If the page instead answers in place, requesting only data without loading a new document, and then stays idle, the wait ends at once; without that evidence the normal wait applies.

A textless layer covering the whole window, while no visible control can be reached, is treated as loading: Metnos waits for it to disappear, within the usual bound, before reading the page or closing a dialog underneath. Dialogs, panels and written messages that offer something to press are not treated as veils.

Loading checks: an error, timeout or invalid result from the loading check does not establish that the page is ready. Metnos observes again within the same deadline, including the time spent on checks. A page immediately observed as stable needs no extra pause.

Likewise Metnos waits for data the page is still downloading, such as a list of bills that appears after the page opens. A request that stays open beyond the bound, such as a permanent connection, does not block reading: the page is read as it is.

After every click Metnos reads the page once it has stopped changing: some links change the address and draw the new page after the click. If a read fails because the page changes at that very moment, Metnos reads it again once, instead of stopping the collection.

An item's detail opened on another page completes that item: Metnos reads it, keeps it and goes back, without exploring other sections from there. For a complete collection the full list (for example «all bills») is opened first, then the details.

Before clicking, Metnos checks again that the control is the one observed, on the same page and in the same context. If it has changed, a previously visited route may be prepared again once, keeping consent requirements and limits. This recovery does not repeat a click already dispatched or preparation that has already closed overlays or handled consent.

The final check observes the control without rewriting identifiers in the page. Approval is consumed when the click is invoked: an error or timeout does not establish the absence of effects and does not authorize another click. A fresh observation can clarify the state without resending the command.

Observed navigation can link a row to its detail view. Only an unambiguous link lets Metnos merge the two views, preferring detail fields while retaining information found only in the list. Matching dates or amounts do not prove that two items are the same. Ambiguous or truncated views remain separate, and the original observations are retained.

Identity requires evidence tied to the item and its source. A contract, customer or supply number does not automatically identify an invoice. The model must distinguish the item's identifier from references to other entities, name the complete field and quote the original source text. The reader assigns the scope of the evidence; the model cannot invent it. Quote validation tolerates only whitespace and line-break differences; it does not reconstruct numbers, dates or amounts.

An observed, unambiguous row-to-detail relation allows enrichment even without an identifier: the individual view takes priority and observed alternatives remain in Notes. The same native link can cover an earlier view only within the same actually observed context. An identifier alone permits merging only when complete, owned by the item, in the same scope and free of collisions or incompatible fields. Dates, amounts, position and generic URLs are insufficient. Without adequate evidence, rows remain separate and ambiguities are reported. Correct interpretation of entity roles by the model and the final spreadsheet still require real-site checks.

Downloaded documents and invoice identity

When the approved action includes saving documents, files are saved in the selected folder within the declared limits and returned for subsequent reading. An error or a lost response does not authorise another submission to the website. HTML and PDF reads preserve the outcome of every address, including errors; a PDF without text reports the need for optical character recognition without claiming that recognition has already run.

Invoices with different codes remain separate even when they share a supply identifier. Code separators preserve the observed groups: INV-20-005 and INV-200-05 are distinct. Equivalent copies merge only within their own group; a row without a code cannot bridge different invoices. These changes have local verification; the complete workflow still requires acceptance testing.

One row per invoice, classes by heading

In the sheet one identifier is one row. When two pages give different values for the same field, the row shows all of them separated by « / » and is declared invalid data; rows read in different contracts or accounts stay apart, with a Context column when there are two or more. A code found in three or more different invoices is not their number.

Rows listed under a heading of another class are other items: the local model labels the page headings against the request, and a page of another class, beside one of the requested class, is not read and is reported in the Notes. A title naming only the contract or the account does not decide the class; a detail opened from a row inherits it. No word list decides what an invoice is.

When the request does not say which items to collect, Metnos asks with a form ("Which items?", for example invoices or bills) and then resumes the request with the answer. After a verified login the session is saved encrypted and reused while the private page opens without signing in; a restored session that reaches no item is not used again.

The model indicates, the code copies. On list pages the code splits rows into numbered fields; the model chooses, once per list shape, which column is number, date, amount and status, and the code copies the values as the page writes them. A code repeated across rows belongs to their container (a customer, a contract), not to a row. A choice that fails the checks leaves the page to the ordinary extraction path.

End of a collection. When the model is done with a list and no next page is left, the search does not go back to other routes of the same contract if the rows already cover the requested year: rows of the year and an older one, rows down to January, or only rows of the year with the site's own filter already set to that year. Dates are read with the shared helpers for observed dates, in any order. Otherwise the search checks the other routes: that is what guarantees no archive is missed.

Speed without dropping checks. A page seen again unchanged, whose scrolling revealed nothing, is not scrolled again; every new page, details included, is still scrolled, since scrolling also lets late data arrive. A return from a detail uses «back» only when the list shows exactly its saved text, in the same contract. A list seen again is recognized by the set of its controls, whatever order the scroll position gives them. Details of one kind (same address without parameters, same controls) are read by the model once: later ones take that reading when their row is of the requested year and the page shows that row's date; otherwise the model decides.

Robustness. When an attempt to set a date filter cannot be verified (for example the click only opens a calendar), Metnos presses Esc and continues on the page as it was, without counting the site's selection as changed. A detail empty in a second tab, where other details of its kind show data, is opened once more in the same tab before its row counts as having no detail.

Measured limits (real runs of 23–25 October): ENI 12 invoices out of 12 in about five and a half minutes (three contracts, one detail per invoice: the number is only on the detail), Enel about two and a half minutes, Fastweb about two minutes. On ENI the collection may declare itself partial at the end, when the contract selector is not recognized again after the last contract: the data are complete, the coverage of contracts is not proven. ENI shows at most five invoices per contract: a contract with more invoices in the year would not be proven complete. After frequent sign-ins sites may ask for a CAPTCHA that needs a person.

When a cloud model is used

If configured, the cloud model in the Frontier tier chooses routes to explore and recognizes visible records during collection. The semantic fallback for navigation recognized as a collection also receives observed content without requiring an exhaustive quantifier. Ordinary actions retain the local model; observing records does not authorize a click without a control or establish collection completeness. Recognition also receives the observed page text within the reading limit; the separate route decision receives control names with their section titles. These observations can contain personal data. Sign-in field values remain excluded. Login, planning, row extraction and other operations keep their respective configured models. The response counts cloud requests and the step displays a red $; a request already sent remains counted even if the available time expires.

Updated behavior; real ENI/CAPTCHA acceptance remains open: when a page read supplies rows for extraction, the linked navigation uses collection traversal and retains observations after page changes or a later error. Without a stated quantity, the goal is to collect all requested records; the original request retains the year and other filters. This rule alone does not establish completeness: evidence that the search has ended is still required.

Without Frontier configured, the local model makes the choice. If Frontier is configured but its decision fails or times out, the collection remains incomplete: it does not automatically switch to another model. Administrators can disable both cloud decisions with METNOS_SITES_FRONTIER_ROUTES=0.

Delivered with the 28 October release: the same collection observation classifies content and context, including a filter rendered as a button without ARIA attributes. Each control must be observed, and requested values quote the original request. An already satisfied filter allows traversal without changing it. Every control window is checked before the first effect; conflicting classifications or a changed scene stop the action. Sources retain the qualified context, and a detail relationship is admitted only after the scene is verified.

A filter selects the requested population; an expandable group reveals rows of the same population and is a collection route. A year in the name does not distinguish these functions. A control classified as context cannot also be a route, even when the filter is already satisfied.

A relevant partition with observed alternatives retains the existing bounded traversal. Unclassified options, ambiguous ownership, or controls that cannot be verified leave collection incomplete; the system does not invent a menu state. Synthetic tests verify two details and the resulting spreadsheet; the actual ENI file still requires acceptance.

Filters, dates, and spreadsheets

Real-workflow acceptance testing remains open. The collection phrases, cookie-panel observations and textual robot challenges described here still require testing and acceptance of the real workflow.

“All” and “complete list” retain their meaning of a complete collection even when the plan shortens the request, only when asserted for the requested object. Negation and prohibitions do not activate that collection; the adjective “complete” alone does not define its scope. Recognizing the request does not establish that every item was found. Period, category, and other constraints must refer unambiguously to the same action and apply together to every item. Filters apply to collected data: an intermediate page’s date is not enough to exclude a route. A summary or another invoice does not establish that an item meets the requirements.

Dates retain the precision of their source: “08/2026” means a month, “July–August 2026” an interval, and “15/09/2026” a day. English month names are also recognized. The year must appear in the source; numeric dates retain day/month order regardless of interface language. Unreadable dates are reported with the number of excluded rows and the affected field, including in the spreadsheet result.

A spreadsheet reuses an extracted field when a heading differs only in capitalization or surrounding spaces. It first looks for an exact name, then a unique match allowing those differences, then a unique match ignoring punctuation and accents. It does not resolve ambiguity by choosing the first field. Issue dates and due dates remain distinct.

The shared vocabulary also recognizes identifier number, amount, and status across Italian labels and English keys. Identifier numbers remain distinct from counts. These matches do not depend on field order or require a model call; competing fields still need an explicit source binding.

Spreadsheet headings are labels, separate from extracted keys. They do not add fields to an already declared schema; an explicit heading-to-source binding can request another field. Without a schema, headings can define it. A temporal filter already declaring its field and period does not receive a second automatic filter without a field.

Field discovery covers every row. A unique field that is present but empty can produce an empty column; a collision remains ambiguous even when it first appears in the last rows.

Values supplied as data never become formulas. In XLSX files, new text is stored as text, preserving existing formulas when rows are appended. In CSV files and Google Sheets writes, active text receives a protective leading apostrophe: in CSV this is part of the value and may be visible. Receipts report the number of cells protected this way. Devices need the updated package: an old package does not gain this protection without an update.

For a failed browser action, internal diagnostics distinguish preparation, command dispatch, subsequent work, cleanup, and recording. They retain the exception type and signals from a closed set, without returning messages, selectors, or page data. Signals may also match quoted text: they do not establish a cause and do not change outcomes, retries, or limits.

When the sign-in procedure returns, including before any credential use, the audit retains its outcome, reason and internal class, the last phase, and the number of search actions. A navigation refusal contributes only counters and comparisons from a closed set, without page data, destinations, or secrets. This trace supports diagnosis without adding attempts or establishing the cause of an error.

CAPTCHAs, codes, and resuming

Website boundaries and consent requirements remain in force throughout navigation. Cookies follow a separate procedure that rejects optional choices and rechecks new notices before submission. After rejection, it briefly waits for the panel to close, observing it without repeating the click or asking the model for another decision. OTP codes are requested from the user unless automation has been explicitly authorized; they are not treated as CAPTCHAs.

Metnos observes the panel’s static, non-editable public text, including text inside forms or elements without their own box (display:contents). It includes the panel’s own accessible name and the alternative text of visible images within it. Hidden or unrelated content, field values, editable text and active code remain excluded, with the same bounds and redaction. This evidence can also identify a promotional notice: classifying it as other does not authorize clicking Close.

Rejecting cookies requires explicit meaning in the control label and an observed pair of identifiers from the same panel. A generic close control or a navigation menu does not constitute rejection. Cached decisions are checked again; when evidence is insufficient, Metnos pauses the action. Rejection expressions come from the updatable native lexicon, without rules specific to each portal.

A field named “code” or “token” does not by itself require an OTP. Metnos looks for a visible, editable field identified as a one-time code or accompanied by verification evidence within the same form or field group. It recognizes numeric and alphanumeric codes, including codes split across single-character boxes. If several fields prevent an unambiguous choice, it does not enter the code. Sensitive fields remain obscured and submission respects the authorized website boundaries.

Metnos also recognizes an explicit textual request to verify humanity within its own sign-in form. It reads the complete prose, retaining FAQ context, quotations and negation around the message, even with nearby links, buttons or fields. Quoted examples, FAQ statements and negated requests do not activate verification. Visible credential fields can be temporarily disabled: this does not clear the challenge or permit filling or submission. A textual request goes to manual control when no widget can be identified.

Updated behavior; real ENI/CAPTCHA acceptance remains open: verification text alongside one supported widget, identified on the current page, does not prevent an automatic attempt within the existing limits. With text alone or ambiguous widgets, Metnos asks for help. The attempt still requires verification on the page; this does not qualify general CAPTCHA solving or image-grid solving.

At every appearance, anywhere (since 29/10): a challenge can come back several times in one visit, for example a checkbox at the entrance, an image grid, a check of the site's own and a new checkbox on the credentials page. Every appearance gets the same attempts described below, at the login as well as while navigating, collecting and reading: the provider checkbox, the local library for Cloudflare CAPTCHAs and one visual proposal; if the challenge remains, it goes to you in the CAPTCHA panel. An appearance ends when the site accepts it or after you had control; the time you spend on the panel does not use up the login's time. At most five appearances per browser session get automatic attempts; later ones go to you. Text-only verifications stay with you. When a login is postponed after an abandoned challenge, the message gives the time from which to try again.

3×3 image grids (since 29/10): when the checkbox opens a grid of nine images ("select all images with…"), Metnos has a public local classifier label them, with no cloud model. A fresh grid almost always holds three right images: Metnos answers only when three tiles clearly stand out, then presses "Verify"; in grids that replace the clicked images it scores each new image and clicks only when it is clearly in or out. When in doubt, when the grid has 16 squares or when the object is unknown, it asks for another challenge with the grid's own button, as you would, up to six grids; then the grid goes to you. The instruction's word, in the page's language, is matched to the object by code or by the local model. On 662 real grids the first view is answered exactly in 57% of cases, with a wrong tile in 0.8%; with new challenges the estimate is about 85 appearances in 100 solved by itself, to be confirmed on real sites. Without the classifier installed the grid always goes to you. Grids it cannot answer stay on the server in a small store of hard cases (at most 500): only the provider's pictures, the instruction word and the scores, with no addresses or account data. They serve to test recognition later.

When it cannot finish

Since release 122: when a web control is obstructed, the managed browser automatically saves a static page copy and the obstruction measurements. No console script is required. The copy omits private fields and active code; it stays local, protected like screenshots. Capture is skipped during pending consent or authentication steps and does not certify the website workflow.

If no proposal is admitted, the loop is inconclusive. If its attempts or elapsed-time budget runs out, it is exhausted. The adapter then maps that outcome to its executor's public contract: it may keep the deterministic result, return a typed error, or request user intervention. The shared loop does not invent a result or promise persistent resumption by itself.

Transport and intelligence are independent. A local or remote executor may be direct or intelligent. Transport determines how it is reached; the manifest, policy, and code determine what it may do.

Supervisor: one proposal or several alternatives

An executor may encounter an obstacle during an already authorised operation. In single mode it evaluates one proposal; in swarm mode it compares independent alternatives. Only the resource owner applies the selected proposal. Analyses share the remaining time and limits; another attempt does not reset them. Parallel analysis will be used where measurements confirm a benefit.

Proposal selection and operation success are separate outcomes. An independent check verifies the change in the current session. Late responses are discarded. All owned activities must actually end before work resumes or control returns to the user; incomplete shutdown remains an explicit obstacle.
