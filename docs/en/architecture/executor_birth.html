Executor birth: a single gate

Every new or modified executor enters service through a single control gate, called Birth. Every Metnos update goes through the same signed administrative path. Signatures on existing contracts remain verifiable, but verifying them does not authorize new code to execute or publish with a previous authority.

One candidate, one admission procedure

A capability proposed by Synt follows the common Birth procedure. The candidate stays separate from the installed version until it passes the required checks. Generating an executor is not a release of all of Metnos and does not require repeating every past certification.

The reviewer's reply is read in full as JSON and rewritten in canonical form before verification. Whitespace and field order do not change the verdict; duplicates, wrong or incomplete content are rejected. The model's opinion still requires independent evidence.

Verifying a new candidate does not create a catalog entry. A rejected candidate therefore leaves no incomplete function that would block the next update.

Behavioural and semantic checks on the candidate run without holding the catalog publication lock. The short final step checks the candidate and compares its name with the signed identities already installed. If another component has damaged code, it stays unusable; its signed name remains reserved, but this does not prevent repairing a different component. While a candidate is being verified, the installed version stays usable.

Memories follow the executor version

Every executor has a single fingerprint, derived from its signed version. All catalog-dependent memories use the same fingerprint: plans already decided, planner alternatives, prefilter and affinity index. When an executor changes, appears or disappears, the decisions that involve it are recomputed. HTTP pages reread the catalog through the same cache: an admission or a withdrawal becomes visible without restarting the server.

Updating without rewriting history

Every update authenticates the historical set and its key bindings under a single barrier. Readers receive only the identity of the set and the public verification keys, not an executable runtime.

If a contract is unchanged, Metnos verifies its signature and content without republishing it. If a change must be published, it builds the complete runtime and checks that its context matches the sources: a different context is rejected. Changing the historical set, the key inventory or the binding between contract and generation causes a rejection; a historical signature is not a general permission to execute new code.

Withdrawn components

Withdrawal entries describe only components of the old installation. A module introduced by the new distribution stays covered by the signed inventory and by the checks of the new distribution. The absence of a real required historical component blocks the update.

Checks on old code entry points can be added while keeping every previous entry identical. If the file existed in the authenticated historical inventory, its exact withdrawn copy is required; if it did not, its absence must be proven in protected folders without following links. A missing file alone does not prove that it was withdrawn.

The verification neither creates nor deletes files. The release tool runs it before stopping services and repeats it under its own exclusive controls. An unchanged withdrawal obligation reuses the signed proof already verified; a new obligation requires its own proof. A missing or altered proof stops the update.

Checking the present without rereading all history

Producer requests identify the verified software version. Repeating the same request on the same version reuses the receipt. After an update, a new request uses the current authority; previous receipts stay intact.

A new admission passes the security checks without repeating work already verified on previous versions. The reader uses the signed reference to the current version, checks the link to the previous one and verifies the files actually installed. Altered signatures or a version change during the read cause a rejection.

The launcher tells services the folder of the verified installation. Publication checks that the code comes from exactly that folder; a value inherited from the environment cannot replace it.

Old program copies

The release procedure keeps the active version and a previous one, plus copies still used by processes, services or operations in preparation. Only after a successful release does it remove the other copies. The previous copy serves recovery: it does not authorize an automatic return to an older version. This cleanup concerns only distribution code: it does not remove signed receipts, personal data, models or information still needed.

Planned: collecting history no longer in use

Metnos will also safely collect history that nobody uses any more: copies of candidates already examined, superseded generations and temporary files. Whatever is still referenced, or needed for an undo or a recovery, is kept, and every collection is recorded before anything is deleted.
