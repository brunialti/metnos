Verifying history does not mean executing it

When Metnos code changes, signatures on existing contracts must remain verifiable. This does not authorize new code to execute or publish using a previous authority context.

One candidate, one admission procedure

A capability proposed by Synt follows the common Birth procedure. Its candidate is kept separate from the installed version until the required checks succeed. Generating an executor is not a release of the whole Metnos system and does not require replaying every past certification.

Property and semantic checks run outside the catalog publication lock. The short publication step checks the candidate and reserves its name against the signed identities already installed. It does not recheck the executable code of unrelated components just to read their names. If an unrelated component has damaged code, that component remains unusable; its signed name is still reserved, but another component can be repaired.

Verification status: the simplified name check is tested in development, not yet deployed. An isolated test follows the real Birth, signed-store and execution paths: the installed version remains callable while a new candidate's check is deliberately paused, and after that check fails. This is not a live chat or model-latency benchmark. Shared authority integrity, candidate safety and name uniqueness remain mandatory.

The first coordinated transition

The initial path authenticates the historical set and its key bindings under one barrier. Readers receive only the set identity and public verification keys, not an executable runtime.

For an unchanged contract, convergence verifies its signature and contents without publishing it again. If a change requires publication, it constructs the full runtime and checks that its context matches the source code: a different context is rejected.

The new context is still required

Historical reading does not replace transition reattestation, which remains bound to the new authenticated distribution. Changes to the historical set, key inventory, or contract-to-generation binding are rejected; a historical signature is not a general permission to execute new code.

The census distinguishes the old and new installations

Retirement entries describe only components of the old installation. A module introduced by the new distribution must not be required in its predecessor: it remains covered by the new distribution's signed inventory and verification. A missing required historical component still blocks the transition.

Resuming reuses the recorded historical census, because retirement may already have renamed some files. The document must retain its valid format, integrity and safe ownership and match the same transition, installation and catalog exactly. It is neither rewritten nor treated as a fresh verification of current state.

Check the present without replaying the entire history

A new admission must pass its safety checks. It should not repeat work already verified for every earlier release. The optimized reader uses the signed current-release reference, checks its link to the predecessor and verifies the actual installed files. Altered signatures or a release change during the read still cause refusal.

Work status: this path is implemented and tested in development, but not yet deployed. The administrative startup verifier has also passed a read-only check on the real installation: it checks the current release, its predecessor and any successor being prepared. The release coordinator's journal inventory remains to be optimized. Initial certification and an explicit historical investigation remain separate activities.

A certification key does not grant operating permissions

The initial F5 proof uses a dedicated administrative identity, separate from the keys that admit executors. Its private part stays with the administrator; a runtime verifier needs only the public part. A missing or revoked certification key must not stop components already operating under F4, and preparing the key does not activate F5.

Development status: isolated Linux tests cover key preparation, recovery after a process stops, and public-only reading by an unprivileged account. The proof derived from real admissions, migration and lifecycle integration are still unfinished. F5 and F6 are not complete; native Windows custody is not implemented.

The administrative evidence record also keeps failed and interrupted test cycles. Two selected successes do not erase an intervening failure; a repeated turn cannot count twice. Closing a known defect requires its repair, verification and independent review. This record is implemented in development, but is not an F5 certificate or an activation switch.

Keep the evidence, not every old program copy

The release procedure normally retains the active release and one predecessor, plus copies still referenced by processes, services or operations being prepared. It may remove other copies only after a successful release. The predecessor is recovery material, not permission to downgrade the selected release automatically.

This cleanup removes distribution code only. It does not remove signed receipts, personal data, models or information still needed for migration. Fewer program copies do not mean fewer safety checks.
