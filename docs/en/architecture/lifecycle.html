Metnos

Change lifecycle
One shared object for proposing, deciding, applying, and observing a change.

Sources that suggest an improvement do not modify Metnos directly. They translate the suggestion into a change_intent: a typed record with origin, target, rationale, score, and state. The /admin/changes page presents these records and keeps their progress visible.

1. The shared object

Records are stored in ~/.local/state/metnos/change_intents.sqlite. Their main fields are:

GroupContents
IdentityAn id and deterministic fingerprint for deduplicating equivalent proposals.
ProvenanceSource family, module, original identifier, and discovery time.
IntentClosed kind, target, summary, rationale, and kind-specific payload.
PriorityScore, confidence, and number of converging sources.
DecisionPerson, action, reason, and decision time.
OutcomeApplied effect, observed metrics, error, or rollback data.

The fingerprint excludes the source family. If two sources describe the same change, the upsert can merge them into one record and increase convergence without duplicating the action. A score is an ordering aid, not an authorization.

For a creation the fingerprint is the executor name alone: one capability has one proposal, whoever wrote it, and a rejected proposal does not come back from another source. Convergence counts distinct sources, not repeated readings of the same one. For missing capabilities the score follows the requests of the last 30 days and falls when they stop; the same sentence counts once a day.

2. States and transitions

proposed  --accept--> accepted --apply--> applied
    |                       |                  |
    |                       +--error--> failed +--measure--> observed
    +--stage--> staged                              |
    +--reject--> rejected                           +--ok--> finalized
                                                   +--problem--> rolled_back

A staged proposal may return for review. A failed change may be retried or rejected. Rollback is terminal in the registry and performs a physical reversal when the change kind supports one. The state machine blocks arbitrary jumps: a proposal cannot become applied before it is accepted.

3. Active sources

The materializer reads four side-effect-free adapters:

SourceWhat it can produce
TelosExecutor creation or extension and a controlled pipeline trial, from actionable cluster heads.
IntrovertivaExecutor deduplication; it also preserves already-recorded states that must remain inspectable.
SyntExecutor-creation requests and their terminal or in-progress states.
User feedbackA proposal to reject a pattern after at least two consistent negative reports.

Adapters translate different storage formats into the same schema. They neither apply the change nor turn an automatic inference into human consent.

4. Materialization, application, and observation

TaskDefault frequencyResponsibility
change_intent_materializeDaily at 01:00Reads adapters, deduplicates by fingerprint, and updates the store.
change_applierEvery 10 minutesProcesses up to 20 accepted records and records either their effect or error.
change_observerDaily at 03:15Measures up to 200 applied or observed changes and decides whether to finalize or roll them back.

The default observation period is seven days and can be changed with METNOS_CHANGE_GRACE_DAYS. Criteria vary by kind: executor health, alias integrity, the result of the turn used to try a pipeline, or new feedback about a rejected pattern.

6. The cycle of a generated tool

Metnos can build by itself a tool it lacks. This is where its introspective functions show best: it notices what it cannot do, tries to build it, asks the person one thing only and removes what does not work. The figure shows the whole path.

  1. It notices. When a request ends with “I cannot do this”, Metnos records what was missing: which action, on which object. The same gap asked several times weighs more; when nobody asks any more, the weight goes down.
  2. It proposes and starts. Each missing capability has one proposal, together with the real requests it was born from. When the name belongs to the tool vocabulary, Metnos starts building without asking: building activates nothing. A few candidates at a time, the most requested first.
  3. It builds. With the local model it chooses the name, decides the arguments, writes the tests starting from those real requests, then the description and the code.
  4. It checks. The candidate runs in an isolated sandbox against its tests, and a reviewer compares what the description promises with what the code does. If something does not match, the precise reason goes back to the builder, which tries again knowing what to fix. At most three attempts.
  5. It asks for help only when needed. After three failed attempts Metnos does not insist. Whether it may use the external model to finish is decided by the person, once: never, always, or “ask me each time”. The external model writes tests and code only; name, arguments, description and checks stay the same. Without permission, or if that is not enough either, the proposal closes for thirty days: no endless loop of create, discard and recreate. When the choice is “ask me”, the question also reaches the administrator on Telegram, with the same two buttons as the page: answering on one side closes the question on the other.
  6. It asks one question. The ready, tested tool appears on top of the Changes page: what it does, which permissions it asks for, whether what it does can be undone, which cases it was built on. The person answers Activate or No. It is the only decision of the whole path. A notice on Telegram says the tool is ready; the answer is given on the page, where everything can be read.
  7. It enters service. After the yes, the final checks and the signature run; only then can the planner use the tool. The page shows the work in progress and then the outcome. If the final checks refuse it, the tool does not enter and the proposal says why. After a no the proposal rests for thirty days.
  8. It stays under observation. It is planned that a generated tool that errors is retired at once and rewritten with that reason, and that one never used decays after sixty days.

The signature is not made by the service that built the tool. It is made by a small program of the server administrator, which keeps the keys and accepts the request only from the administration page. It is installed once; while it is missing, the page says so and the button stays off. Generated tools cannot reach it.

What always stays with the person: the final answer on every tool, new vocabulary words and the choice about the external model. Handwritten tools are never touched by this cycle.

It is planned that “safe” tools need not even the final question. “Safe” has a precise meaning: the tool only reads or computes, or does things that can be undone, and asks for no new permission.

The underlying idea: safety does not come from asking the person everything, but from asking one thing only, about something finished and tested, and from being able to remove at once what does not work.

7. Natural-language example

Ask Metnos with a request like this example: “Show me the system changes waiting for my decision and explain the first one in plain language.”

Decisions are made in the web chat. If you are talking to Metnos through Telegram, open the web chat, enter the administration area, and choose Changes; the technical route is /admin/changes. The page can filter by state, source, and kind and offers only the transitions allowed for each record.

8. Guarantees and limits

  • Acceptance is an explicit decision attributed to the administrator; a high score does not replace it. Accepting a proposal that asks for a new vocabulary word requires the reason; an error is shown in the row it came from.
  • The applier is idempotent per kind and writes a local audit. An error leads to failed, not apparent success.
  • Rollback depends on the kind. A pipeline run as a real turn cannot reverse external effects that have already occurred; normal consent gates still apply before execution.
  • Text produced by automatic generators helps triage, but must be read alongside provenance, payload, and recorded effects.
