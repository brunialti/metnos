Shared spreadsheet writing

The shared writer separates column and type selection from physical output. The API and the local XLSX/CSV creation adapter are in use on the server, covered by module and regression synthetic tests and by authenticated readback. Real-site acceptance of complete collections, Google adoption and verification of the package loaded on the PC remain separately in progress.

One contract

The internal API write_table(source, spec, destination, mode="create") takes records or matrix rows. An explicit schema declares each header, exact source field, supported transform and type. The compiler produces a versioned Workbook / Sheet / Column / Cell contract; adapters only write this contract. Header-only resolution happens at the runtime boundary and reuses the existing shared projection across all public rows.

Every matrix row in the shared contract is data, even when it equals the header. The local create adapter consumes a header only when declared by the caller or produced by record projection; a matrix without declared columns keeps its first row as data. Writing never removes duplicate rows. Private fields and runtime-declared sensitive fields are excluded recursively, including inside structured cell values and source metadata.

from tabular.api import write_table
receipt = write_table(
    [{"observed": "2027-04-12", "amount": "12.50 USD"}],
    {"locale": "en", "name": "Data", "column_specs": [
        {"header": "Date", "source": "observed", "type": "date"},
        {"header": "Amount", "source": "amount", "type": "currency", "currency": "USD"}]},
    {"backend": "local_xlsx", "path": "synthetic.xlsx"})

Local spreadsheet destination

The spreadsheet is written to the file or folder named in the request. The folder searched for data does not by itself become the destination: when no destination is given, the ordinary spreadsheet folder applies. The runtime checks contract-declared arguments, including the path alias, using the vocabulary of the ready language. References to earlier step results and writing to a named existing spreadsheet remain valid. A reference such as “there” can point to one of the folders already named; the check does not choose a new folder. A name without a folder remains a file in the ordinary spreadsheet folder or a remote name, according to the backend contract. An invented folder is removed from a path while its filename remains, even when the plan chose it. Writes to the same spreadsheet stay together in the ordinary folder; two distinct named files stay distinct.

Column identity and header language

When a column matches a record field by name, it preserves empty values too. A populated field may replace it only when the vocabulary declares both names as aliases of the same field, or its more specific name contains every word in the header. Distinct dates do not fill one another. Deriving a filename from a path remains possible; if the alias vocabulary is unavailable, the empty field stays empty.

column_specs separates source, the exact record key, from header, presentation text in any language or alphabet. The planner, extractor or executor that knows the schema must supply this map, for example {"source":"amount","header":"金額"}. Record key order does not matter. The writer does not translate keys, infer equivalence from values or position, or call Frontier. No per-language aliases are added; an explicit map also works without a header lexicon.

The normal plan can declare the map from the schema already available to it, without an extra model call. Header-only resolution remains available at the same boundary; when a map is missing and the correspondence is not unique, it returns an error listing headers and available fields. Dates with distinct roles are not merged: the caller must declare the chosen source.

Producer-declared roles distinguish the original and the copy for both paths and dates. When a header recognized by the existing vocabulary contradicts the declared role, the projector corrects the source only when the correspondence is unique. A header expressing only the role preserves the source data concept; ambiguous mappings are rejected.

Declared conversions without invented data

Extraction sends one source to the model per call; requests for larger groups are clamped to one. Each field receives only a value that the source attributes to that field: when absent, it stays empty even if another field in the same record contains a value of the same type. Date normalization respects this attribution before applying precision and assumed-year rules.

When the request explicitly asks for extraction, the plan uses those words as its instruction, together with other clauses naming a requested field. This preserves the person's explicit rules without adding filling rules of its own. Extraction applies a requested filling rule even when the source lacks the value; without an explicit rule, the field stays empty. A separate rule using different words from the field names is not included. If extraction is implicit or the request contains several extraction clauses, the planner's instruction remains; frozen plans and internal extraction calls in site collections follow their existing path.

The extract_entries producer recognizes amount fields through the reconciliation lexicon’s amount_field gate. For these fields and explicitly declared numeric or monetary columns, the readings allowed by the separator table are compared. One valid reading, or several readings with the same value, is converted directly: 10.00 becomes 10 in Italian too. When readings yield different values, the instance language decides: Italian 7,80 becomes 7.8 and 100.000 becomes 100000; English 100.000 becomes 100. The runtime adds the internal locale argument only for an explicit choice found in the request lexicon; otherwise it stays absent from the plan and the instance language applies. The planner does not choose it. An explicit request can select another convention, for example “use Italian number format”. Separators are defined in one table per language. Values invalid in every convention, codes with leading zeros and values with more than 15 written digits stay text; native numbers retain their value. The decision to keep an amount as text follows its record to the writer, even when the column is numeric and uses another convention. The answer and Notes count these values and explain how to request Italian or American number format. In declared amount fields, an observed EUR, USD, GBP or JPY code or symbol identifies the column currency, which stays visible in its format. Mixed currencies in a field stay text; an unknown code is not converted. Values written directly by the planner without a declared type retain their existing behavior.

Complete dates become real date values. Month/year, year-only, assumed years marked with * and impossible dates remain text. Datetimes with a timezone or precision beyond milliseconds remain text until an appropriate conversion is declared. Missing days, years or midnight are never supplied. Numeric locale does not select a regional date grammar: slash dates follow the existing observed-date helper's day/month/year contract; use ISO dates for an unambiguous interface.

The initial contract accepts no formulas. A type="formula" field or a value extracted from a site cannot grant formula authority. New active XLSX strings stay text; Google uses explicit string values. CSV adds a visible apostrophe to active text, including headers and Notes, and reports this change.

Source incompleteness and writer limits

Declared source flags such as truncated and collection_partial, available_total, used and cap metadata remain in per-sheet source_metadata, cleaned of private and sensitive fields. An unknown total stays null. Counts alone do not authorize a claim of complete or incomplete collection.

source_partial and source_truncated describe the source declaration; writer_truncated and truncations describe reductions during writing. The receipt’s general total counts rows received by the writer and does not replace the declared source total. A partial collection flag produces the localized WARN_TABLE_PARTIAL_SOURCE notice in chat and Notes even without a textual reason. A verified file readback does not prove that all site pages were collected.

The browser broker produces a typed envelope with its producer and a collection-specific scope. Metadata follows act_sites → read_sites → extract_entries → filter_entries → write_table through the local adapter as a runtime-resolved argument: page text, rows and the model cannot declare source completeness. Successful extraction or filtering preserves upstream incompleteness. A known cause produces a localized explanation in Notes and chat; an unknown cause retains the generic warning without exposing its technical code. Provenance retains only the HTTP(S) origin and path, without credentials, query or fragment. Producer and scope do not identify invoices or authorize new record associations or row removal.

When extract_entries reads the result of read_sites, the runtime captures the text without attaching a screenshot of the page to the chat.

The text preview after navigation is separate from stored data: the 4,000-character presentation cap exposes presentation_truncated, preview_used and preview_available_total, without declaring a collection cut or changing collection limits. An actual collection stop instead retains its partial state and cause through to the sheet; file verification does not cancel them.

Notes, receipts and undo

Notices and provenance appear both in the chat-facing receipt and in a Note sheet. New sheet name collisions are resolved and declared, for example as Note_2. An existing user Note sheet is preserved: a write that would replace it is rejected. Generated Notes carry an internal ownership marker; updates never silently leave stale generated Notes behind.

For CSV, Notes use <name>_note.csv. The receipt lists both files and each undo. Updating an existing pair requires an explicit destination.notes_path; an unrelated Notes file is not implicitly overwritten. Publishing the pair is not atomic: failure on the second file retains the first as a partial result.

Receipts distinguish compiled rows, verified rows and known created or modified artifacts. XLSX and CSV are read back before publication; Google is read back by comparing typed values and formats. A known created Google ID remains in the receipt with undo even when readback fails. A creation error without an ID has an unknown outcome and is never retried automatically.

Adoption boundary

The runtime routes local creation in backends.files.local.create_spreadsheet through write_table, retaining the caller’s consent boundary, shared projection and ordinary undo for all created files, including CSV Notes. XLSX creation and readback use the standard-library writer; XLSX overwrite and append still require openpyxl. The observed-date normalizer is also pure and consumes explicitly supplied month names; the server facade retains catalog lookup.

Distribution must include the writer and date-normalizer support files. Updated create code in a package missing those supports returns an error without claiming a verified file; an entirely older package continues to run its older code. A server package offer does not prove which package a device loaded: actual readback is needed before claiming adoption.

The Google paths do not use the shared writer yet: the API reuses the Python OAuth client, but consent, replay with original inputs and Google adoption require separate verification. Verification of the package actually loaded on the PC is planned. File-writing verification does not establish complete collection.
