1. Cosa fa: secondo server HTTP

La HTTP API è il secondo server di Metnos: in ascolto su porta 8770, separata dal server di pairing dei device remoti (porta 8765). Espone tre cose: un cruscotto amministrativo in HTML per il host, un canale agent uniforme (POST /agent/turn) per chi preferisce HTTP/SSE al posto di Telegram, una discovery del nodo (/.well-known/metnos.json) per i client.

La scelta di un secondo server (anziché estendere il pairing server o passare tutto da Telegram) e' motivata da tre vincoli: (a) l'interfaccia admin deve essere a portata di browser senza che l'host debba aprire Telegram per gestire utenti, scheduler, proposte introspettive; (b) il canale agent HTTP serve come fondamento per il client Rust e per integrazioni a venire; (c) il pairing server e' minimale per design (porta 8765, solo register-device) e non va appesantito.

Bind di default: 127.0.0.1:8770. Per esporre alla LAN si modifica il bind nella config; per andare oltre la LAN va aggiunto un terminatore TLS davanti al server (vedi cap. 8).

3. Autenticazione e ruoli

Tre ruoli, in ordine crescente di privilegio: anonymous < user < admin.

Admin key

File ~/.config/metnos/admin.key (mode 0600), 256-bit hex generato con secrets.token_hex(32) al primo avvio del server. Nei log compare solo l'impronta sha256 (primi 16 hex). La admin key e' anche la chiave maestra della cifratura delle credenziali (vedi cap. 7).

Accesso web: POST /admin/login con la admin key in chiaro; risposta set-cookie con TTL 7 giorni (HttpOnly, SameSite=Strict). Da CLI/curl: header Authorization: Bearer <admin.key>.

Bearer token device

Il middleware confronta il Bearer con la public_key_b64 di ogni device pairato (tabella devices di pairing). Match → ruolo user.

LAN fidata + lista bianca anonima

  • LAN: 127.0.0.0/8, 192.168.0.0/16, 10.0.0.0/8 → ruolo user di default, solo se nessun Bearer e' stato presentato e fallito.
  • Lista bianca anonima: / (chat), /agent/health, /.well-known/*, gli asset statici/PWA, /oauth/callback, /pair/{token}. Ogni altra path richiede almeno user.
  • Varco admin: ogni path che inizia con /admin/ richiede ruolo admin; altrimenti 403.
La distinzione «LAN fidata» e' figlia del modello self-hosted: sulla rete di casa il rischio e' contenuto, e l'host vuole curl/htmx senza header. La policy si irrigidisce appena il bind si apre alla WAN (dove va aggiunto il TLS).

4. Negoziazione del contenuto + ETag

Le rotte di collezione esaminano Accept: text/html → frammento Jinja2 (adatto a htmx); altrimenti JSON. In entrambi i casi viene calcolato un ETag (sha256 del corpo della risposta, primi 16 hex). Se il chiamante ripresenta If-None-Match con lo stesso valore, la risposta e' 304 Not Modified senza corpo.

5. SSE su /agent/turn

Quando il client manda Accept: text/event-stream, POST /agent/turn apre uno stream e installa un _SSEProgress (implementa l'interfaccia runtime.progress.Progress) che il run_turn invoca a ogni passo. Eventi emessi:

EventoQuandoPayload
thinkingApertura stream + intestazione di ogni fase LLM{"message": "..."}
progressAvanzamento dei passi (note operative){"stage": N, "label": "..."}
tool_callA ogni passo, prima di invocare un tool. Alimenta la traccia dei passi in tempo reale nella chat.{"tool", "step_num", "path", "predicted_remaining", "args"}
finalChiusura dello stream con la risposta finale{"message": "..."}
errorErrore catturato dal turno{"message": "..."}

Il run_turn gira in un thread executor (sincrono) mentre la coroutine principale pompa gli eventi sullo stream tramite asyncio.run_coroutine_threadsafe.

Niente evento tool_result separato. L'esito di ogni passo non viaggia come evento a sé: è già riflesso nel path del tool_call successivo (i passi completati diventano contrassegni pieni nella traccia) e, alla fine, nel messaggio final. Così la chat disegna l'avanzamento in tempo reale senza un evento dedicato.

6. Cruscotto /admin (htmx + uPlot)

Impianto di interfaccia deliberatamente minimo: htmx + Jinja2 + uPlot via CDN, nessuna fase di build, nessun framework CSS. Template compatti (<50 righe ciascuno) sotto runtime/templates/. Stile system-ui pulito, tavolozza allineata al resto della doc canonica (navy / sage / bronze).

Pagine principali (rendering Jinja2 + frammenti htmx):

  • dashboard.html — sommario: conteggio del catalogo, ultimi 5 turn, ultimi 5 utenti pairati, conteggio delle firme di safety, latenza media degli ultimi 20 turni.
  • executors.html — tabella del catalogo con colonne name, kind (handcrafted/synth), lifecycle, uses_30d, last_used.
  • executors_stats.html — grafico uPlot con i conteggi giornalieri di esecuzioni per executor.
  • changes.html — ciclo di vita unificato delle modifiche con bottoni accetta / rifiuta / metti in stage / ripristina / riprova.
  • runs.html — ultime esecuzioni dello scheduler (cron + task utente ricorrenti).
  • safety.html — firme di safety.
  • turns.html — ultimi N turn dal jsonl, con le credenziali gia' rimosse.
  • users.html — tabella utenti host + guest (vedi pairing).
  • user_detail.html, user_pair.html — dettaglio + emissione pairing token.

7. Rapporto con channel (Telegram) e pairing

Telegram resta canale primario per il dialogo conversazionale (long-poll, basso costo, esperienza d'uso coerente su dispositivo mobile). L'HTTP API e' canale alternativo per:

  1. Host browser: cruscotto /admin per amministrazione (utenti, scheduler, proposte introspettive, safety).
  2. Client Rust: turn remoto da PC Windows/Linux pairato, via POST /agent/turn con SSE.
  3. curl/script: automazioni casalinghe veloci (curl -H "Authorization: Bearer..." http://localhost:8770/agent/turn).

Il run_turn invocato via HTTP riceve channel="http"; non viene registrato un Channel formale nel channels.daemon (modello poll-based incompatibile con request/response). Per il vaglio e per policy l'effetto e' equivalente: i passi passano dagli stessi controlli, l'audit conserva channel="http" nel turn log.

Multi-utente: l'HTTP API e' il punto di amministrazione della tabella users.db. Pairing dei guest via POST /admin/users/{id}/channels/telegram/pair: l'admin riceve un token a vita breve, lo passa al guest, il guest manda /start <token> al bot. Il flusso e' descritto in pairing cap. 6.

Credenziali: la admin key del server HTTP e' anche la master della cifratura simmetrica per ~/.config/metnos/credentials/<domain>.json.age. Chi controlla ~/.config/metnos/admin.key (mode 0600) puo' leggere le credenziali. Copia di sicurezza offline raccomandata.

8. Limiti noti

  • TLS: la porta 8770 è in chiaro. Sul piano LAN-only il rischio è contenuto; per l'esposizione su WAN va messo davanti un terminatore TLS (o un certificato autofirmato fissato per impronta, riusando il materiale di pairing).
  • Limite di frequenza: nessuno a livello applicativo. Da aggiungere se il server viene esposto oltre la LAN.
  • Vincolo di istanza singola: un lockfile flock POSIX in ~/.local/state/metnos/http_server.lock impedisce due istanze sullo stesso host.
Verifica veloce dello stato. GET /agent/health → 200 {ok:true, version:"...", uptime_s:...}. GET /.well-known/metnos.json → 200 con l'impronta della admin key. GET /admin senza credenziali → 403; con Bearer admin key → 200 (cruscotto HTML). Un ciclo completo If-None-Match su una collezione → 304.
