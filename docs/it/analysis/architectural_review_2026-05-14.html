1. Architettura software

Metnos e' un assistente personale self-hosted (single-tenant + multi-utente guest) costruito su una microarchitettura non convenzionale di executor sintetizzati al volo. La codebase, in /opt/myclaw, contiene:

  • 349 file Python (~74 mila righe nette di runtime escludendo node_modules);
  • 54 executor handcrafted + N synth in ~/.local/share/metnos/executors/;
  • 129 ADR (0001-0132 con 4 skip) datate 22 aprile - 14 maggio 2026, ~3 settimane di sviluppo intensivo;
  • 85 prompt Jinja in runtime/prompts/<lang>/ (IT + EN canonical);
  • 55 manifest TOML firmati Ed25519 + signature in manifest.toml.sig;
  • 147 moduli runtime in /opt/myclaw/runtime/.

ADR 0078 (HTTP API Phase 1) e ADR 0083 (multi-user) descrivono l'architettura.

1.2 Vocabolario chiuso 23 verbi + 17 oggetti

La scelta architetturale piu' caratterizzante di Metnos e' un vocabolario CHIUSO per i nomi degli executor, centralizzato in /opt/myclaw/runtime/vocab.py. Pattern di naming: azione_oggetto[_qualifier].

CategoriaElementiConteggio
Azioni (verbs)read, write, move, delete, create, find, list, filter, sort, group, classify, get, set, send, describe, render, extract, compress, compute, compare, change, order, share23
Oggetti (plurale)files, dirs, packages, messages, events, contacts, places, processes, urls, numbers, images, signatures, texts, proposals, inputs, credentials, entries17
Qualifier formatocsv, xlsx, ocr, zip, pdf, xml, html, json, text, gz, tar, video, audio, image, hash15
Qualifier modalita'size, format, loc, similar, empty, lines, paragraphs, sentences, pages, segments, indices11
Qualifier safetyblacklist, whitelist, graylist, forbidden, seed, sanity, command, reversibility, diff, promotion, candidates11
Verbi-meta riservatiundo, admin (fuori dal vocabolario chiuso, registry verb-unique)2
System verbs (SAFE_VERBS)11 verbi read-only/pure-compute11

Il vincolo "vocabolario chiuso" e' enforced ovunque: synt_multistage.validate_stage1 rifiuta nomi che usano verbi/oggetti fuori dalle tuple VOCAB_ACTIONS e VOCAB_OBJECTS; runtime/loader.py rifiuta synth in collisione con handcrafted (ADR 0114 Layer 2); il prefilter mappa sinonimi IT/EN ai verbi canonici (~150 voci nel modulo prefilter._VERB_TO_CANONICAL).

La distinzione fra i 5 verbi-produttori e' particolarmente curata:

  • find: pattern/query, discovery, sussume verifica esistenza;
  • get: id noti o nessun arg (lookup, snapshot);
  • read: id di sorgente, ritorna contenuto;
  • list: container, enumera senza contenuto;
  • filter: lista preesistente in memoria, riduce per predicato.

ADR 0045 (executor naming convention closed vocabulary, 27 aprile) e' l'atto fondativo; ADR 0128 (12 maggio) estende il vincolo agli executor importati via skill agentskills.io con tabella di mapping deterministica.

Valutazione Il pattern azione_oggetto e' un Domain Specific Language (DSL) deterministico che riduce drasticamente la superficie di hallucination del PLANNER LLM. Il costo di mantenimento e' alto (richiede ortogonalizzazione semantica continua: vedi storia di share separato da send e set in ADR 0128), ma il payoff e' misurabile: la pipeline synt da 4/4 vs 32% single-prompt (riferimento ADR 0051-0052).

1.3 Vettorialita' obbligatoria degli executor

ADR 0041 (27 aprile 2026): Executors vectorial by construction; single item is the degenerate case. Ogni executor accetta una lista come input naturale (paths, entries, urls, ids), N=0 e' permesso (no-op con report strutturato), N=1 e' degenere. Nessun sibling *_batch.

Il vincolo nasce da un caso live (turn abb3a4d1 del 27 aprile): l'utente chiede di smistare 98 foto per anno EXIF; move_file single-item satura il cap_steps del PLANNER al passo 12, l'LLM ragionevolmente rinuncia. La soluzione "move_files_batch" sarebbe stata il fix tampone; Roberto ha preferito invertire il default architetturale.

Implementazione: cap_inferiore = 0 (lista vuota = no-op onesto, MAI silenzio), cap_superiore = parametro esplicito (max_total, max_results, max_bytes), iterazione interna (loop, paginazione, time_window last-Nd). Il branching su osservazione torna al PLANNER. truncated: true con cap_field + cap_value + available_total dichiarato ovunque il cap sia raggiunto (CLAUDE.md §2.7, §2.11 "notify then ask").

1.4 Synt pipeline 5 (+1) stadi

Quando il PLANNER incontra un'intent che nessun executor in catalogo copre, invoca request_new_executor; il synth multistage orchestra 5 stadi per fabbricare al volo un nuovo executor (codice + manifest + test + signature). Sorgente: /opt/myclaw/runtime/synt_multistage.py (473 righe) + /opt/myclaw/runtime/synth_request.py + 6 ADR (0049-0053, 0114).

StageTipoTier LLMOutputMax tokens
1 NAMINGproceduralemiddlename, revertible, critical, target_kind1800
2 SIGNATUREproceduralemiddleargs_schema, capabilities, reverse_pattern4000
3 TESTSproceduralemiddle4-6 birth test TOML4000
4 DESCRIPTIONcreativomiddle/wisedescription (80+ char) + 6-10 affinity keyword2200
5 CODEcreativo+proceduralewise<name>.py con def invoke()5000
6 VERIFY (ADR 0114 L6)verificatore semanticowisealigned bool, mismatch reason300

L'idea cardine, dichiarata in ADR 0049-0051: dividere un task complesso in stadi sempre piu' creativi, tier LLM proporzionato, contesto ristretto. Stages 1-4 girano su Gemma 4 26B middle (~370 ms/query medio), stage 5 (code) su Gemma 4 26B con think=true, stage 6 (verifier) su wise tier ma con think=false + 300 token max.

Stage 5 ha un addendum specializzato per ogni verbo del vocabolario chiuso (synt_code_addendum_{move,delete,send,write,extract,read,create,find,list,get,filter,describe}.j2), spliciato prima del marker "I/O CONTRACT" nel prompt generico. Stage 6 e' fail-safe: se il verifier stesso fallisce, il synth e' ammesso comunque (layer 2/3/5 sono ridondanti).

Anti-pattern intercettato (ADR 0114) L'8 maggio 2026 il synth find_texts ha hijackato per giorni il PLANNER per query web come "cerca su web ..." perche' affinity catch-all + description fabbricata vs codice scollegato. La pipeline synt NON aveva un giudice di drift semantico, e nessun ager decay-ava per inefficacia (solo per inattivita'). ADR 0114 introduce 4 layer cumulativi + smoke routing assertion + stage 6 verifier. L'aneddoto e' rappresentativo di una classe di rischi reali in agent runtimes auto-generanti.

1.5 Planner ReAct e prefilter

Il loop ReAct di agent_runtime.py (5280 righe, modulo monolitico) implementa la versione "tool-use nativa" del classico paper Yao et al. 2022 (ReAct: Synergizing Reasoning and Acting in Language Models), con cinque adattamenti significativi:

  1. Tool-use nativo Ollama+Qwen+Gemma (ADR 0042): niente parser JSON fragile, il provider emette tool_calls strutturati.
  2. Data piping schema-guided (ADR 0043): output di step N referenziato via from_step: N (lista) o {{stepN.field}} (scalare).
  3. Prefilter token-based (ADR 0073): bag-of-words su affinity + verbi canonical IT/EN. ADR 0073 documenta che il bench embedding vs token e' stato vinto dal token-based (5/5/2026).
  4. Adaptive re-rank intra-turno (ADR 0072): post-step, re-ranking additivo cap 2×k_max.
  5. Fast path deterministico (ADR 0094): tabella chiusa di pattern 1:1 ("che ore sono", ecc.) cortocircuita il PLANNER per ~24 query banali IT+EN.

Cap chiusi:

  • cap_steps = 30 (limite di passi per turno);
  • cap_same_executor = 10 (anti-loop sullo stesso tool);
  • cap_max_per_turn = 3 (per executor non-action su intero turno, anche non consecutivi);
  • DUPLICATE_CALL detection: stessa call args identici = forza final_answer.

Lo seed-step injection (ADR 0099): se la query contiene un URL completo, il runtime inietta read_urls_html(urls=[URL]) come step 1 prima di interpellare il PLANNER. Bypass deterministico nato dal turno federvolley del 7 maggio 2026 dove il PLANNER aveva scelto find_urls nonostante la regola prompt.

1.6 Prompt-as-data multilingua

ADR 0092 (5 maggio 2026): i prompt LLM vivono su filesystem in runtime/prompts/<lang>/<role>.j2, engine MiniJinja (Rust core), accesso via prompt_loader.get(role, lang, **vars). Nessuna stringa di prompt inline nei moduli Python.

L'evoluzione piu' interessante e' il 3-layer planner (ADR §10.6.45, 11 maggio 2026): il prompt PLANNER, originariamente monolitico ~600 righe, e' stato splittato in: 

runtime/prompts/<lang>/planner/
    _core.j2          identita', vocabolario, regole, esempi generali
    sections/*.j2     mail, calendar, web, photos, system, admin_shell
                      (iniettate selettivamente per intent)
    _footer.j2        project_paths, users_known, now_vars dinamici

prompt_loader.compose("planner", lang, sections=[...], **vars) assembla i 3 strati con cache LRU. La selezione delle sezioni e' deterministica via vocab.detect_target_objects; sections=None include tutto (graceful degrade per intent.confidence bassa).

Pattern latest-wins per allineamento multilingua: ogni dir lingua ha sibling .lang_state.json con {version_hash, source_lang, source_hash}; il daemon i18n_translator.align_prompts() (scheduler v2 daily@02:00) fa hash-content compare (non mtime), sceglie edit-source via mtime + tie-break alfabetico, ritraduce le altre lingue divergenti. Niente IO extra nel critical path get(role, lang, **vars).

Il bench format/budget (13 maggio): test 3x2 (prose/yaml_raw/json_raw × reasoning_budget 0/256). Verdict: json_raw + budget=0 vince Pareto su latenza e qualita' (85.1 s, q=4.40 vs prosa). Cambio drop-in via env METNOS_SECTION_FORMAT=json_raw.

1.7 Plugin areas: backends per OBJECT

ADR 0130 (14 maggio 2026, freschissimo): i provider backend sono organizzati per OBJECT canonical: 

runtime/backends/
    events/        local_ics.py    google_workspace.py
    messages/      email_metnos.py  telegram_bot.py  gmail_google_workspace.py
    files/         local.py        google_workspace.py
    urls/          httpx_default.py playwright_stub.py

Il pattern: il dispatcher canonical <verb>_<object> importa from backends.<object> import <provider>. La directory radice e' l'OBJECT, allineata 1:1 a vocab.OBJECTS; il provider e' il file. Niente registry magico, niente discovery dinamico: drop-in deterministico.

ADR 0132 (14 maggio) descrive il complemento futuro: plugin esterni in ~/.local/share/metnos/plugins/<provider>-<name>/<object>.py con manifest che dichiari [(object, provider), ...]. Trust gate enabled=true + consent_token, precedenza builtin > plugin. La CLI metnos-plugins e' pending.

Pattern A vs B La scelta backends/<object>/<provider>.py (A) su backends/<provider>/<object>.py (B) e' motivata esplicitamente: l'OBJECT §2.2 e' la radice deterministica del dominio, il dispatcher canonico importa 1 cartella sola, e gli helper provider-shared (OAuth, ecc.) restano nello skill agentskills.io fuori dal runtime. Decisione coerente con §7.2 (semplicita').

1.8 Synth admission policy (4+2 layer)

ADR 0114 (8 maggio 2026) introduce una difesa stratificata contro i synth scadenti. ADR 0122 (proposal auto-evaluator) aggiunge un 5° gate preventivo:

  1. L1 vocab semantic gate (deferred): controllo che il synth proposto aderisca semanticamente al verbo canonico scelto in stage 1.
  2. L2 affinity overlap guard (loader.py::_check_affinity_overlap): Jaccard pairwise >= 0.5 vs handcrafted o synth piu' vecchio = rejected. Catalog espone i rejected in catalog._rejected[].
  3. L3 efficacy ager (runtime/executor_aging.py::apply_efficacy_ager): sorgente ~/.local/share/metnos/turns/*.jsonl filtrato per chosen_tool. Synth con invocations >= 100, success_rate < 0.20 -> deprecated; < 0.05 dopo altre 30 invocations -> archived. Handcrafted MAI demoted.
  4. L5 smoke battery con expected_first_tool: 8+ query "must work" con asserzione del tool atteso al primo step. Routing canary integrato in smoke.py.
  5. L6 LLM semantic verifier (stage 6): confronta description vs code, fail-safe (errore = reject in dev, ammetti in prod).
  6. L7 admission imported skills (ADR 0126): trust-classify all'importer agentskills.io, fail-closed.

La policy e' un caso di studio: 4 layer cumulativi tutti deterministici (§7.9), solo L6 usa LLM e mai per la decisione finale.

1.9 Determinismo come principio strutturale

CLAUDE.md §7.9: codice deterministico > LLM se equipotente, equiefficace o se codice deterministico [sarebbe] troppo complesso. LLM solo quando deterministico e' inefficace, troppo complesso, o impossibile.

Esempi concreti applicati:

ComponenteSenza determinismoCon determinismo
Fast path query banali PLANNER LLM 53.4s per "che ore sono" Tabella chiusa 24 pattern IT+EN, 0 LLM, < 50ms (ADR 0094)
Vaglio safe verbs Giudice LLM ~1.5-3s per step read-only vocab.SAFE_VERBS shortcut, 0 LLM (ADR 0107)
Output formatter describe_entries LLM per ogni "stato server" runtime/output_format.py markdown channel-agnostic (ADR 0095)
Implicit actions LLM decide ask vs skip vs auto vocab.detect_implicit_actions + confidence weights (ADR 0129)
Synth admission L2-L5 LLM giudica overlap, efficacia, routing Jaccard, success_rate counter, expected_first_tool (ADR 0114)
Reverse pattern LLM scrive funzione reverse() per ogni executor Catalogo chiuso 5 pattern (swap_src_dst, restore_blob_backup, ...) (ADR 0060)
Credentials extraction LLM parses query, classifies, redacts Regex deterministici + binding hint (ADR 0089)
HTML rendering LLM o template engine generico html_sanitizer whitelist chiusa channel-aware (ADR 0109/0110)
Thinking-leak scrubber LLM post-processing Regex su line-by-line trigger EN+IT chirurgico (ADR 0102)

L'effetto e' che il LLM e' usato solo dove davvero serve creativita' o ragionamento sotto-determinato: planning, synt stage 4-5, intent extraction (gemma 4 26B middle ~370ms), describe_entries, classify_entries. Il "core decisionale" e' codice Python testabile.

1.10 Punti di leakage architetturale e debito tecnico

Un'analisi neutra deve riconoscere anche i punti di tensione:

  • agent_runtime.py monolitico (5280 righe): il main loop incorpora seed-step, fast-path, vaglio invocation, scrubbing, hallucination detection, health prepend, output formatter, multi-pipeline implicit_actions, resume_with_scratchpad. L'estrazione di moduli e' iniziata (vedi fast_path, orchestration) ma il file resta il choke point di tutta la logica di turn.
  • Vocabolario chiuso con escalation a Roberto: aggiungere un verbo richiede modifica di vocab.py + prefilter._VERB_TO_CANONICAL + intent_extractor + opzionalmente un addendum stage 5. Single-maintainer discipline; ma se Metnos diventa multi-user developer, questo collo di bottiglia diventa visibile.
  • Synth admission L1 deferred: il "vocab semantic gate" non e' implementato. Oggi L2-L6 coprono il caso, ma il design originale prevedeva 6 layer.
  • i18n.sqlite con chiavi pending: 92 EN + 116 IT chiavi needs_translation=1 in i18n.sqlite + manifest description multilang stale. Il daemon di traduzione scheduler v2 (TODO traccia in MEMORY.md) e' pianificato ma non ancora wired.
  • Sandbox bubblewrap fallback graceful: se bwrap non e' installato, il comando viene eseguito senza wrapping (la pseudo-sandbox di agent_runtime resta attiva come prima). Strato di sicurezza weakened in ambienti dove bwrap manca.
  • Stage 6 verifier "fail-safe = admit": scelta pragmatica (se il verifier crash, layer L2/L3/L5 sono ridondanti), ma in scenario adversarial un attaccante potrebbe forzare crash del verifier per bypass.
  • Reverse pattern catalogo a 5 entries: tutti i synth con revertible=true devono dichiarare uno di {swap_src_dst, delete_created_dirs, delete_created_paths, restore_blob_backup, delete_<obj>_by_id}. Se emerge un caso non riducibile, l'estensione richiede design + ADR.
  • Test rotti vs daily test: CLAUDE.md §8.1 vieta di disabilitare, impone iterazione. La regola e' chiara ma in pratica diversi turn logs mostrano "8 fail pre-esistenti" trasportati di sessione in sessione.

2. Sicurezza

2.1 Threat model esplicito

Il modello di minaccia di Metnos e' atipico per un personal assistant:

  • LLM planner (Gemma 4 26B locale, think=true) e' considerato untrusted: puo' allucinazare, deviare, leakare token interni nel canale text. Patch: _scrub_thinking_leak (ADR 0102), prompt prescrittivo §6, vaglio post-LLM.
  • Executor synth on-the-fly: il PLANNER puo' richiedere generazione di nuovo codice Python eseguito sul host. Synth pipeline genera firma Ed25519, manifest + signature; loader.verify_executor rifiuta executor con digest mismatch.
  • Input utente: testo, immagini, allegati. Pattern di credenziali in chiaro intercettati e cifrati prima del PLANNER (ADR 0089 Strato 1).
  • Skill agentskills.io e plugin esterni: codice di terzi importato. Trust gate L7 (ADR 0126), enabled flag, consent_token (ADR 0132 pending).
  • Multi-utente guest: cross-user send vaglio (ADR 0084). Host = gatekeeper.

2.2 Vaglio: guardia + giudice + safe-verb shortcut

Sorgente: /opt/myclaw/runtime/vaglio.py (348 righe). Architettura a due fasi:

  1. Guardia (binaria): guard_check. Forbidden path pattern chiusi (~/.ssh, /etc/passwd, /etc/shadow, /root, /boot, /sys, /proc, /dev/{sd,nvme,mmcblk,loop}, .aws/credentials, .gnupg). Comandi shell pericolosi (rm -rf /, mkfs, dd of=/dev/, fork bomb, chmod -R 077X /).
  2. Giudice (graduato): judge_score. Backend selezionato via env METNOS_JUDGE_KIND:
    • rule-based-v1 (default): heuristica deterministica, soglia 0.30. Bonus per intent menziona executor, penalita' per path traversal o chiavi anomale.
    • llm-v1 (opt-in): Gemma 4 26B middle tier, prompt sulle 4 Leggi e i telos. ~1500-3000 ms/step.
  3. Safe-verb shortcut (ADR 0107): dopo la guardia, se l'action e' in vocab.SAFE_VERBS (11 verbi read-only/pure-compute), il giudice e' bypassato con score=1.0. La guardia esegue PRIMA, quindi read_files su ~/.ssh/id_rsa resta bloccato.

La separazione deontologia (binaria) / teleologia (graduata) e' descritta come "evita l'auto-conferma del modello" nel capitolo 11.1 dell'Architettura. Una decisione di design solida: in molti agent runtimes, lo stesso LLM giudica E propone, con un fenomeno noto di confirmation bias.

2.3 Sandbox bubblewrap

Sorgente: /opt/myclaw/runtime/sandbox.py (219 righe). Wrapper bubblewrap (bwrap) che applica:

  • System paths read-only: /usr, /bin, /sbin, /lib, /lib64, /etc, /opt;
  • /tmp tmpfs privata, /proc, /dev minimal;
  • Code dir read-only (codice executor non modificabile durante invocazione);
  • Bind capability-driven: ogni fs:read/write capability del manifest espone i path nei hint come bind r/o o r/w;
  • Network: se nessuna network:* capability, --unshare-net;
  • --unshare-user, --unshare-ipc, --unshare-uts, --die-with-parent.
Punto debole strutturale sandbox.bwrap_available(): se bwrap non e' nel PATH, oppure se METNOS_SANDBOX=0, wrap_command() ritorna il comando invariato. Il commento dichiara "la pseudo-sandbox di agent_runtime resta attiva come prima", ma quella pseudo-sandbox e' un filtro path/host nel runtime Python, bypassabile da subprocess Python che lancia altri processi o tocca syscall direttamente. Su sistemi enterprise dove bwrap manca, la difesa reale degrada a "fiducia nel synth verifier + vaglio".

Limiti dichiarati: niente landlock (kernel >= 5.13 + syscalls custom), niente Docker namespace, niente seccomp custom. Il design e' "MVP utility, non production hardening".

2.4 Admin / sudoer / consent token HMAC

ADR 0070 (2 maggio) + ADR 0087 (CIFS mount via admin/sudoer) + ADR 0088 (admin esposto al PLANNER). Architettura: 

PLANNER (Gemma 4 26B) → admin(query NL)
                          │
              ┌───────────┴───────────┐
              │ admin deliberativo:    │
              │ - canonicalize comando │
              │ - check graylist/wl    │
              │ - genera argv          │
              │ - emette approval card │
              │ - genera consent_token │
              │   HMAC TTL 600s        │
              └───────────┬───────────┘
                          │
                       user "si"
                          │
                          v
                    sudoer (executive)
                    - verify token
                    - exec via NOPASSWD
                    - log audit

admin e' un builtin verb-unique (ADR 0069): verbo fuori dal vocabolario chiuso, registry VERB_UNIQUE_REGISTRY in runtime/loader.py. Esposto al PLANNER (ADR 0088, deroga all'invariante ADR 0069 originale) per permettere risoluzione di intent shell-adjacent ("monta share Public da NAS").

Safety signatures (ADR 0071): graylist / whitelist / blacklist / forbidden canonicalizzate binary:subcommand:target_kind. Visibili al PLANNER come ordinari executor find_signatures_*, write_signatures_*.

HMAC consent token: TTL 600s in ~/.local/share/metnos/.admin_consent_key. Il key e' un secret separato dall'admin.key master (che protegge il credentials store).

2.5 Credentials store Fernet + HKDF

Sorgente: /opt/myclaw/runtime/credentials.py. Cipher: cryptography.fernet.Fernet, chiave derivata da ~/.config/metnos/admin.key via HKDF-SHA256 con salt random per file. Storage: ~/.config/metnos/credentials/<domain>.json.age mode 0600.

Layout file: 

<salt_base64>\n
<fernet_token>

Validazione domain: rifiuto di caratteri /, \\, \\x00, .. per bloccare path traversal. fingerprint(domain) espone sha256[:16] della pwd per audit; supporta entrambi i layout (ADR 0082 legacy form_data e ADR 0089 flat).

Invariante metnos:credentials_metadata_only (ADR 0123 §2.2): i 3 executor find/set/delete_credentials non ritornano mai cleartext al PLANNER. FORBIDDEN_KEYS in credentials.py espone una blacklist chiusa: value, values, token, secret, secrets, api_key, password, passwd, client_secret, cleartext, raw. La funzione assert_no_secrets_in_return valida ricorsivamente che nessun campo proibito porti valore non vuoto. Layer di difesa centralizzato (regola del 3 §7.2).

ADR 0131 (14 maggio) consolida: tutti i segreti SMTP/IMAP per Migadu, register.it, tiscali sono migrati dai file .env plaintext nello store cifrato (smtp_metnos_system, smtp_metnos_roberto, smtp_mykleos, ecc.). CLI one-shot credentials_migrate.py idempotente. ADR 0131 estende anche a Google API keys, Telegram bot token, Google Maps API.

ADR 0001 (28 aprile, primo ADR): undo come hook runtime generico con reverse(plan, results) esposta dall'executor. Storage append-only in ~/.local/share/metnos/undo.jsonl con fsync+flock. find_crashed() al boot rileva record pending senza done.

2.7 Trust gate per skill importer e plugin esterni

ADR 0123 (10 maggio) introduce l'importer agentskills.io. La pipeline in 5 stadi (parser + translator + codegen Jinja + LLM stage 4 description + admission 5 layer) trasforma uno SKILL.md in executor firmato indistinguibile da un synth interno.

Trust mechanism:

  • Provenance dichiarata nel manifest: [provenance] imported_from, source_version, source_sha256, imported_at;
  • Verb boundary (ADR 0128): la tabella runtime/skill_vocab_map.json::contextual mappa <domain>:<action> a {target_kind, side_effect, verb}. Verifier deterministico runtime/importer_verb_verify.py::check_plan rifiuta plan che invocano verb-provider scorretti (es. gmail get MSG_ID deve diventare read_messages, non get_messages);
  • Capability invariant metnos:credentials_metadata_only su skill che toccano credentials;
  • L7 admission (ADR 0126): trust-classify all'importer, fail-closed.

ADR 0132 (14 maggio) prepara il pattern per plugin esterni non agentskills.io: manifest + trust gate enabled=true + consent_token. Precedenza builtin > plugin. CLI metnos-plugins pending.

2.8 Punti deboli e gap residui

Una valutazione neutra deve riconoscere:

  • HMAC consent token TTL 600s: in scenario di shoulder-surfing (utente Telegram con dispositivo compromesso), 10 minuti sono molti. Mitigato parzialmente dall'approval card "monta share X come utente Y", che richiede conferma esplicita.
  • Sandbox bypass quando bwrap manca: vedi §2.3. Soluzione completa richiede landlock (kernel-side) o container per executor untrusted.
  • OAuth token plaintext in skill scope: skill agentskills.io google-workspace memorizza google_token.json in chiaro in ~/.local/share/metnos/skills/google-workspace/. Non e' nel credentials store cifrato.
  • Vaglio rule-based default: METNOS_JUDGE_KIND=rule-based-v1 e' la default. Soglia 0.30 e' permissiva (regime "benevolente"). Per scenari sensibili dovrebbe essere LLM-based + soglia 0.70.
  • Audit log non firmato: ~/.local/share/metnos/turns/*.jsonl e vaglio/<YYYY-MM>.jsonl sono append-only ma non firmati. Un attaccante con access locale puo' rewriting.
  • Capability hint non enforced cross-process: i path nei capability hint sono usati per bind bwrap, ma il sandboxing finisce quando l'executor finisce. Output passato al PLANNER puo' contenere data esfiltrata senza essere bloccata (mitigato da scrubbing credentials).
  • Reverse blob backup <= 10 MB (ADR 0001): scrittura di file grandi non e' reversible. Trade-off pragmatico ma documentato.

3. Innovazione

Una valutazione sincera deve mettere in luce dove Metnos diverge dall'orizzonte degli agent framework di oggi (LangChain, AutoGen, CrewAI, Goose, Open Interpreter, Claude Code, Cursor, Semantic Kernel). Non tutti i confronti sono favorevoli al progetto: alcune scelte sono ortogonali, non superiori.

3.1 Vocabolario chiuso come anti-drift LLM

Nessun agent framework mainstream impone un vocabolario CHIUSO per i nomi dei tool. LangChain e AutoGen permettono nomi arbitrari (libera composizione "snake_case description"); CrewAI usa role descriptions; Goose si appoggia a MCP che ha schema JSON per tool ma non vincola i nomi.

La motivazione di Metnos: se il PLANNER e' un Gemma 4 26B local, la sua capacita' di tenere consistenza su un naming aperto degrada rapidamente. Esempi nei turn log: "fetch_news", "search_internet", "get_emails" diventano collisioni di lessico dopo poche centinaia di turni. Con vocabolario chiuso, ogni intent ha UNA mappatura canonical e i sinonimi sono nel prefilter, non nel catalogo.

Il discrimine tra i 5 verbi-produttori (find vs get vs read vs list vs filter) e' un esempio di micro-design semantico raro: la maggior parte dei tool framework usa "search" come catch-all.

Pattern adiacente (in letteratura): Domain-Specific Languages as the deterministic backbone of AI agents [Endo 2026, Microsoft Azure dev blog]. Metnos applica il pattern in modo radicale: il DSL e' il nome stesso degli executor, non un layer separato.

3.2 Vettorialita' come boundary architetturale

Nei principali framework, il pattern e' "tool single-call". Per processare 98 file, il PLANNER emette 98 tool call. LangGraph mitiga con StateGraph batching, ma il default e' single-call.

Metnos inverte: vettoriale per costruzione. ADR 0041 e' una decisione di boundary: iterazione interna allo executor, branching su osservazione al PLANNER. Questo cambia drasticamente il profilo di latenza per query data-intensive: "sposta 98 foto" = 1 step (non 98).

3.3 Synt multistage procedural/creative tier-split

La separazione "stadio procedurale = LLM medium / stadio creativo = LLM wise" non ha un equivalente diretto in letteratura agent. La tecnologia piu' vicina: chain-of-thought decomposition e self-refine. Tuttavia:

  • Self-refine: usa lo stesso modello per generare e critiquare (Madaan et al. 2023);
  • Chain-of-thought: e' un pattern prompt, non un'architettura di tier.

Metnos esplicita 3 tier (fast/middle/wise) e li assegna per criterio "task procedurale vs creativo". L'effetto: stage 1 NAMING (lookup nel vocab) gira su middle ~300ms, stage 5 CODE gira su wise (think=true) ~30s. L'investimento computazionale e' proporzionato al compito.

Adozione su scala piu' ampia: Anthropic stesso ha discusso il pattern in "Building Effective Agents" (2024) sotto il nome routing.

3.4 Multi-pipeline intent-implicit actions

ADR 0129 (14 maggio) introduce un pattern raro: la detection deterministica di azioni mutating sottintese. Query come "proponi 3 orari per un appuntamento di 1 ora la mattina, dopo la scelta mandami una email" hanno il verbo propone (describe) + send, ma il verbo mutating create_events e' implicito nel sostantivo "appuntamento".

Tabella chiusa vocab.OBJECT_DEFAULT_MUTATING_VERB + euristica confidence + mapping a strategy auto / ask / skip. Il decisional layer e' deterministico, il LLM solo OBBEDISCE al hint strutturato. Pattern raro in framework agentic: la maggior parte si affida al LLM per inferire azioni latenti, con failure rate misurabile.

3.5 Channel-aware HTML rendering

ADR 0109/0110 (7 maggio): la stessa risposta finale del PLANNER viene resa in due forme:

  • HTTP browser: to_safe_html_full con whitelist estesa (h1..h6, ul, ol, li, blockquote, hr, table, p, br) e GFM soft break (newline interno in <p> diventa <br>).
  • Telegram: to_safe_html subset compatibile con Telegram Bot API (b/i/code/pre/a). chunk_html spezza messaggi > 4000 char preservando <a href> via close+reopen LIFO/FIFO. time.sleep(0.05) fra chunk per rispettare rate limit ~20msg/s.

Il pattern e' poligonale: lo stesso markdown del PLANNER passa attraverso _safe_final_html dispatcher che sceglie il renderer per canale. Nessun re-prompting LLM. Determinismo §7.9 applicato a output formatting.

3.6 Auto-evaluator + promoter daemon

ADR 0122 (proposal auto-evaluator, 10 maggio) + TODO promoter daemon: chiude il loop synt_suggest → evaluator → catalog. 6 killer (uso 60d < soglia, disuso, drift, errori, ecc.) + 7 signal weighted = verdict accept|gray|reject. ETA index per stimare il tempo di promozione (path_hashes + count_60d).

Anti-pattern intercettato: synth che generano valore zero ma restano nel catalog con success_rate 0 per settimane. ADR 0114 L3 efficacy ager (post-hoc) + ADR 0122 (pre-hoc) coprono il ciclo. La maggior parte dei framework agent ha "tool registry" ma nessuno strumento di aging dei tool.

3.7 Pattern propose+create+notify

Pipeline live convergente (14 maggio): find_events_empty → get_inputs(choice) → create_events → send_messages. L'utente dice "proponi 3 orari, dopo la scelta mandami email"; il sistema risolve la pipeline lineare con il dialog manager (ADR 0090) che persistite lo stato nel mezzo, e resume_with_scratchpad riprende il turno post-pick.

La persistenza dialog state cross-turn (dialog_pending.py + 9 dialog kinds) e' un'innovazione architetturale: la maggior parte dei framework agent ha "human-in-the-loop" ma come breakpoint sincrono, non come continuation deterministica del plan.

4. Sviluppi futuri possibili

4.1 Fase 7: multi-OS, multi-user, disconnect-proof

CLAUDE.md §12: Fase 7 e' parzialmente avviata (topic 1: client Rust per executor remoti, 10 decisioni chiuse, MVP 5 settimane). I topic 2+ sono "DA AVVIARE":

  • Multi-OS: il Rust client (ADR 0046) e' progettato per Windows, Linux, macOS. Self-contained binary (ADR 0037): static-link libgcc/libstdc++/winpthread, niente VC++ Redist. python-build-standalone Astral + uv subprocess.
  • Multi-user: ADR 0083 modella host + guest. users.db in SQLite (users, user_channels) + pairing via /start <token> Telegram. Cross-user send vaglio (ADR 0084). Open: SSO, RBAC.
  • Disconnect-proof: TODO HIGH (MEMORY.md). Sync chat cross-device, offline queue, mTLS, conversation identity. Roberto preferisce fix completo (non quick-win). Effort L ~3-4 settimane.

4.2 Fase 8: stress logico

Pianificata "DOPO fase 7". L'idea (Roberto, conversazioni di fine aprile): rigorosamente stressare il sistema su query ambigue, multi-step lunghe, edge case linguistici. Il framework "iterare-test-cluster" (CLAUDE.md §8.1) e' la baseline; la fase 8 dovrebbe estendere a test adversariali.

4.3 Voce, video, real-time collaboration

CLAUDE.md §12: Fase 6 voce e' "STANDBY (riusare satellite proprietario; non bloccante)". Asset: Piper TTS + whisper.cpp gia' in toolchain self-hosted (CLAUDE.md §10.3).

Estensioni naturali:

  • Voice input: read_messages_audio + transcription whisper.cpp, inject come query testuale al PLANNER. Latency budget: ~1.5s per minuto audio.
  • Voice output: render_text_audio via Piper. Channel adapter Telegram supporta voice messages nativi.
  • Video: gia' parzialmente nel pipeline immagini (ADR 0117 unified image enrichment index). Estendere a frame extraction + VLM (Qwen2-VL gia' running su :8081).
  • Real-time collaboration: TODO HIGH (sync chat cross-device). Conflict resolution, offline queue, mTLS, conversation identity.

4.4 Client mobile (iOS, Android)

Oggi: Telegram bot + HTTP /chat WebUI (htmx + Jinja2 + uPlot). Niente client nativo mobile. Estensione naturale:

  • PWA: la chat HTTP e' gia' una HTML page, manca manifest.json + service worker. Effort S ~1-2 giorni.
  • Rust client mobile: ADR 0046 menziona Windows/Linux/macOS. Estensione a Android (NDK) + iOS (xcodebuild) richiede toolchain separata. Effort L > 2 mesi.
  • Notification push: oggi delegato a Telegram. Una PWA con push API sblocca notifiche outside-Telegram.

4.5 Plugin marketplace

ADR 0132 (14 maggio) e' il piede in plugin esterni: manifest + ~/.local/share/metnos/plugins/<provider>-<name>/. Estensione naturale: un marketplace pubblico per skill agentskills.io + plugin backend.

La direzione del settore (Anthropic ha donato MCP all'Agentic AI Foundation a dicembre 2025) e' verso protocolli standard. Metnos oggi e' MCP-adiacente: il suo tool-use e' OpenAI-compatibile via Ollama/llama.cpp, ma il pattern "executor handcrafted + synth + skill importer + plugin esterni" e' piu' ricco del singolo "MCP server".

Migrazione possibile: esporre gli executor canonical come MCP server. Lo skill importer agentskills.io di ADR 0123 e' gia' multi-vendor (Claude Code, Cursor, Copilot, Gemini CLI hanno tutti SKILL.md format). Quel ponte e' aperto.

4.6 LLM frontier come fallback integrato

Oggi: Gemma 4 26B locale + Sonnet/GPT-5 frontier come fallback (CLAUDE.md §1, §11). Tier "wise" supporta entrambi via LLMRouter; default llamacpp locale.

Estensioni utili:

  • Smart routing: per query misurabilmente complesse (multi-step >= 5, intent.confidence < 0.5, retry budget esaurito), commute a frontier automaticamente. Oggi richiede opt-in esplicito.
  • Prompt caching frontier: Claude API supporta cache (skill claude-api automatically detecta). Per il PLANNER prompt (~25KB oggi, ~5-8KB con sezioni) il cache hit rate sarebbe alto.
  • Cost tracker enforcement: cost_tracker.py esiste ma e' osservativo. Estensione: budget hard per turno, downgrade automatico a fast tier se budget esaurito.

5. Confronto con sistemi simili

Per ogni framework: stack, approccio, dove diverge da Metnos, dove converge. La tabella riassuntiva e' in §5.10.

5.1 Open Interpreter (Killian Lucas)

Stack: Python, dispatch function-call con argomento (lang, code); runtime locale (genera codice, lo esegue).

Approccio: natural language interface for computers. Il LLM genera codice Python/JS/bash che viene eseguito direttamente sull'host. Sandboxing opzionale (chiede conferma utente, mai default-no).

Diverge da Metnos:

  • Niente vocabolario chiuso: il LLM scrive codice arbitrario per ogni richiesta;
  • Niente synth + manifest + signature: codice "one-shot" per turno, non persistito;
  • Niente vaglio: confirm-then-execute, ma il LLM decide cosa eseguire;
  • Niente vettorialita' obbligatoria: il LLM scrive il loop se serve.

Converge con Metnos: tool-use locale, opt-out cloud, focus su filesystem e shell. Sandboxing weak (entrambi: bwrap quando disponibile, fallback graceful).

5.2 LangChain / LangGraph

Stack: Python + JS, AgentExecutor (legacy) o LangGraph (StateGraph, recommended 2026). 600+ integrazioni (vector DB, cloud, SaaS). LangSmith per observability.

Approccio: framework generale. Composizione tool + prompt + chain via API Python. LangGraph aggiunge stato persistente, retry, error handling.

Diverge da Metnos:

  • Tool registry aperto (nomi arbitrari): nessun vincolo lessicale;
  • Niente synth on-the-fly: i tool sono dichiarati staticamente;
  • Niente sandbox / signature / vaglio: tutto in-process Python;
  • Adopter pattern: chiama API esterne, niente self-hosting di default;
  • Niente determinismo §7.9: il LLM e' usato dovunque possibile.

Converge con Metnos: ReAct come pattern fondante (LangChain ha implementazione canonical da 2022). State persistence (LangGraph) e' simile a resume_with_scratchpad ma piu' generale.

5.3 CrewAI

Stack: Python, role-based DSL ("crews" di agenti con ruoli espliciti). Built-in task delegation. Curva di apprendimento bassa (20 righe per partire).

Approccio: multi-agent, ogni agente ha un role. Process types sequential, hierarchical. Task output passa sequenzialmente.

Diverge da Metnos:

  • Multi-agente vs single-agente: Metnos ha UN planner, CrewAI ha N agenti che dialogano per ruolo;
  • Naming tool aperto: nessun vocabolario chiuso;
  • Niente sandboxing OS-level: tutto in-process;
  • Niente synth on-the-fly: i tool sono dichiarati staticamente.

Converge con Metnos: separazione ruoli e' simile alla separazione PLANNER / VAGLIO / SYNT di Metnos (tre tier LLM). La differenza e' che CrewAI espone i ruoli come agenti dialoganti; Metnos li tiene come stages deterministici.

5.4 AutoGen / Microsoft Agent Framework

Stack: Python, GroupChat conversazionale fra agenti. Microsoft ha shiftato focus al "Microsoft Agent Framework" piu' ampio. AutoGen riceve bug fix + security patches.

Approccio: agenti che negoziano per turno via GroupChat. Ogni agent turn = full LLM call con history accumulato. Costoso per high-volume.

Diverge da Metnos:

  • Multi-agente conversazionale: Metnos ha un planner + vaglio + synt, non agenti che dialogano;
  • Niente self-hosting di default: assume Azure OpenAI / OpenAI API;
  • State in-memory (history-driven): Metnos persiste scratchpad su disk ~/.local/share/metnos/scratchpad/.

Converge con Metnos: separazione di responsabilita' fra "agenti" (in Metnos: planner, vaglio, synt) etool use. Concettualmente AutoGen e' un superset disordinato di Metnos.

5.5 AutoGPT / BabyAGI

Stack: Python. AutoGPT 2026 e' visual Agent Builder + persistent AutoGPT Server + plugin system. BabyAGI 2026 ha modular skill system + memory management. L'originale BabyAGI marzo 2023 e' archived.

Approccio: autonomous loop. AutoGPT: LLM analizza obiettivo, decompone subtasks, chiama API esterne, monitora progresso. BabyAGI: 3 funzioni cicliche (task execution, creation, prioritization) con vector memory.

Diverge da Metnos:

  • Loop ad-libitum vs cap_steps=30 di Metnos: meno controllo;
  • Niente synth typed: AutoGPT genera task in linguaggio naturale, BabyAGI usa vector memory per "skill" non strutturati;
  • Niente sandbox / signature / vaglio.

Converge con Metnos: parsimonia e non-renunciation telos (ADR 0010). BabyAGI cycle execution + creation + prioritization e' simile alla "synthesis cascade" di Metnos (compose → generate → dedupe → generalize → specialize). Metnos formalizza la cascade in 5 strategie orthogonalizzate; BabyAGI e' piu' fluido.

5.6 Claude Code (Anthropic) / Cursor / Aider

Stack:

  • Claude Code: agent CLI Anthropic. Tool use (Read, Edit, Bash, ...), legge codebase, esegue comandi, scrive file end-to-end. Sandbox OS-level (in versione recente).
  • Cursor: IDE wrapper VS Code + AI features. Cloud agent in sandboxed VM con repo clone, apre PR finita. Local agent con streaming.
  • Aider: terminal AI pair programmer + git. Editing diretto + meaningful git commits. Token-efficient (4.2x meno di Claude Code per task equivalente).

Approccio: coding-focused. Claude Code agent-first, Cursor IDE-first, Aider terminal+git.

Diverge da Metnos:

  • Domain: coding vs personal assistant. Metnos non e' una coding tool primaria (anche se via admin/sudoer puo' eseguire comandi shell);
  • Frontier-LLM-dependent: tutti e tre assumono cloud API. Metnos e' self-hosted by default;
  • Niente vocabolario chiuso, niente vettorialita' obbligatoria, niente synt.

Converge con Metnos: tool-use nativo (function calling), edit diretto filesystem, agente-first (Claude Code).

5.7 Microsoft Semantic Kernel

Stack: C# + Python + Java. Kernel = orchestratore centrale; Plugin = wrapper standardizzato attorno a function (Semantic + Native). Migration in corso verso "Microsoft Agent Framework" (open-source 2025).

Approccio: Kernel + Plugins. Semantic Function = prompt template; Native Function = codice C#/Python. Il Kernel sceglie cosa chiamare.

Diverge da Metnos:

  • Plugin registry esterna vs vocabolario chiuso integrato;
  • Multi-language (.NET first, poi Python/Java) vs Python-only;
  • Enterprise-grade (Azure-friendly) vs single-tenant self-hosted.

Converge con Metnos: separazione fra orchestratore (in Metnos: planner) e plugins/executor e' parallela. Tool admission via schema (Metnos: manifest TOML, SK: function metadata).

5.8 Goose (Block / AAIF)

Stack: Rust, modular core agent loop + provider abstraction LLM (15+ provider) + extension system su MCP (70+ extensions, 3000+ MCP server discoverable). Donato da Block ad Agentic AI Foundation 2025.

Approccio: local-first open-source agent, focus developer. MCP as the wire protocol. Apache 2.0.

Diverge da Metnos:

  • MCP-native: l'estensibilita' passa interamente per MCP server. Metnos ha plugin areas (ADR 0130/0132) + skill importer (ADR 0123) ma MCP non e' wired nativamente;
  • Niente vocabolario chiuso: MCP tool sono nomi arbitrari;
  • Niente synth on-the-fly: estensione = installare un MCP server.

Converge con Metnos: local-first, multi-LLM provider, focus self-hosting. Estensibilita' come asse di design centrale.

5.9 Progetti italiani / europei

Panorama:

  • Mistral AI (Francia): leader EU per modelli open-weight. Devstral e' best-in-class per agentic coding. Mistral offre Workflows come orchestration enterprise layer. Posizionamento European sovereignty. Diverge da Metnos per scope: Mistral fornisce modelli + workflow API, Metnos e' un personal assistant completo con stack proprio.
  • AgenticSeek (open-source, Fosowl): "Fully Local Manus AI", no API. Autonomous agent che pensa, naviga, scrive codice locale. Stack: Python. Converge con Metnos su local-only + multi-step.
  • PyGPT (multi-european): desktop AI assistant multi-platform. Supporta tutti i modelli noti. Piu' simile a un wrapper di chat che a un agentic runtime; converge su self-hosting.
  • DeepSeek-V4-Pro (Cina, ma open-weight): modello base riferimento per agentic coding. Non e' un framework agent ma un foundation model.

Nel panorama italiano specifico non ho trovato un progetto open-source equivalente a Metnos (single-developer + microarchitettura proprietaria + 3-settimane di sviluppo intensivo + 129 ADR documentati). E' un progetto di nicchia ma con qualita' tecnica indipendente.

6. Valutazione complessiva

6.1 Punti di forza

  • Coerenza disciplinare. La quadrupletta CLAUDE.md + ADR registry + memory persistente + vocabolario chiuso forma un sistema di vincoli che si rinforzano a vicenda. Pochi progetti di scala simile mostrano 129 ADR datati con tracciabilita' decisionale completa.
  • Determinismo come principio strutturale. §7.9 e' applicato rigorosamente: ogni volta che il LLM sarebbe equivalente al codice, il codice vince. L'effetto netto: latenza p50 dei turni "trivial" sotto 100ms (fast path), latenza p99 dei turni complessi dominata da gemma 4 26B think=true (~30s), niente fluttuazione stocastica nascosta.
  • Sicurezza stratificata. Guardia binaria + giudice graduato + safe-verb shortcut + sandbox bubblewrap + credentials cifrate Fernet + reverse pattern catalogo + signature Ed25519 sui manifest. Nessun layer e' presente "perche' moderno"; ognuno e' motivato da uno scenario concreto in ADR.

6.2 Punti deboli

  • Single-maintainer scalability. Il vocabolario chiuso richiede escalation per ogni nuovo verbo. Il progetto e' single-developer (Roberto Brunialti); la disciplina che oggi e' un vantaggio diventera' un collo di bottiglia se Metnos aprira' contributor esterni.
  • agent_runtime.py monolitico. 5280 righe in un singolo file. Concentra fast-path, prefilter, vaglio invocation, scrubbing, hallucination detection, output formatter, resume logic. Refactor in moduli e' iniziato ma incompleto. Difficile per un nuovo lettore mappare il flusso.
  • Sandbox bypass quando bwrap manca. Su sistemi senza bubblewrap, la difesa reale degrada a "fiducia in vaglio + synth verifier". Non e' enterprise-ready per sistemi sensibili senza un secondo layer (landlock, container, VM).

6.3 Opportunita'

  • MCP bridge. Esporre gli executor canonical come MCP server renderebbe Metnos un cittadino di prima classe nell'ecosistema Anthropic/Block/OpenAI (10k+ MCP server pubblici a marzo 2026). Lo skill importer agentskills.io di ADR 0123 e' gia' il ponte multi-vendor.
  • Plugin marketplace. ADR 0132 e' il primo passo. Un registry pubblico di plugin per backends/<object>/<provider>.py renderebbe Metnos estensibile dall'utente finale senza editare il runtime.
  • Mobile via PWA. La chat HTTP e' gia' una HTML page htmx + Jinja2. Manifest PWA + service worker = ~1-2 giorni di lavoro, sblocca install-on-home-screen e push notification fuori da Telegram.
